## 一、背景：从"曝光度"到"有用度"

U 线落地后，heat 排序的输入是 hit_count——它度量的是"被检索到"（曝光），不是"被用上"（采纳）。一条每次都被搜到、从来没人用的笔记，和一条每次都被搜到且真正解决问题的笔记，在数据上无法区分。P1 三项就是补上这后一半信号并消费它：

1. **A 线（采纳信号）**：让"Agent 实际引用了哪条召回结果"变成可记录的数据（teamai 的 upvoted 票），并回流进 heat 排序。
2. **B 线（低采纳检查）**：消费采纳数据做质量诊断——"高频召回零采纳 = 内容相关但不够 actionable"（teamai quality-update 信号），成为 lint 第 17 项检查。
3. **C 线（promote 晋升）**：消费采纳数据做生命周期升级——被反复采纳的笔记 AI 重写为"去个人化"的正式 wiki 页面（teamai promote 机制），打通 notes → wiki 的断层。

依赖链：B、C 都读 A 产生的 adopted_count，A 先行；B/C 可并行。

## 二、A 线：采纳信号与投票回流（#4）

### 2.1 声明约定（数据的来源）

Agent 在最终回复（或工作过程中的 assistant 轮次）里声明实际引用的召回结果：

```
<!-- codewiki:referenced-docs: ["notes/pitfall-port-conflict.md", "wiki/modules/MCP_Cache.md"] -->
```

- 路径格式与 query_wiki 返回的 `file` 字段完全一致（相对 output_dir），Agent 零转换成本；
- 声明是**自觉约定**（同 teamai），产出为下界信号：漏报有（忘了声明）、误报少（不会把没用的声明进来）——做排序权重够用，做严格考核不行，此定位写进文档；
- 约定的两处植入点：query_wiki 返回 JSON 顶层加一句 `adoption_hint`（提示 Agent 引用结果时带上声明注释）；`init-wiki` prompt 写入 AGENTS.md 的使用建议段补一条约定。

### 2.2 解析与记录（数据的采集）

解析点放 **`capture_conversation`**（单一入口，MCP 调用与 IDE hook 两条路都经过它，与 K 线 friction 同款集成点）：

- 新增纯函数（放独立模块 `codewiki/mcp/tools/adoption.py`，与 friction.py 同风格）：`extract_adopted_docs(turns) -> List[str]`——扫描 assistant 轮次中的声明注释，正则提取 JSON 数组，路径规范化（反斜杠→正斜杠），忽略不存在的路径；
- `handle_capture_conversation` 在 friction 评分后调用，有采纳时写库（无采纳零 I/O，capture 保持轻量）。

**存储：同库新表，retrieval_stats 表零变更**

```sql
CREATE TABLE IF NOT EXISTS adoption_events (
    capture_key TEXT NOT NULL,   -- source_session_id；无会话 id 时用 content_hash
    doc_path    TEXT NOT NULL,
    adopted_at  TEXT NOT NULL,   -- YYYY-MM-DD
    PRIMARY KEY (capture_key, doc_path)
)
```

幂等性设计：同一会话被 supersede 重捕（transcript 变长重写 raw），capture_key 相同 → `INSERT OR IGNORE` 不重复计数；无 session id 的手动捕获用 content_hash 做 key，内容不变不重计。极端情况（重捕后新增了声明）按新 doc_path 计一次——语义正确：那是新的一次采纳。mtime 缓存天然复用：adoption_events 与 retrieval_stats 同库，写采纳会 bump db mtime，`_load_retrieval_usage_map` 的 mtime 缓存自动失效重读。

### 2.3 heat 公式升级（数据的消费）

`compute_usage_heat` 增加第三参数 `adopted_count`（默认 0，向后兼容现有调用与测试）：

```
boost = 1 + min(boost_cap, 0.03·ln(1 + hit_count) + 0.06·ln(1 + adopted_count))
```

- 采纳权重是召回权重的 2 倍（teamai 是 3 倍，我们区间更保守故取 2），总增益仍被 boost_cap 封顶（默认 0.15）——热度信号再强也压不过相关性；
- 冷惩罚不变（仍基于 hit_count/last_hit）；
- **注**：当前 usage_map 是 `file_path → (hit_count, last_hit)` 二元组，升级为三元组 `(hit_count, last_hit, adopted_count)`，`_load_retrieval_usage_map` 的 SELECT 改为对两表做合并（adoption_events 表缺失时 adopted=0，静默降级）——cache.py 与 wiki_search.py 双路径的解包点同步改。

### 2.4 配置与透出

- `schema.yaml`（根 + templates 双份）`conventions.usage_ranking` 增补：`adopted_weight: 0.06`（与 recall 的 0.03 对偶，可调为 0 关闭采纳影响）；
- query_wiki 结果条目的 `usage` 字段扩为 `{hit_count, last_hit, adopted_count}`（消费方字段形状稳定原则，无记录补 0）；
- `wiki_stats` 的 stats 列表附带 adopted_count，支持 `sort_by=adopted_count`。

### 2.5 nudge-once（防漏报的软提醒）

teamai 的经验：Agent 召回了却忘声明时，Stop hook 检测到"召回了但没有任何声明注释"就用 marker 文件 nudge 一次。我们的对应：capture 时若 turns 里出现过 query_wiki 的调用痕迹（assistant 轮次含检索结果特征）但无任何声明注释，在 capture 返回 JSON 加 `"adoption_nudge": true` 字段（提示文案一句话）——只提示一次、不阻塞、不重复。**降级为可选实现**：特征检测易误判，v1 仅做返回字段提示（IDE hook 打印可见），不做状态文件。

## 三、B 线：lint 新检查项 low_adoption（#5）

### 3.1 检查定义

第 17 项检查 `low_adoption`（severity: warning）：

```
判定对象：notes/ 下 status=stable 的笔记
触发条件：hit_count ≥ min_hits (默认 5)
       且 adopted_count ≤ max_adopted (默认 0)
       且最近 60 天内仍被检索过（last_hit ≥ 60 天前，排除"曾经热过现在已死"的——那种归 stale_notes 管）
message：Note '<title>' was recalled N times recently but never adopted —
         内容可能相关但不够 actionable，建议按 query_page 格式重写（补充步骤/命令/预期结果）
```

三参数语义与 teamai quality-update（minRecalled=5, maxUpvoted=1, minUsers=2）对齐，去掉 minUsers（我们是单机单用户信号，无多用户维度）。

### 3.2 实现与同步约束

- `wiki_lint.py`：`_ALL_CHECKS` 集合加 `"low_adoption"`；新函数 `_check_low_adoption(output_dir, ...)` 读 retrieval_stats.db 两表（复用 A 线的 usage map 加载，或直接小查询——lint 是低频操作，直接查库即可）；
- **registry.py 的 checks 枚举同一提交同步**（吸取 type_filter 漏 scenario、mode 加 check 的教训：MCP 输入校验先于 handler，枚举不同步则合法输入被拒）；
- lint description 里"16 项检查"的文案更新为 17 项（README 两语言版同 PR 更新，遵循 teamai CLAUDE.md 那条"行为变更必须更新所有描述它的文档"的纪律——我们自己的约定）；
- 配置：`conventions.usage_ranking.low_adoption: {min_hits: 5, max_adopted: 0, recent_days: 60}`。

### 3.3 与既有检查的边界

- `stale_notes`：时间维度（多久没验证）——本检查不管时间窗内的采用情况；
- `note_clusters`：数量维度（同模块同类笔记太多）——不管质量；
- `low_adoption`：**效用维度**（被需要但不被满足）——三者正交，互补不重叠。冷启动保护：无 adoption_events 表或全库零采纳记录时检查静默跳过（避免 A 线刚上线、还没人声明过就把所有热笔记全报警）。

## 四、C 线：promote 晋升机制（#6）

### 4.1 机制形态：检测自动化 + 执行 prompt 化

遵守"不新增 MCP 工具"约束，promote 拆成两半：

1. **检测（自动化）**：`wiki_stats` 新增 `promotion_candidates` 段（与 `cold_candidates` 同款）——数据驱动地找出该毕业的笔记；
2. **执行（prompt 化）**：新增 workflow prompt `promote-note`——Agent 按提示完成"读取原笔记 → 选择目标页面类型 → 去个人化重写 → write_doc_file 落 wiki/ → 回标原笔记"全流程。AI 重写必须由 Agent 做而非工具内置（无 LLM 原则），评审闸门保留（产出页面默认 draft 状态，走既有 confirm 流程）。

### 4.2 晋升判据

```
候选条件（全部满足）：
  status = stable（已确认的笔记才谈晋升）
  adopted_count ≥ 3（被真实采纳过，非单纯曝光）
  树龄 ≥ 14 天（metadata.date 或 verified[-1].at 距今，防新笔记速通）
  无 metadata.promoted_to 标记（防重复晋升）
```

对照 teamai（confidence≥0.90 / upvoted≥5 / ≥2 用户 / ≥14 天）：我们没有多用户维度，adopted≥3 是合理的单人等价门槛。参数进 schema 配置（`conventions.promotion: {min_adopted: 3, min_age_days: 14}`）。

### 4.3 类型路由（笔记 → 页面）

`promote-note` prompt 内置映射表（Agent 可按内容微调，映射是默认值不是硬约束）：

| 笔记类型 | 默认目标 page_type | 重写方向 |
|----------|-------------------|----------|
| pitfall / bug_fix / workaround | `query`（排查记录页） | 结构化为"症状→根因→排查步骤→修复"，补命令与预期输出 |
| lesson | `concept`（概念页） | 从个案抽象为通用机制描述，补适用边界 |
| decision / architecture | `concept` | 补决策上下文（当时备选、取舍理由），去一次性事件细节 |
| general | Agent 自行判断 | — |

重写规则（写进 prompt，源自 teamai generatePromotedContent 的类别指引）：**抹掉具体日期、人名、一次性事件**（"上周三那个订单超时" → "支付超时的典型根因"）；保留可验证的技术事实；长度不超过原笔记；原笔记的 aliases 并入新页面（检索连续性）。

### 4.4 原笔记回标（OKF 约束的关键点）

晋升后原笔记**不删除、不降级状态**（它是审计轨迹与 source_ref 链路的锚点），仅在 frontmatter 加：

```yaml
metadata:
  promoted_to: wiki/queries/port-conflict.md   # 新页面相对路径
```

**必须放 `metadata` 下**：OKF v0.2 顶层键白名单（`_OKF_TOP_LEVEL_KEYS`）不含 promoted_to，顶层直写会触发 okf_conformance 告警；metadata 是生产者私有扩展的规范位置（OKF §4/§5）。写入方式：Agent 用 `edit_doc_file` 对 frontmatter 做行级替换——不新增 frontmatter 写入点（5-writer 约束保持），`_apply_status_to_file` 等既有 writer 的 yaml 重 dump 也不会丢它（metadata 是合法顶层键）。

### 4.5 检测实现

`knowledge_loop.py` 新增 `_promotion_candidates(output_dir)`（紧挨 `_cold_candidates`，同款风格）：扫 notes/ frontmatter（status/metadata.date/verified/metadata.promoted_to）+ 读 usage map 的 adopted_count，返回候选列表（含 title/type/adopted_count/age_days/suggested_page_type 按映射表预填）。挂进 `handle_wiki_stats` 返回（try/except 静默，与 freshness/cold 同款防御）。

## 六、风险与明确不做的事

| 风险 | 缓解 |
|------|------|
| 声明靠自觉，采纳数是下界 | 定位写入文档（排序权重够用、考核不行）；adoption_hint 软提醒；adopted=0 永不惩罚（只影响加分） |
| A3 三元组改造波及双路径解包点 | 改动集中在 usage_map 构造与解包两处；既有 usage_ranking 24 项测试兜底回归 |
| B 线冷启动误报（无人声明≠质量差） | 无 adoption_events 表/全库零采纳时检查整体跳过；max_adopted 默认 0 语义就是"从未被采纳"，需配 adopted_weight 启用一段时间后再开 |
| promote 重写丢信息 | 原笔记保留不删（审计+回溯锚点）；新页面走 draft→confirm 闸门；prompt 强制"保留可验证技术事实" |
| promoted_to 顶层误写触发 okf 告警 | prompt 明确写 metadata 下；测试断言 lint 零告警 |

**明确不做（本期）：**

- 不做 marker 文件级 nudge-once 状态跟踪（特征检测易误报，v1 只做返回字段提示）；
- 不做 promote 的自动执行（检测提示 + Agent 显式走 prompt，永不自动改写笔记）；
- 不做多用户投票维度（团队共享 votes 依赖 P2 分发模型）；
- 不做 lint 的"召回多采纳少 → LLM 自动重写草稿"（teamai 的 generateUpdateDraft）——只报检查项，重写由人/Agent 显式发起。
