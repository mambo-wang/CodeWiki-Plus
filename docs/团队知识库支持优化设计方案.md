# 团队知识库支持优化设计方案（多人共享正确性专项）

> 来源：`docs/teamai-cli-调研与借鉴分析.md` P2-9 团队分发模型的重定义。原 P2 假设"知识资产需与业务仓分仓分发"，经核实 CodeWiki 天然 repowiki 随业务仓走（clone 即得），分发基建不适用；本方案改为解决真正存在的**多人共享正确性**问题。
> 日期：2026-08-22 · 状态：**设计评审中（未实施）** · 预计工作量：**T1 约 1 人日 / T2 约 2–3 人日 / T3 约 1 人日 + 一个决策**
> 前置：P0（摩擦触发/使用反馈/检索透明）与 P1（采纳信号/低采纳检查/promote 晋升）均已落地——本方案 T2 直接消费其基建。

---

## 一、背景：当前形态对 N≥2 人的四个断层（全部经源码核实）

CodeWiki 的共享面天然成立：wiki/、notes/、schema.yaml、module_tree.json 均为随 git 分发的文本，任何人 clone 后装上 codewiki-plus 即可检索。**冷启动已实测可用**（模拟队友视角——仅有 git 入库文件、无 `.codewiki/`，query_wiki 走三层降级中的 JSON 索引层，9 条结果排序正常）。但以下四个断层的本质都是"**本机派生状态 vs 共享事实源**"的边界未清理：

| # | 断层 | 证据 | 后果 |
|---|------|------|------|
| 1 | **拉取后索引静默过期** | `_open_standalone_cache`（wiki_search.py）只查 `total_docs>0`，无新鲜度检测；`.codewiki/`（SQLite 主路径）整体 gitignore | 队友 `git pull` 拿到新笔记后，本机 SQLite 不含它们且优先命中 → **检索不到刚拉下来的知识，无任何提示**；自己双机同步同样中招 |
| 2 | **P1 信号层本机碎片化** | `retrieval_stats.db` 与 `adoption_events` 均 gitignore（后者每次 query_wiki 写入，churn 决定不可直接入库） | heat 排序/low_adoption/promotion 全是单机视角：我常查的笔记在同事处是冷的；一条笔记两人各采纳 2 次，谁也触发不了晋升门槛 3 |
| 3 | **聚合文件系统性冲突** | 每次 ingest_note 全量重写 `wiki/index.md` 与 `.meta/search_index.json`；`log.md` append（本机有 fcntl/msvcrt 文件锁，跨机合并无保护） | 两人先后写笔记必冲突；频率随人数线性上涨 |
| 4 | **无身份** | `actor_id()` 返回 `codewiki/<版本>`（config.py:65）；capture_key 用 IDE session_id，跨机器可能碰撞 | verified[]、采纳遥测分不出是谁；聚合时事件可能互相覆盖 |

顺带核实的两个**非问题**（避免误投入）：冷启动不需要提交 ignore 文件（已实验证明）；`.codewiki/analysis_cache.db`（7.7MB 二进制）即使提交也无法 merge——两人各写一条笔记后 pull 二进制冲突二选一，**落选方的笔记从检索静默消失**，比现状更糟。

## 二、总体原则：md 是唯一共享事实源，一切索引本机派生

把现有 `retrieval_stats.db` gitignore 的哲学推广到全部派生状态，形成一条清晰判据：

| 状态 | 性质 | 归属 |
|------|------|------|
| wiki/ notes/ schema.yaml 的 md 内容 | 共享事实源 | 入库 |
| module_tree.json、symbol_map.json、source_registry.json 等代码分析产物 | 派生但**重建昂贵**（需 analyze_repo 源码解析） | 入库共享 |
| search_index.json | 派生且**重建廉价**（秒级，只需 md 文本 + jieba） | 本机派生（T3 决策项） |
| .codewiki/analysis_cache.db、retrieval_stats.db | 本机缓存/遥测 | 本机（T2 将遥测升级为 per-user 事件入库） |

## 三、T1 索引新鲜度自愈（最高优先级，单人也有价值）

**问题**：断层 1。SQLite 主路径与 JSON 回退路径都可能落后于磁盘上的 md 文件清单。

**设计**：搜索入口加一道**廉价新鲜度检查**，不一致自动重建，对调用方零感知。

```
检查点：wiki_search.search() 与 cache.search() 的入口
判据（两层，均为 O(清单扫描)，不读文件内容）：
  ① 数量级：磁盘上 wiki/**/*.md + notes/*.md + raw/sources/** 的文件数 N
            vs 索引 total_docs（SQLite 读 search_stats；JSON 读 total_docs 字段）
  ② 清单级（数量巧合相等时兜底）：索引 doc_key 集合 vs 磁盘相对路径集合
触发：任一不一致 → 记 warning 日志 → 调 build_full_index 重建（复用现有全量构建）
     重建失败 → 继续用过期索引返回结果（检索永不因自愈失败而中断），
                结果 JSON 附 "index_stale": true 提示调用方
频率控制：同一 output_dir 的检查结果做 60s 进程内缓存（每分钟最多一次扫描），
          避免 max_results 分页式连续调用反复扫描
```

**project.json 路径相对化**（同批修复）：`.meta/project.json` 的 `repo_path/output_dir/cache_db` 是绝对路径且入库——队友机器上必然失效，正是"陈旧 session 劫持"类问题的根源。改为写入**相对路径**（cache_db: `.codewiki/analysis_cache.db`、output_dir: `repowiki`），读取端（`_resolve_db_path` 已有 project.json 解析）加相对路径支持：以 output_dir 自身为基准 resolve；存量绝对路径条目继续兼容，读到不存在的绝对路径时静默走标准布局回退（现有行为）。

**验收**：新 clone 冷启动直接可检索（现状已过，回归保护）；`git pull` 拿到新笔记后下一次 query_wiki 自动检出并重建、能检索到新笔记；删除笔记后检索不再返回它；60s 缓存生效（同分钟内两次调用只扫描一次）。

## 四、T2 身份与遥测共享（团队价值最大项）

**问题**：断层 2 + 4。借鉴 teamai 的 per-user 文件 + pull 捎带聚合模式（借鉴其并发写解法，不借鉴其分发基建）。

### 4.1 身份

`user_id()`：优先 `git config user.name`（开发者机器必配），回退环境变量 `CODEWIKI_USER`，再回退 `os.getlogin()`。落点：

- `verified[]` 事件：`confirm_note` 写入 `{by: "human:<user_id>", at: ...}`（OKF §7 actor 约定本就支持 `human:<id>` 形态，现有 `_trust_tier` 的 human-reviewed 分级直接受益）；
- capture_key 命名空间化：`<user_id>/<session_id>`，跨机器同 session_id 不再碰撞；
- 遥测文件的文件名（见 4.2）。

### 4.2 遥测事件化 + per-user 入库

**新共享层**：`repowiki/.meta/telemetry/<user_id>.jsonl`（**入库**，每人只写自己的文件——git 文件级合并零冲突）：

```jsonl
{"t": "hit",     "doc": "notes/x.md", "at": "2026-08-22T10:00:00"}
{"t": "adopted", "doc": "notes/x.md", "at": "2026-08-22T10:05:00", "key": "u1/sess-9"}
```

- **hit 事件**：`_record_retrieval_stats` 现在写聚合表（hit_count 累加）；改为**追加一条 hit 事件到本 user 的 jsonl**，聚合表继续写（本机缓存不变，热路径零回归）；
- **adopted 事件**：`record_adoption_events` 除写 adoption_events 表外，同 append 到 jsonl（幂等键 `key` 事件内去重）；
- **聚合缓存重建**：`_load_retrieval_usage_map`（mtime 缓存的三元组来源）升级数据源——本机两表 + 扫描 `telemetry/*.jsonl` 全部用户的事件流聚合。mtime 缓存扩展为对 jsonl 目录做 mtime 快照（目录内任一文件变化即失效）。队友 pull 带来新的他人 jsonl → 下次搜索自动聚合进 heat。

### 4.3 消费端升级为团队视角（改动极小）

| 消费点 | 升级后语义 |
|--------|-----------|
| heat 排序 | hit/adopted 计数变为**全团队聚合**（两人都常查的文档更热） |
| `low_adoption` 检查 | min_hits 语义变为团队总召回；冷启动保护条件不变 |
| `_promotion_candidates` | adopted_count 跨人累计——"不同的人各自采纳过"才是真正的晋升证据（可加 `distinct_users` 字段，门槛暂维持总数 ≥3，数据攒起来后再细分） |
| `wiki_stats` | usage/adopted 字段自动变为团队口径 |

**明确不做**：不做 pull 钩子/自动同步——jsonl 就是普通入库文件，随用户日常 commit/pull 流动（比 teamai 更简：我们的 repowiki 本来就在业务仓工作流里，无需捎带协议）。

**验收**：user A/B 两个临时目录模拟——A 写笔记 + 产生 hit/adopted 事件，把 md + telemetry 拷入 B（模拟 pull），B 的下一次搜索 heat 与 promotion_candidates 反映 A 的事件；`human:<user>` 出现在 verified[]；同 session_id 跨用户不碰撞；telemetry jsonl 缺失/损坏行静默跳过。

## 五、T3 冲突面治理（一个决策 + 一天实施）

**问题**：断层 3。三个聚合文件按治理力度分档：

| 文件 | 建议 | 理由 |
|------|------|------|
| `.meta/search_index.json` | **移出 git**（加入 .gitignore） | 重建廉价（T1 自愈兜底）；移出后彻底消灭最大的全量重写冲突面，且"索引与 md 不一致"不再可能被提交固化 |
| `wiki/index.md` | 保留入库，**纳入 T1 自愈** | 它是人读的目录页（有价值）；冲突时任选一方，下次文件数变化触发自愈重建即修复。写入端不变 |
| `wiki/log.md` | 保留现状 | OKF §9 审计格式；append-only 行冲突可手工双保留；已有本机文件锁。按月分文件会破坏 §9 消费端，收益不值 |

**search_index.json 出库的迁移**：.gitignore 增条目 + `git rm --cached`（一次性）；存量 clone 的本地副本不删（继续可用，T1 会按需重建）。风险窗口：迁移提交后到队友拉取前，新 clone 首查多花一次秒级重建——已被 T1 自动化吸收。

> 此项为 T3 的**决策点**：若你更看重"clone 即带索引、离线首查零延迟"，可保留入库并接受冲突（冲突频率 = 团队写笔记频率，初期很低）。默认建议移出（一致性 > 首查延迟）。

## 六、明确不做（及理由）

| 不做 | 理由 |
|------|------|
| 孤儿分支 / worktree 分发协议 / push-pull / roles / 跨团队订阅 | teamai 为"知识资产与业务仓分仓"设计；我们 repowiki 随业务仓走，无分发问题 |
| 提交 `.codewiki/analysis_cache.db` 或 `retrieval_stats.db` | 二进制不可 merge（丢数据）；遥测表每次检索写入（churn）；聚合表共享会互相覆盖——事件化（T2）才是正解 |
| MR/PR 知识提取 CI | 与团队评审流程绑定，当前单人 confirm 闸门下无增益；归入"未来团队方向的配套项" |
| dashboard / digest 周报 | 依赖 T2 团队遥测数据积累，后置 |
| pull 时自动同步钩子 | jsonl 走日常 git 流程即可，不加协议 |

## 八、风险

| 风险 | 缓解 |
|------|------|
| T1 自愈重建拖慢首查（大库） | 重建仅秒级（jieba 分词 md 文本）；60s 检查缓存；失败降级不阻塞 |
| T2 jsonl 无限增长 | hit 事件按天聚合计数（同日同 doc 合并为一条 `{"t":"hit","doc":..,"n":3}`）；adopted 本就低频；提供 prune 工具位（后续） |
| git config user.name 缺失/重名 | 三级回退 + 文档说明 user_id 仅作命名空间不鉴权（信任模型与 confirm 闸门一致：入库即团队可信成员） |
| T3 出库后离线首查变慢 | 默认接受（秒级）；保留入库为可选决策，配置不改代码只改 .gitignore |
| 旧 project.json 绝对路径存量 | 读取端双形态兼容；不写迁移脚本（下次 close_session 自然覆盖为相对路径） |
