## 一、调研目标与本篇定位

前三篇分析已经确立了 CodeWiki-CN 的本体论升级路线（P0 激活 `ontology.yaml` → P1 占位节点+过期提示 → P2 视图渲染 → P3 Action 闭环），但存在三个缺口：

1. **理论来源偏"二手"**：Palantir 五原语、Think-on-Graph 等关键论据来自中文拆解文章，未核对官方文档/论文原文（本篇第 9、7 节核实，其中发现一处 arXiv 编号错误，见 §7.1）；
2. **检索机制缺对照**：CodeWiki 的 BM25 + hop/expand 检索要升级为"图谱上的检索"，但没有对照过业界图检索方案（GraphRAG/LightRAG/HippoRAG/Graphiti 的一手机制），不知道哪些机制在"无外部 LLM/embedding、无图数据库"约束下可落地；
3. **知识生长机制缺细节**：`stale_after` 保鲜期是单一时间戳，对照 Agent 记忆领域（Zep/Graphiti 的双时态、mem0 的 ADD/UPDATE/DELETE/NOOP 更新语义）是否够用，没有结论。

**本篇补什么**：对 11 类一手来源逐一拆解核心机制，逐条标注"适配 / 部分适配 / 不适配"（评判标准见 §二），最后给出融合新发现后的完善版 P0–P3 路线（§十四），并列出对现有三篇文档的具体修正建议（§十五）。

## 二、评判约束（所有借鉴点统一适用）

CodeWiki-CN 的硬约束：

| # | 约束 | 说明 |
|---|------|------|
| C1 | **检索不依赖外部 LLM/embedding** | `query_wiki` 纯 BM25 + 确定性图扩展；LLM 只允许出现在生成/蒸馏阶段（analyze_repo、distill_conversation 已如此） |
| C2 | **存储 = 文件系统 + SQLite 缓存** | 不引入 Neo4j 等图数据库；图结构以 frontmatter/YAML 声明 + SQLite `wiki_links` 表承载 |
| C3 | **本地轻量** | 新增机制应是"加字段/加检查项"级别，不是"加子系统"级别 |

三档评级：**适配** = 满足 C1–C3 且改动小；**部分适配** = 思想可用但需降级实现（如把图算法降级为 BFS/文件链接）；**不适配** = 依赖 embedding/图数据库/查询时 LLM，仅做方向印证。

**代码现状基线**（源码核查，2026-08-10）：

- `codewiki/mcp/cache.py:145` `_load_ontology()` **只读取 `ontology.yaml` 的 `terms` 节**构建同义词扩展表；`types`、`relations` 两节虽已写入骨架（见 `repowiki/ontology.yaml`），**在检索代码中零消费**——本体"关系图"目前是空转的。
- `codewiki/mcp/cache.py:1392` `graph_expand()`：hop 多跳沿 SQLite `wiki_links` 表（文档间 wikilink）做 **BFS + 每跳 decay 衰减**，结果带 `via` 溯源字段——这是确定性的、无 LLM 的图扩展，符合 C1，但边类型单一（"有链接"），无语义区分。
- `codewiki/mcp/tools/distill_conversation.py:48` `_VALID_NOTE_TYPES` = decision/lesson/pitfall/architecture/workaround/known_issue/general；去重仅标题 Jaccard + BM25 相关度阈值（`:87` `_DEDUP_THRESHOLD=0.6`），**无"更新/作废"语义，只有"抑制/合并/新建"**。
- `codewiki/mcp/tools/wiki_lint.py`：检查集比想象中完善——`_check_superseded_pages`（`:699`，识别 frontmatter `status: superseded|deprecated` 并解析 `superseded_by`）、`_check_stale_notes`（`:893`，**同时**要求"confirmed 且超龄 **且** 近 60 天无检索命中"，命中数据来自 `.meta/retrieval_stats.db`）、`_check_note_clusters`（`:999`，同模块同类型 ≥3 条 note 提示合并）均已存在；`knowledge_loop.py` 有 `confirm_note` / `reject_note`（OKF 状态机 draft→stable→deprecated）。
- **真正的缺口在写入侧**：`distill_conversation.py` 蒸馏产出只有 `draft` / `merged` / `suppressed` 三种去向（`:487-505`），**从不生成 `superseded_by` 标记、也从不修改被推翻的旧 note**——即读取侧（lint）的失效检查已就位，写入侧（distill）的状态迁移语义缺失，失效链路断在中间。

## 三、Microsoft GraphRAG：社区检测 + 分层社区摘要

**一手来源**：
- 论文 arXiv:2404.16130《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》（Edge 等，Microsoft Research），摘要页 https://arxiv.org/abs/2404.16130 （WebFetch 获取）
- 仓库 https://github.com/microsoft/graphrag （`gh api` 获取 README）
- 官方文档 https://microsoft.github.io/graphrag/ ，其中索引数据流与查询模式取自仓库 `docs/index/default_dataflow.md`、`docs/query/global_search.md`、`docs/query/local_search.md`（`gh api` 获取原文；docs 站点直连失败）

**核心机制**：
1. 文档切成 TextUnit（默认 1200 token）→ LLM 抽取实体/关系/claim → 构建实体图；
2. **Hierarchical Leiden 社区检测**：对实体图递归聚类直到达到社区大小阈值，形成多层级社区结构（官方文档原文："we generate a hierarchy of entity communities using the Hierarchical Leiden Algorithm"）；
3. **社区摘要（Community Report）**：LLM 为每层社区生成摘要报告；
4. 查询分两种模式：**Global search** 把社区报告分批做 map-reduce（生成带评分的中间回答再聚合），回答"整个语料的主题/趋势"类问题；**Local search** 从实体描述嵌入出发，沿 entity→text unit / entity→report / entity→relationship 扩展，回答特定实体问题。另有 DRIFT search（`docs/query/drift_search.md` 存在，本篇未展开）。
5. README 明确警告："GraphRAG indexing can be an expensive operation"——索引阶段重度烧 LLM。

**对 CodeWiki-CN 的借鉴点**：
- ✅（部分适配）**"分层社区摘要"≈ 模块级 wiki 视图**：GraphRAG 用算法聚类出"社区"再生成摘要；CodeWiki **已经有现成的层级**——AST 解析出的模块树（父模块/叶模块），等价于一棵预计算的社区层级。P2 视图渲染不需要 Leiden，只需"对每个父模块，从其子页面 + 本体 relations 渲染一份聚合摘要"，形式上就是低成本的 Community Report。这修正了现有文档中隐含的"要做社区检测"假设：**聚类靠现有模块树，摘要靠离线生成，检索零依赖**（符合 C1：Global search 的 map-reduce 在查询时需要 LLM，CodeWiki 不做，改为预生成静态视图页）。
- ✅（适配）**Local search 的"实体→多类候选→排序过滤"管线**与 `graph_expand` 的 BFS+decay 同构，验证了 CodeWiki hop 机制的方向正确。
- ❌（不适配）Leiden 算法本身、实体描述 embedding、查询时 map-reduce——需要图算法库与 embedding，违反 C1/C2；且 GraphRAG 索引成本极高，与 CodeWiki 轻量定位冲突。

## 四、LightRAG：轻量图 + 双层检索

**一手来源**：
- 论文 arXiv:2410.05779《LightRAG: Simple and Fast Retrieval-Augmented Generation》，摘要页 https://arxiv.org/abs/2410.05779 （WebFetch 获取）
- 仓库 https://github.com/HKUDS/LightRAG （`gh api` 获取 README）

**核心机制**：
1. 图结构索引 + 向量表示混合；**双层检索（dual-level retrieval）**：低层关键词（具体实体）走 local 检索、高层关键词（主题/概念）走 global 检索；
2. 明确以"不依赖社区报告和多跳推理"为卖点降低索引与查询的 LLM 调用成本；
3. **增量更新与选择性删除**：新文档即时并入图而无需全量重算；删除文档时利用索引期 LLM 缓存快速重建受影响的实体/关系。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配）**双层查询语义**：CodeWiki 的 `query_wiki` 可借 frontmatter `type` 区分"找具体对象"（type_filter=entity/module → 对应低层）与"找主题/概念"（type_filter=concept/note → 对应高层），无需 LLM 判断，纯参数化。这是对现有 `type_filter` 的语义化包装，零依赖。
- ✅（适配）**"删除后局部重建"思想**：CodeWiki 已有 git diff 增量更新，但 `ontology.yaml` relations 若由蒸馏持续生长，需要对应机制——note 被删除/确认作废时，清理或标记其贡献的 relation 边（见 §十四 P1）。
- ❌（不适配）其检索仍需查询时 LLM 生成关键词 + embedding 匹配，违反 C1。

## 五、HippoRAG：KG + Personalized PageRank 单步多跳

**一手来源**：
- 论文 arXiv:2405.14831《HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models》（Gutiérrez 等，NeurIPS 2024），摘要页 https://arxiv.org/abs/2405.14831 （WebFetch 获取）
- 仓库 https://github.com/OSU-NLP-Group/HippoRAG （`gh api` 获取 README；含后续工作 HippoRAG 2，arXiv:2502.14802《From RAG to Memory》，ICML 2025）

**核心机制**：
1. 索引期用 OpenIE 从文本抽三元组建 KG；
2. 检索期把 query 中的命名实体映射为图上种子节点，跑一次 **Personalized PageRank（PPR）**，一步完成多跳关联排序——论文原文："single-step retrieval" 即可匹敌迭代检索（IRCoT 类方法）；
3. 结果：多跳 QA 上最多提升 20%，成本降 10–30 倍、速度提升 6–13 倍（摘要数字）。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配，P2 增强候选）**PPR 是纯图算法**，可用稀疏矩阵幂迭代在 `wiki_links` 邻接表上实现（SQLite 读出边集即可），无 LLM、无 embedding、无图数据库——它是 `graph_expand` 现有 BFS+decay 的更优替代：BFS 对高度数枢纽节点（如 overview.md）的扩散不可控，PPR 自带度归一化与种子相关性衰减。且 HippoRAG 证明"一次图排序 ≈ 迭代多跳"，说明 CodeWiki 不必做复杂的多轮检索循环，**单 pass 图扩展就是上限合理的方案**。
- ⚠️（风险提示）PPR 种子质量依赖"query 词 → 图节点"的对齐，CodeWiki 无 NER，可用现有 BM25 种子文档（search top-k）代替实体种子，即"seed docs 上跑 PPR"，实现门槛低。
- ❌（不适配）OpenIE 抽取需要 LLM（CodeWiki 用 AST + wikilink 已有边，不需要）。

## 六、Zep / Graphiti：时序知识图与边失效（对照 stale_after）

**一手来源**：
- 仓库 https://github.com/getzep/graphiti （`gh api` 获取 README + 源码）
- 论文 arXiv:2501.13956《Zep: A Temporal Knowledge Graph Architecture for Agent Memory》（Rasmussen 等），摘要页 https://arxiv.org/abs/2501.13956 （WebFetch 获取）
- 源码核查（`gh api` 读原文）：`graphiti_core/edges.py:263-277` `EntityEdge` 含三个时间字段；`graphiti_core/utils/maintenance/edge_operations.py:538-570` `resolve_edge_contradictions()`

**核心机制**：
1. **双时态 / 三时间戳模型**（源码实证）：`valid_at`（事实在现实世界开始为真的时间）、`invalid_at`（事实失效时间，null=至今有效）、`expired_at`（该边在知识层被作废的时间）——前两者是"事实有效期窗口"，后者是"知识被更新事件标记作废"的时刻；
2. **边失效而非删除**（edge invalidation）：新事实与旧事实矛盾时，`resolve_edge_contradictions()` 把旧边的 `invalid_at` 设为新边的 `valid_at` 并打上 `expired_at`，**旧边保留可查**（"old facts are invalidated — not deleted"，README 原文）；
3. **Episodes 溯源**：每个实体/边可追溯到产生它的原始 episode（raw data）；
4. **Prescribed & learned ontology**：实体/边类型可用 Pydantic 预先声明（prescribed），也可让结构从数据中涌现（learned），"Start simple, evolve as patterns appear"；
5. 混合检索：semantic + keyword(BM25) + 图遍历，检索不依赖 LLM 摘要。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配，P1 核心修正）**CodeWiki 的 `stale_after` 只覆盖了 Graphiti 模型的一角**：它是"复核提醒时间"（≈ 创建时间 + TTL），既不是事实有效期（valid window），本身也不含"被谁取代"的信息。核查发现 CodeWiki 读取侧其实已有基础——`lint_wiki` 的 `superseded_pages` 检查已能解析 `status: superseded` + `superseded_by`，`stale_notes` 甚至已实现"超龄+无检索命中"双条件判定——**但写入侧从不产生这些字段**。借鉴方案（零图数据库）：给 note frontmatter 补齐 `superseded_by: <note_slug>` 与 `valid_until`，由 `distill_conversation` 在检测到"推翻型"新知识时自动回填到旧 note，使已有的 lint 检查真正有数据可查。这就是 edge invalidation 的文件系统版。
- ✅（适配）**"prescribed + learned 混合"正是 CodeWiki 应有的本体生长模式**：`ontology.yaml` 的 types/relations 由 `init_wiki` 从代码预置（prescribed），由 `distill_conversation` 从对话持续生长（learned），两条腿走路——Graphiti 的官方经验支持这种"先简单后演进"路径，降低了一次性建模完美的压力。
- ✅（适配）**episodes 溯源**：CodeWiki 蒸馏链路已有 raw/ → note 的对应，建议把 raw 文件名写入 note frontmatter `source_ref`（字段已存在于 `ingest_note` 参数表，见 AGENTS.md，但蒸馏默认流程未强制填写）。
- ❌（不适配）Graphiti 本体需要 Neo4j/FalkorDB 后端 + 查询期 embedding，违反 C1/C2。

## 七、Think-on-Graph：KG 上的 beam search 推理（含编号勘误）

**一手来源**：
- 论文 arXiv:2307.07697《Think-on-Graph: Deep and Responsible Reasoning of Large Language Model on Knowledge Graph》（Sun 等，**ICLR 2024**），摘要页 https://arxiv.org/abs/2307.07697 （WebFetch 获取）
- 系列后续（arXiv API 检索确认）：ToG 2.0 arXiv:2407.10805、Fast Think-on-Graph arXiv:2501.14300、Think-on-Graph 3.0 arXiv:2509.21710

### 7.1 ⚠️ 编号勘误
任务与部分流传资料给出的编号 **arXiv:2307.14002 是错误的**——经 arXiv 摘要页实测，2307.14002 是数学论文《Level numbers preserving transformations on excursions…》（Huillet & Martinez），与知识图谱无关。正确编号为 **arXiv:2307.07697**（经摘要页标题/作者核实）。引用 Think-on-Graph 的历史文档应一并更正。

**核心机制**：
1. "LLM as agent"：LLM 在 KG 上交互式探索实体与关系，**逐跳迭代执行 beam search**，保留得分最高的候选推理路径；
2. 回答绑定图上的推理路径，支持"knowledge traceability and knowledge correctability"（可溯源、可纠错）；
3. 无需训练，小模型也能受益；在 9 个数据集中 6 个取得 SOTA（摘要表述）。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配）**CodeWiki 的 hop+decay 本质是"无 LLM 的确定性 beam search"**：`graph_expand` 每跳按分数×decay 剪枝、保留 top-`max_expand`，结构与 ToG 的 beam 一致，只是把"LLM 评估下一跳"替换为"BM25 分数衰减"——这在 C1 约束下是唯一合法替换，且方向被 ToG 验证。可借鉴的增量是**输出侧**：ToG 把推理路径作为答案的一部分返回；`graph_expand` 已经记录了 `via`（经由哪个文档跳达），`query_wiki` 应在返回结果中把 `via` 链显式呈现给 Agent（当前仅存于内部结构），让 Agent 能看到"为什么这个结果相关"。
- ❌（不适配）逐跳 LLM 评估（违反 C1）；其前提是外部结构化 KG（CodeWiki 用文档链接图即可）。

## 八、Anthropic Contextual Retrieval：对纯 BM25 的最直接改进

**一手来源**：Anthropic 官方博客《Introducing Contextual Retrieval》，https://www.anthropic.com/news/contextual-retrieval （WebFetch 获取）

**核心机制**：
1. 索引前用 LLM 为每个 chunk 生成 50–100 token 的"所处上下文说明"（输入=整篇文档+目标 chunk），**拼在 chunk 前面再入库**；由此产生 Contextual Embeddings 与 Contextual BM25 两个索引；
2. 配合 reranker（先取 150 候选再精排到 20）；
3. 官方数字：Contextual Embeddings 使 top-20 检索失败率降 35%（5.7%→3.7%）；**Contextual Embeddings + Contextual BM25 降 49%**（5.7%→2.9%）；再加 reranking 降 67%（5.7%→1.9%）。借助 prompt caching，索引期成本约 $1.02/百万 token（一次性）。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配，**本轮调研中 ROI 最高的单项**）关键洞察：上下文增强发生在**索引期**（生成时），查询期仍是纯 BM25——完全符合 C1。CodeWiki 的 `_build_indexable_text()`（`cache.py:211`）已经把 frontmatter 的 tags/description/aliases 等字段加权拼入索引文本（tags 3x、title 2x 等），**机制完全现成**。落地方式：`write_doc_file` / `ingest_note` 落盘时（此时 LLM 已在场），为每页生成一个 `context:` frontmatter 字段，一句话说明"本页面属于哪个模块/解决什么问题/被谁依赖"，`_build_indexable_text` 对其 2–3x 加权。这解决 BM25 的经典死穴：chunk 内的代词与术语脱离上下文后检索不到（官方案例：chunk 提到"the company"但没写公司名）。
- ✅（适配）对蒸馏 note 尤其有效：note 正文常以"这个问题…"开头，补上 context（"本 note 涉及 X 模块的 Y 问题"）后 BM25 召回直接受益。
- ⚠️（注意）embedding/reranker 部分不适用（C1），只取 Contextual BM25 这一半；官方 49% 的组合数字含 embedding 贡献，纯 BM25 侧的增益幅度未单独披露——引用时应注明。

**官方定义核实结果**（对照前文《本体知识库文章》的二手拆解）：

| 原语 | 官方定义（原文摘译） | 与二手文章差异 |
|------|---------------------|----------------|
| Object types | "the schema definition of a real-world entity or event"（现实实体/事件的 schema 定义） | 一致 |
| Link types | objects 之间的关系建模元素，与 object/property 同属语义层 | 一致 |
| Action types | "the definition of a set of changes or edits to objects, property values, and links"；组成=**parameters / rules / submission criteria / side effects**（通知、webhook），所有编辑作为**单一事务**提交 | 二手文章"参数/规则/提交条件/副作用/权限"基本准确，官方文档另有独立 permissions 章节 |
| Functions | "author and evolve business logic with arbitrary complexity"（注册到本体的业务逻辑） | 一致 |
| Interfaces | "describes the shape of an object type and its capabilities"；组成=**interface properties、link type constraints、action type constraints、metadata**；Object Set Service 可"按 interface 搜索排序对象"（多态查询） | 二手文章只提"公共形状"，**官方补充了约束（link/action type constraints）与按接口检索的能力**——后者对 CodeWiki 有直接价值（见下） |

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配）**Interfaces 的"按形状查询"可降级为"按 frontmatter 字段组合查询"**：CodeWiki 若定义 `Diagnosable` 接口 = 拥有 `failure_mode` + `recovery` 字段的页面，`lint_wiki` 就能检查"所有 known_issue note 是否实现了 Diagnosable 形状"，`query_wiki` 可加 `has_fields` 过滤。无需类型系统，纯字段检查。
- ✅（适配）**Action Types 四元组（parameters/rules/submission criteria/side effects）是 P3 的直接模板**：阿里文章建议的 `policies` 节可照此结构化——每条 policy = 受保护对象（scope）+ 规则（rules）+ 提交条件（何时触发检查）+ 副作用（违反时的动作：lint 报错级别）。
- ❌（不适配）Ontology Manager 的可视化建模、平台级治理——CodeWiki 走"ontology.yaml 单一事实源"即可。

## 十、MADR：决策记录的标准格式与生命周期

**一手来源**：
- 仓库 https://github.com/adr/madr （`gh api` 获取 README + `template/adr-template.md` 原文；官网 https://adr.github.io/madr/ 直连抓取失败，内容以仓库源文件为准）
- 学术出处：Kopp, Armbruster, Zimmermann,《Markdown Architectural Decision Records: Format and Tool Support》, ZEUS 2018（README 提供的 BibTeX）

**核心机制**：
1. YAML frontmatter：`status`（**proposed | rejected | accepted | deprecated | superseded by ADR-0123**）、`date`、`decision-makers`、`consulted`、`informed`；
2. 正文固定章节：Context and Problem Statement → Decision Drivers → Considered Options → Decision Outcome（"Chosen option: X, because …"）→ Consequences（Good/Bad）→ Confirmation（如何验证决策仍被遵守）→ Pros and Cons of the Options；
3. 文件按 `nnnn-title.md` 编号存放于 `docs/decisions/`。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配，P1 关键补强）**`superseded by ADR-xxxx` 是"无图数据库的决策链"**：一个 frontmatter 字符串字段就表达了"该决策被哪条新决策取代"，配合 §六 Graphiti 的"失效不删除"原则，CodeWiki 的 decision note 即获得生命周期闭环（proposed→accepted→deprecated/superseded）。Semantica 分析文档中建议的 `decision_chain` 可简化为 MADR 风格的 `status` + `superseded_by` 两字段，更轻、更标准。
- ✅（适配）**Confirmation 章节 ↔ CodeWiki lint**：MADR 问"如何确认决策仍被遵守"，这正是 `lint_wiki` 的角色——decision note 可写"确认方式：lint 检查 X"，形成决策→检查的可验证回路（呼应阿里文章的验证策略）。
- ✅（适配）**Decision Drivers / Considered Options 模板**可直接并入 `_DISTILL_SYSTEM`（`distill_conversation.py:55`）的 decision 抽取指令，使蒸馏出的 decision note 结构统一，BM25 可按章节标题命中。
- ⚠️ **ADR×知识图谱**：arXiv 检索（2026-08-10）找到多篇 ADR 自动化论文（见 §十三），但**未发现"ADR 直接入图"的成熟一手方案**，该方向业界仍在探索（未核实到权威实践）。

3. **SPDX**：工业级 SBOM 标准，许可证标识符表是其最广为人知的部分；
4. **SWO**：模块化结构（Software / Data / Data Format / Algorithm / License / Organization / Programming language 等分支），通过社区工作坊迭代 + 测试问题驱动构建，**经验是"用具体问题检验本体够不够用"**。

- ⚠️（部分适配）JSON-LD/RDF/OWL 序列化体系对 CodeWiki 过重（C3），只取词表不取格式。

## 十二、mem0：Agent 记忆的抽取/更新管线

**一手来源**：
- 仓库 https://github.com/mem0ai/mem0 （`gh api` 获取 README，含 2026-04 新算法说明）
- 论文 arXiv:2504.19413《Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory》，摘要页 https://arxiv.org/abs/2504.19413 ，管线细节取自 HTML 全文 https://arxiv.org/html/2504.19413v1 （WebFetch 获取）

**核心机制**：
1. **两阶段管线**（论文原文确认）：抽取阶段从最新消息对提取候选记忆；**更新阶段让 LLM 对每条候选在相似历史记忆上选择 ADD / UPDATE / DELETE / NOOP** 四种操作之一；
2. **Mem0^g 图变体**：抽实体与关系三元组存为带类型的节点/边，与已有图数据做冲突消解，检索走图探索或三元组匹配；
3. **2026-04 新算法**（README）：改为**单次 ADD-only 抽取**（不再 UPDATE/DELETE，记忆只增不改），agent 生成的事实与用户事实同权，实体抽取后跨记忆链接，检索为多信号融合（semantic + BM25 + 实体匹配并行打分）+ 时间感知排序；
4. 论文数字：较 OpenAI memory 相对提升 26%，p95 延迟降 91%，token 成本省 90%+。

**对 CodeWiki-CN 的借鉴点**：
- ✅（适配）**ADD/UPDATE/DELETE/NOOP 四分语义正是 `distill_conversation` 缺失的**：现状只有"新建 or 近似去重抑制"（`_DEDUP_THRESHOLD`）。借鉴后蒸馏产出对已有 note 的操作类型：内容被修正→UPDATE（在旧 note 上增补并刷新 `stale_after`）、被推翻→标记 superseded（§六）、重复→NOOP、新知识→ADD。这把去重从"相似度阈值"升级为"有语义的操作决策"，且发生在蒸馏期（LLM 已在场），不违反 C1。
- ✅（适配）**"ADD-only + 时间标记"与 §六 Graphiti 的"失效不删除"互为印证**：两个独立团队先后收敛到同一结论——**Agent 记忆/知识宁可只增不删，靠时间字段区分新旧**。对照 CodeWiki：raw/ 无自动过期；note 侧读取侧失效检查已就位但写入侧从不产生失效标记（§二基线）——应按此原则补齐写入语义。
- ❌（不适配）其检索依赖 embedding 与 LLM 操作判定（CodeWiki 的判定在蒸馏期做即可，检索期保持纯 BM25）。

### P0 — 激活 ontology.yaml：让 terms/types/relations 有消费方（原 P0 修正版）

**现状问题**：`types`/`relations` 零消费（§二代码基线）；`terms` 有消费方但词表为空。

1. **（新增，本轮最高 ROI）索引期上下文注入**——借 Contextual Retrieval（§八）：
   - 改 `codewiki/mcp/tools/doc_writer.py`（write_doc_file）与 `distill_conversation.py` 落盘逻辑：frontmatter 增加 `context:` 字段，由生成期 LLM 产出一句话定位（模块归属 + 职责 + 上游）；
   - 改 `codewiki/mcp/cache.py:211` `_build_indexable_text()`：`context` 字段 2–3x 加权（复用现有 boost 管线，改动约 5 行）。
2. **词表落地**：`init_wiki` 时从 wiki 页面的 aliases/tags 自动回填 `ontology.yaml` 的 `terms`（词表来源对齐 CodeMeta 的 crosswalk 思路，§十一）；`query_wiki` 的 expand 已能立即受益。
3. **types/relations 首批数据**：`init_wiki` 从模块树生成 module/concept 类型与 `depends_on` 关系（**draft 状态，走 confirm 通道**，§13.2 教训）；建模前先列 10 个 Agent 高频问题做验收（SWO 方法，§十一）。
4. **relations 的第一个消费方**：`cache.py` 建索引时把 `ontology.yaml` relations 写入 `wiki_links` 表（带边类型列），`graph_expand` 无需改动即获得"本体边可 hop"——这是最小改动的打通方式。

### P1 — 知识生长：占位节点 + 失效标记（原 P1 扩展版）

1. **占位节点**：蒸馏引用未定义概念时写 `todo: true` relation（ontology.yaml 格式已支持），`lint_wiki` 报"待补全占位"（并入 `wiki_lint.py` 检查清单）。
2. **失效不删除——补上写入侧**（Graphiti §六 + MADR §十 + mem0 §十二 三方共识）：
   - note frontmatter 字段扩展：`superseded_by`、`valid_until`（`status` 已支持 draft/stable/deprecated，见 `_LEGACY_STATUS_MAP`）；
   - 改 `distill_conversation.py` 的 submit 分支：对已有相似 note 输出显式操作（UPDATE 内容/SUPERSEDE 旧 note/NOOP），替换纯阈值抑制；SUPERSEDE 时**回填旧 note 的 `superseded_by` 与 `status: deprecated`**，让已存在的 `lint_wiki` `superseded_pages`/`note_clusters` 检查（§二基线）有数据可查；
   - `stale_notes` 的"超龄+无检索命中"双条件机制保留并复用（该机制甚至超出 Graphiti 的思路——它用检索行为而非纯时间判定知识活性）。
3. **删除联动**：note 删除/作废时清理其贡献的 relation 边（LightRAG §四的局部重建思想，文件系统版）。
4. **溯源补强**：蒸馏落盘强制写 `source_ref`（raw/ 文件名），对齐 Graphiti episodes 模型。

### P2 — 视图渲染：模块级聚合视图 + 图排序升级（原 P2 具体化）

1. **模块级视图**：不做 Leiden（§三），直接按模块树渲染——新增脚本/工具（如 `codewiki/mcp/tools/wiki_views.py`）从"模块文档 + relations 下游边"生成父模块聚合页（影响面视图：某接口 → 所有 `depends_on` 下游），渲染进 `wiki/views/`，由 `lint_wiki` 校验视图与 relations 的一致性。
2. **PPR 增强 hop**（可选，§五）：`cache.py` `graph_expand` 增加 `method="ppr"` 选项，种子=BM25 top-k，在 `wiki_links` 邻接上跑幂迭代；与现有 BFS+decay 并存 A/B。
3. **双层查询语义**（LightRAG §四）：`query_wiki` 文档化两种用法（具体对象→type_filter=entity/module；主题→type_filter=concept/notes），无需新代码，只补 MCP 工具描述。
4. **via 路径显式化**（ToG §七）：`query_wiki` 结果里 hop>0 的条目附带 `via` 跳转链。

### P3 — Action/Interface 闭环（原 P3 按官方定义细化）

1. **policies 采用 Action 四元组结构**（Palantir 官方定义 §九）：`schema.yaml` 新增 `policies:`，每条 = scope + rules + trigger（提交条件：哪些变更触发检查）+ effect（违反时的 lint 级别），替代阿里文章中较随意的 YAML 草案。
2. **Interfaces 降级为字段形状**（§九）：在 `ontology.yaml` types 节支持 `interfaces:`（字段组合声明），`lint_wiki` 检查页面 frontmatter 是否满足所声明接口的必填字段。
3. **团队记忆飞轮回写 relations**（原 P3 保留）：`confirm_note` 时若 note 带结构化 relation 字段，自动合并进 `ontology.yaml`（仍走 grounding 匹配，§13.1）。

**与原路线的主要差异**：P0 前置了"索引期 context 注入"（原路线未涉及，来自 Contextual Retrieval）；P1 从"过期提示"升级为"过期+失效双机制"（来自 Graphiti/MADR/mem0）；P2 明确"不做 Leiden、用模块树"（修正 GraphRAG 类比）；P3 的 policies/接口按 Palantir 官方定义重新结构化。
