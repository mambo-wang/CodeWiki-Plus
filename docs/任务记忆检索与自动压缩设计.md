# 任务记忆检索与自动压缩设计

> 日期：2026-09-12 · 状态：定稿待实施 · 归属任务：统一知识存储层（KnowledgeStore 动词式门面）
> 决策方式：wayfinder + grilling 两轮（Q1-Q10 全按推荐定案）；实施排期：Phase5 批次二之后（同动 task_manager.py/store.py，避免三线并行撞车）。

## 一、问题定义（现状事实，2026-09-12 实读）

**瓶颈是检索缺失，不是上下文预算。** 单任务读取已有三层防护（尾部截断 `max_memories=20`、warm 层 2048 字符预算降级、压缩阈值 40 条/24KB），13 个任务、最大记忆文件 17KB（`他山之石/memories/iamwangbao-163-com.md`）远未失控。

真实缺口（`codewiki/mcp/tools/task_manager.py`）：

1. **任务内回忆不可检索**：`get_task_context` 只能按 task_id 整取尾部 N 条（`:668-794`）——被截断或已压进摘要的旧条目，按关键词找不回（他山之石任务实测：44 条压缩 26 条，摘要覆盖不到细节）。
2. **跨任务发现靠标题**：`list_tasks`（`:449-472`）只返回 id/标题/status，13 个任务只能人读标题猜归属。
3. **压缩需显式触发**：`compact_task_memories` 须 Agent 主动调用，`compaction_due=true` 提示可能被忽略。
4. **tasks/ 完全不在检索语料**：BM25 索引只扫 wiki/、notes/、skills/SKILL.md、raw/sources/（`wiki_search.py:375-453`），`.index.json` 仅 id→标题映射（2.3KB）。

## 二、决策（Q1-Q10）

### D1 目的地与场景（Q1/Q2）

产出本设计文档；驱动场景为**任务内回忆**（主）与跨任务发现（次）。不扩展 query_wiki 语料——任务记忆与 Wiki 笔记分轨（CONTEXT.md 既有边界），活性数据混入知识语料会污染 usage heat。

### D2 新工具 `search_task_memories`（Q3）

条目级检索，独立于 query_wiki 语料：

```
search_task_memories(
    task_id,                    # 必填：单任务内召回
    query,                      # 关键词
    include_archive=true,       # 压缩归档条目也进召回（标注 archived: true）
    include_others=false,       # 他人 memories 文件默认不搜（对齐 get_task_context 分层隐私姿态）
    max_results=10
)
```

- 颗粒度：**条目级**（`### YYYY-MM-DD HH:MM` 一个 entry 一条索引记录），非文件级。
- 返回：date + 摘录（命中片段）+ est_tokens + archived 标注（命中 archive 条目时提示「此条已被压缩，原文见 memories-archive」）。
- 跨任务发现走轻路径：先 `list_tasks` 按标题选，再进单任务搜；**不做全局任务记忆搜索**（13 任务规模下标题过滤够用，全局搜索留作规模触发的后续决策）。

### D3 索引：复用 AnalysisCache（Q8）

- 条目 key = `tasks/<task_id>/memories/<user>.md::<n>`（文件内序号），坐现有 SQLite upsert 通道（`wiki_search.py:356-358`），两 adapter 已收口在 SearchIndex Protocol。
- 索引文件 gitignore（可重建，对齐 `.index.json` self-heal 惯例）。

### D4 新鲜度：惰性重建（Q4）

search 时校验目标文件 mtime/条目数，不一致重建**该任务**的条目索引（对齐 `_ensure_index` freshness gate 模式：build-if-missing + 校验 + 60s 节流）。

- 否决写路径同步更新：须在 add/compact/distill 直写三个写路径挂钩子，漏一处即静默漂移（本仓「静默降级」前科：白名单漏判、schema 契约不同步、候选截断）。
- 否决每次全量重建：压缩会改写文件（多条变一条摘要），全量重建成本随任务数线性涨；惰性按需只重建脏任务。
- 单写者环境下 mtime 校验够准；若将来出现跨进程并发写，升级为 sidecar 锁内校验（复用 `store.locked`）。

### D5 压缩失效语义（Q6）

压缩后旧条目从 hot 层索引移除，archive 条目照常可搜（append-only 冷层，条目数有限）。**压缩与检索正交**：压缩省的是每次会话的固定注入成本，检索是用户主动付费的可选成本（est_tokens 可见）——archive 进检索范围不等于「白压」。

### D6 自动压缩：get_task_context 顺带驱动（Q7）

`compaction_due=true` 时，`get_task_context` 返回值**直接携带** prepare 好的待压缩条目 + 摘要指令（`compaction_work` 字段），本会话 Agent 顺手写摘要并 `compact_task_memories(mode="submit", ...)`。压缩全程**无需用户确认**（用户定案 2026-09-12；ADR-0002 直写语义的自然延伸——压缩本就可逆，原文全在 archive）。

- Agent 即 LLM（Mode C 精神），零新基建、零后台进程。
- 返回值携带待办 = Agent 不可能忽略（对齐 capture/distill 的 prepare→submit 既有形态）。
- 否决 Mode B 后台压缩：依赖 MAIN_MODEL 环境变量常驻，LLM 成本不可见（违反成本可见性优先原则）。
- 否决机械压缩（首行降级）：丢结论性信息，摘要意义归零。

### D7 隐私边界（Q5）

搜索默认只搜本人（含本人 archive）；他人文件须显式 `include_others=true`——与 get_task_context 的分层姿态（他人默认降级一行 hint）严格对齐，**搜索侧不得比读取侧更宽**。产品面向多用户（PyPI 分发），单人使用下该参数无感但语义先行。

## 三、验收链

1. 单任务条目搜索：旧条目（超 max_memories 窗口）按关键词可召回，带 date/est_tokens。
2. archive 召回：压缩后旧条目仍可搜到，标注 archived，原文可从 memories-archive 取回。
3. 惰性刷新：追加新条目后立即搜索能命中（mtime 校验触发重建）；压缩后旧条目不再以 hot 形态出现。
4. 自动压缩：compaction_due 的任务在 get_task_context 返回 compaction_work → Agent submit → hot 层归位、archive 增补，全程无用户交互。
5. 隐私：默认搜索不返回他人条目。
6. 索引可重建：删除索引文件后首次搜索自动重建，结果一致。
