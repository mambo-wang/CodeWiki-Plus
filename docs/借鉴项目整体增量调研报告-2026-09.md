## 1. 结论（先看这三条）

### 1.1 本轮最大的价值仍然在证伪：一半以上的候选，本仓早就有等价物

最典型的一条：OpenViking 的「auto-recall 超预算整体丢弃」被列为候选时，本仓
`codewiki/mcp/tools/injection_budget.py:1` 的模块 docstring 第一行就写着
**「injection_budget — 注入预算降级（V2, OpenViking auto-recall 借鉴）」**——
我们已经吸收过并落地了（配合 `note_query.py:1154-1164` 的 `apply_snippet_budget` 降级）。
同类「他仓新东西 = 本仓既有能力」还有：

| 他仓候选 | 本仓等价物 |
|---|---|
| semantica 撤回 + 墓碑（`context_graph.py:1662/:1821/:1895`） | `note_lifecycle.py:116` 的 `deprecated` + reason，文件不删、状态可查 |

| CBM index-time importance（`pass_importance.c:12`） | `note_query.py:94` 相关度 + heat + adopted_count + `:575-595` 特异性 + `:1043-1057` superseded 降权，多信号确定性排序 |
| RepoWiki 逐页 fingerprint 未变跳过（`markdown.py:45-47`） | `page_manifest.detect_stale_pages:351` + `watch._incremental_refresh:118-156` |
| WeKnora 页面修订历史 + revert（`80a5003c`） | 本仓 repowiki 随代码版本化，**git 本身就是修订历史** |
| WeKnora 停用 chat model 重排（`e7582cf5`） | 本仓检索排序全程确定性，从不用 LLM 重排 |

这条坐实了已有的 stable 笔记「借鉴调研先证伪：在他仓看到的『新能力』，本仓往往已有等价实现」——
本轮又多了 6 个样本。

### 1.2 他仓集体在往「服务端/队列/多租户」走，本仓是主动不同的取向

OpenViking 的队列 claim 与自愈（#4779）、claude-mem 的计费归因（#3898）、semantica 的跨存储擦除协调、
CBM 的 workspace manifest 审批——都预设了**常驻进程 + 服务端 + 多写者**。
本仓是本地 markdown + git 版本化 + 同步 MCP 工具，没有常驻写入端，因此：

- 队列 latch 只在 session init 复位导致「一次失败永久卡死」（`pending-queue.mjs:282/:378`）——本仓无此面；
- 「机器数据搬出业务仓」——本仓模型相反（已有 architecture 笔记）；
- 「缺失任务记录视为已删除」（`task_tracker.py` 系）——本仓对未知 task_id 是**显式报错**
  （`task_manager.py:619-622`），对 stale 索引条目是**就地跳过**（`task_session_start.py:146`），
  两条都是 Doctrine「不静默失败」的直接体现，属于**主动不同**，不是缺口。

### 1.3 真正值得盯的一条行业主线：把「成本/预算」从软约束改成硬约束

五个项目互不约而同地在做同一件事：

| 项目 | 把什么从软变硬 |
|---|---|
| CBM | 分页只在 `end < allowed_count` 时才发 `nextCursor`（`mcp.c:988`），预算内不丢信息 |
| WeKnora | 直接删掉「用聊天模型再跑一次重排」（`e7582cf5`），把成本/不确定性转回检索侧 |
| llm_wiki | Smart 模式连续 2 次检索无证据增量即强制收尾（`runtime.rs:1808-1823`） |
| OpenViking | 超预算整体丢弃系统注入（`context-lifecycle-service.ts:464-468`） |
| RepoWiki | 扫描预算按语言优先级分配 + 硬上限（`scanner.py:101-102/:267-269`） |

本仓 `injection_budget` 已在这条线上（注入侧）。**空档在两头**：
① **扫描/解析侧**没有优先级预算（RepoWiki 那条注释「docs 重的仓里朴素 walk 会先用 markdown 填满预算」值得警惕）；
② **deprecated 笔记是否会被后续 ingest 复活**（semantica 墓碑专门防这个），本仓未查。

## 4. 本轮附带的两个方法论产出

### 4.1 测量通道覆盖面先于样本量

本轮发现 `[tool-error: …]` 只由 `tool_digest` 产生，而它只有两个调用点
（`codewiki/mcp/_ide_hook.py:268`、`capture_conversation.py:221`），
session-end 的 transcript 补采集**不经过它**。
所以上一轮「8 条 raw 中仅 1 条含 tool-error、漏检率 0%」测的是**通道覆盖面**而不是漏检率——
换更大样本只是放大同一个偏差。正确的次序是：先确认「信号在几条通道上被采集、各覆盖多少会话」，再谈样本量。

### 4.2 增量调研 SOP 已成型（本轮第三次完整跑通）

统一克隆 → `git fetch` → `since <基线>` 取增量并**按模块前缀聚类** → 只读与本仓同层的模块
（CI/依赖/UI/i18n/宿主接入广度整片跳过，并写明跳过理由）→ 候选落到「文件:行号」→
逐项在本仓 grep 证伪 → 三分类处置表（excluded 必填原因）→ 存 `docs/`。
本轮新增两点：**提交数口径要写明是否含 merge**（否则 1182 vs 727 会被当成矛盾）；
**三路并行采集 + 主 Agent 统一裁决**（子代理只做事实采集，不做本仓对照——
他仓行号必须来自实测 diff，本仓行号必须由裁决者亲自核）。
