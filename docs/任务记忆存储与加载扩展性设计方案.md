# 任务记忆存储与加载扩展性设计方案

> 状态：P0 已实施（2026-08-24）；P1 已实施（2026-08-24，LLM 调用形态选定为 Mode C 两段式，见 §5.2）
> 关联：《团队记忆融合-L2场景聚合与L3-Doctrine设计方案》（互引：本方案的压缩段是"任务级巩固"，L2/L3 是"团队级巩固"，两者分层独立、格式同构）
> 决策记录：ADR-0001（任务记忆保持 markdown，不迁移 JSONL）

## 1. 背景与问题

任务记忆存储于 `repowiki/tasks/<task_id>/` 下三个文件：

> **后续演进（2026-08-25）**：多人协作场景下 memories.md 已按用户分片为 `memories/<user_id>.md`（每人只写自己的文件，git 冲突隔离；本文件转为只读兼容的热层，首次压缩后并入当前用户文件）；加载改为 hot/warm 分层，压缩改为文件域。见《任务记忆多人协作分片设计方案》。

- `memories.md` — 已确认任务记忆的累积（append-only；现为存量兼容文件）
- `pending-memories.json` — 蒸馏产出待确认暂存区（confirm/reject 闸门）
- `../.index.json` — 任务索引

现状问题有两个：

1. **格式之问**（已定案，见 ADR-0001）：memories.md 是否应迁移 JSONL？结论是否——它的消费者是 LLM（原文直接进上下文）和人（直接阅读），markdown 是消费链路原生格式；追加频率低（人工确认后才落盘），读改写开销无关紧要。TencentDB-Agent-Memory 用 JSONL 是因为旁边有 SQLite 索引层兜底，CodeWiki 任务记忆没有也不需要这个量级。
2. **无界加载**（本方案主问题）：`get_task_context` 与 `get_task` 均全量读入 memories.md 原文返回。文件只增不减，条目上百后会话启动即吃掉大块上下文。

跨项目调研（TAM / OpenViking / teamai-cli）的共识印证了修法方向：**存储格式不重要，加载策略才重要**。TAM 的"L2 上限 15 块 + L3 ≤1200 字有界注入"、OpenViking 的"写时 L0/L1/L2 分层摘要"、teamai 的"subagent 主动检索 + token 预算"是同一件事的三种实现——没有任何一家在会话开始时全量加载记忆。业界术语为**记忆巩固（consolidation）**：短期→长期的转化必须是有损压缩 + 可回溯原文（MemGPT 换页保留外存原文、ChatGPT 离线"做梦"保留聊天记录）。

## 2. 现状事实（已核实）

- 写入方两个：`add_task_memory`、`confirm_task_memories`，均走 `_append_memory_atomic`（读全文 → 重写，temp + os.replace 原子替换）。
- 读取方两个：`get_task`、`get_task_context`，均 `read_text` 全量返回。
- 条目现状：裸段落、空行分隔、无时间戳头（存量 16 条）。
- 既有模式可复用：`pending_raws` 已实现"截断到 10 条 + `pending_raws_truncated` 标志 + 分页参数"。

## 3. 设计决策（全部经 grill 拍板）

| # | 决策 | 选项 |
|---|------|------|
| Q1 | 只做任务记忆自身扩展性，不绑 L2/L3 实施；压缩段输出格式与未来场景块同构 | A |
| Q2 | 三文件维持现有格式 | 定案 → ADR-0001 |
| Q3 | 条目写入时加时间戳头；存量运行时回退解析；首次压缩时惰性重写 | 是 |
| Q4 | 加载走"摘要 + 截断兜底"路线 | B |
| Q5 | 落设计文档进 docs/，拆 P0/P1 两阶段 | — |
| Q6 | 双阈值触发（条数 40 / 字节 24KB），目标头部摘要 ≤2KB + 最近 20 条全文；信号暴露不自动执行 | — |
| Q7 | 新增显式 MCP 工具 `compact_task_memories` 执行 | B |
| Q8 | 压缩产出直写，不走 confirm 闸门 | — |
| Q9 | 被压缩条目原文归档到 `memories-archive.md`，不删 | — |
| Q10 | `get_task` 与 `get_task_context` 共用同一截断函数，默认 5 条 | — |

### 3.1 决策理由摘录

**Q7-B（显式工具而非内联/委托）**："hook/轻路径只做确定性采集，LLM 重活留给显式调用"是本项目从 teamai 借鉴并已写进多份文档的铁律。get_task_context 内联自动触发直接违反它；委托 distill-worker 会让该 subagent 职责从"蒸馏 raw"膨胀为两种异质任务，且补蒸馏是会话启动高频路径，压缩不该绑上去。

**Q8（直写不走闸门）**：confirm 哲学防的是"噪声知识进库"（不可信内容永久留存）；压缩是**可逆操作**——原文全在归档（Q9），摘要写坏重跑一次工具即可，零信任损失。给压缩加人工闸门会把低价值进度性内容抬到与正式知识同等的评审成本，与"任务记忆 vs Wiki 笔记分轨"的定位矛盾。摘要质量验收下沉到 lint_wiki 格式检查层。

**Q9（归档不删）**：任务记忆虽是进度知识，但均经用户逐条 confirm 落盘，删除违背"不删已确认内容"原则；归档让"摘要漏了关键细节"永远有补救路径。归档文件不进任何自动加载路径，无上下文成本。

## 4. 格式规范

### 4.1 条目结构化（P0）

新条目写入时（`_append_memory_atomic`）：

```markdown
### 2026-08-24 14:32

<条目正文，一段或多段>
```

解析规则（读取侧统一函数 `_split_memories(text)`）：

- 文本含 `### ` 行 → 按三级标题切条，标题内时间戳为该条时间；
- 不含（存量旧文件）→ 回退按空行分段，条目时间为 null；
- 不写迁移脚本；首次压缩触发时把整个文件惰性重写为带标题格式。

### 4.2 压缩后文件形态（P1）

```markdown
## 早期记忆（摘要）

<LLM 生成的有损摘要，≤2KB>

> 原文归档于 memories-archive.md，截至 2026-08-24，共 N 条。

### 2026-08-20 09:11

<最近 20 条全文……>
```

- 摘要段固定以 `## 早期记忆（摘要）` 二级标题开头（解析与渲染锚点）。
- `memories-archive.md`：append-only，条目同样带 `###` 时间戳头，追加被压缩条目原文（按原时间顺序）。
- 压缩目标态：总条数 ≤ 40、总字节 ≤ 24KB（以触发阈值为目标态上界）。

### 4.3 压缩段与 L2 同构预留

摘要段的结构（背景→关键事实→当前状态→未决事项）刻意与 L2 场景块的组织方式对齐；未来 L2 实施时，任务收尾（complete_task）可将摘要段直接作为场景块候选输入，无需二次解析。本方案不实现该衔接。

## 5. 工具与接口变更

### 5.1 P0（纯确定性代码，无 LLM）

1. `_split_memories(text) -> List[MemoryEntry]`：统一切条函数（含回退逻辑）。
2. `get_task_context` 增加 `max_memories` 参数（默认 20）：返回最近 N 条全文 + 新字段 `memories_total`、`memories_truncated`；超阈值时另附 `compaction_due: true`（P1 上线前的过渡信号，字段先行）。
3. `get_task` 同参数（默认 5），走同一内部函数。
4. 写入侧：`add_task_memory` / `confirm_task_memories` 落盘时自动加时间戳头。
5. registry.py 注册新参数（注意历史坑：inputSchema 枚举与 handler 常量同步）。

### 5.2 P1（LLM 调用，显式工具）

1. 新 MCP 工具 `compact_task_memories(task_id, mode, summary)`（LLM 调用形态已定案：**Mode C 两段式**，与 distill_conversation 的 prepare/submit 同构，工具自身无状态不持有 LLM）：
   - 前置校验：未达双阈值（40 条 / 24KB）**或**条数未超出保留窗口（≤20 条）时直接返回 `compaction_needed: false`（单条超长但总量在窗口内时压缩无意义，同样 no-op）；
   - `mode="prepare"`：返回 `entries_to_compress`（全部条目减最近 20 条）+ `existing_summary`（上轮压缩的旧摘要，调用方应将其折叠进新摘要）+ 摘要指令（≤2KB、覆盖关键事实/已定决策/未决事项/仍影响后续的上下文）；
   - `mode="submit"`：校验 summary 非空且 ≤2048 字 → 原子重写 memories.md（`## 早期记忆（摘要）` 段 + 归档指引行 + 近 20 条全文，存量无头条目在此惰性迁移为带头格式）；被压缩条目按原时间顺序 append 到 memories-archive.md（存量无头条目加合成标题 `### 历史条目（存量格式，无时间戳）`）；
   - 失败顺序：先归档后重写主文件——两步之间崩溃则原文双存（安全可重试），永不丢失；
   - 幂等：重复调用在未达阈值时为 no-op；submit 与 prepare 之间新增的条目落入保留窗口，语义安全（详见 handler 内 NOTE 注释）。
2. `get_task_context` 的 `compaction_due` 信号在 P1 后生效为真实触发提示。

### 5.3 不做的事

- 不迁移存量文件格式（惰性重写）；不删归档；不给压缩加 confirm 闸门；不把 memories 改成检索按需拉（teamai 路线——任务记忆是会话启动必须恢复的进度上下文，不应依赖 agent 主动检索；teamai 自己无任务记忆对应物，其经验不可平移）；不绑 L2/L3 实施。

## 6. 测试断言点

- 切条：带标题新格式、存量空行分段回退、混合文件（迁移中间态）三态全覆盖。
- 截断：`memories_total` 计数正确；`memories_truncated` 在 total > 返回数时为 true；分页参数（max_memories）边界。
- 时间戳头：写入侧自动加头；同分钟连续写入不覆盖（条目唯一性由内容+顺序保证，不做幂等去重）。
- 压缩（P1）：双阈值边界（39/40 条、23.9/24KB）；摘要段解析；归档文件条数 = 被压缩条数；重跑幂等（第二次调用 no-op）；原子性（重写失败时归档不落、原文件不动）。
- 回归：现有 test_task_manager.py 全量通过（17+ 条）。

## 7. 实施顺序

P0（条目结构化 + 截断 + 信号字段先行）→ 自测 + E2E（在本仓 repowiki/tasks/ 真实数据上跑）→ P1（compact_task_memories + 归档）→ E2E → 按 feat/docs 分笔提交。P0 与 P1 可独立发布。
