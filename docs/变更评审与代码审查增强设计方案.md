# 变更评审与代码审查增强设计方案

> 状态：设计稿（待评审）｜日期：2026-08-25｜关联：Backlog 第 1/2 项（analyze_changes / watch_repo）的延伸

## 1. 背景与目标

`analyze_changes`（变更影响分析）已落地：行级 diff 定位变更函数 → 传递影响半径 → 回归测试建议。但"改了什么、影响了谁"没有回答"**改得对不对**"。本方案扩展 change-review 为**代码审查**：对同一次代码变更（commit 范围或未提交），综合以下四类依据输出结构化评审报告：

1. **SPEC / 设计文档**（用户传入或仓库自动发现）——查业务正确性：缺失、超范围、实现偏离
2. **项目 Wiki 编码规范**（notes / wiki 场景块 / L3 Doctrine）——查项目约定符合性
3. **相关模块笔记**（pitfall / lesson / architecture / decision）——查历史踩坑与模块约定
4. **通用编码规范**（内置 checklist）——查语言无关的工程基线

## 2. 现状盘点（可复用能力）

| 能力 | 位置 | 复用方式 |
|------|------|---------|
| 行级 diff 解析（`parse_unified_diff`） | `change_analysis.py` | 直接复用，评审对象与影响分析同源 |
| 变更组件定位（`locate_changed_components`） | `change_analysis.py` | 复用，取变更函数源码切片 |
| 传递影响（`transitive_impact`） | `topo_sort.py` | 复用，评审时提示受影响调用者 |
| Wiki/notes 检索（`handle_query_wiki`，BM25） | `knowledge_loop.py` | 复用，作为规范/模块笔记依据的检索引擎 |
| Doctrine L3 项目原则 | `repowiki/wiki/doctrine.md` | 复用，`query_wiki(mode="overview")` 注入 |
| 需求来源四优先级（Spec 轴选型决策） | notes `2026-08-24-单次-commit-业务-review-工具选型...` | 借鉴：issue 引用 → 手动路径 → docs/specs/.scratch 匹配 → 问用户 |

## 3. 核心架构决策

### 3.1 工具形态：prepare → Agent 推理 → submit（无状态工具 + LLM 外置）

遵循 Doctrine 约束「工具只做确定性笔记，推理与决策永远在调用方 agent 手里」。工具**不持 LLM**：

```
review_changes(mode="prepare", ...)   → 返回「评审上下文包」（确定性组装）
        │
        ▼
调用方 Agent 持有 LLM，依据上下文包执行评审推理
        │
        ▼
review_changes(mode="submit", ...)    → 校验并落盘评审报告（可选）
```

与 `distill_conversation` 的 Mode C 同构：工具做收集与落盘，推理外置。评审报告由 Agent 直接向用户输出（不阻塞在工具内），用户确认后才经 `ingest_note` 沉淀为知识。

### 3.2 单一新工具 `review_changes`，不修改 `analyze_changes`

变更定位与评审依据是两个职责，复用代码但工具独立注册，避免 `analyze_changes` 响应膨胀。

## 4. 工具设计：`review_changes`

### 4.1 参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `repo_path` | string | ✓ | 仓库路径（须已 analyze_repo） |
| `mode` | enum: `prepare` \| `submit` | ✓ | 收集评审上下文 / 落盘评审报告 |
| `since` | string | ✗ | commit 范围 `git diff <since>..HEAD`；留空默认未提交变更 |
| `spec_paths` | string[] | ✗ | SPEC/设计文档路径（相对或绝对）；缺省自动发现（docs/specs/.scratch/openspec） |
| `focus` | enum: `all` \| `spec` \| `convention` \| `module_knowledge` \| `general` | ✗ | 只跑指定评审轴（默认 all） |
| `report` | object | 仅 submit | `{title, findings: [...], summary}`，见 §5 |

### 4.2 prepare 返回：评审上下文包

源码版本规则：`since` 模式读 `git show HEAD:<path>`（与 diff 严格一致，不受工作区后续修改污染）；未提交变更读工作区文件。变更行在源码切片中用行号 + `>>` 前缀标注。

```json
{
  "status": "prepared",
  "query": {"repo_path": ..., "since": ..., "focus": ...},
  "target": {
    "diff_summary": {"changed_files": 3, "added_lines": 42, "deleted_lines": 18},
    "changed_components": [{"component_id": "b.py::func_b", "file_path": "b.py",
                             "start_line": 10, "end_line": 40, "component_type": "function"}],
    "changed_sources": {"b.py": "def func_b(...):\n    <变更函数全文+变更行标注>"},
    "affected_components": [{"component_id": ..., "depth": 1}],
    "suggested_tests": [{"file": "tests/test_b.py", "exists": true}]
  },
  "evidence": {
    "spec": {
      "found": true,
      "sources": [{"path": "docs/specs/payment.md", "excerpt": "退款须幂等..."}]
    },
    "convention": {
      "queries": ["编码规范", "日志约定", "命名约定"],
      "hits": [{"path": "repowiki/notes/xxx.md", "title": "...", "excerpt": "...", "score": 12.3}],
      "doctrine": "Core Principles 全文（query_wiki mode=overview 注入）"
    },
    "module_knowledge": {
      "hits": [{"path": "repowiki/notes/yyy.md", "type": "pitfall", "excerpt": "...",
                 "related_modules": ["payment"]}]
    },
    "general": [
      {"id": "err-handling", "title": "错误处理与资源释放", "lang": "all",
       "questions": ["异常是否被吞掉？", "文件/连接是否在 finally 中释放？"]}
    ]
  },
  "hint": "以 target 为评审对象、evidence 为依据执行评审；产出 findings 后可用 mode=submit 落盘。"
}
```

### 4.3 依据收集策略（prepare 内部，确定性）

**A. SPEC 轴（业务正确性）** — 借鉴已归档决策的四来源，去掉 gh CLI 依赖：
1. `spec_paths` 显式传入（最高优先，直接读文件）
2. 自动发现：在 `<repo>/docs/`、`<repo>/specs/`、`<repo>/.scratch/`、`<repo>/openspec/` 下**递归 3 层**，用**变更文件名 stem / 模块目录名**做模糊匹配（`payment.py` → `payment*.md`、`*支付*`）；命中后按排序取前 3 个（排序：stem 精确 > 子串 > 中文匹配），每个截断至 4000 字符
3. 全部未命中：在 prepare 响应中提示"未找到 SPEC，仅能评审通用正确性，无法查缺失/超范围"

**B. Wiki 规范轴（项目约定）**：
- 固定多查询检索：`["编码规范", "命名约定", "日志约定", "错误处理约定", "测试约定"]`（可配置，默认内置）
- 每查询取 top-K（默认 3）hits，携带 path/title/excerpt/score
- Doctrine 注入：`query_wiki(mode="overview")` 恒注入（L3 项目原则是最高优先级约定）
- `include_notes=true`（规范类知识存在 notes/，不在 wiki 页）

**C. 模块知识轴（历史踩坑）**：
- 模块名 = 变更文件所在**目录的全路径**（如 `codewiki/mcp/tools`，不用路径首段——太粗）；以模块目录名 + 变更函数名做查询
- `type_filter` 优先 `pitfall`/`lesson`/`architecture`/`decision`/`known_issue`
- 命中笔记按 `related_modules` 与变更目录相关性排序

**D. 通用规范轴（内置 checklist）** — 语言无关 + 语言相关两层：
- 语言无关：错误处理、资源管理、并发安全、输入校验、日志、安全（注入/密钥）、空值、边界条件、可测试性、向后兼容
- 语言相关：按变更文件后缀选择内置条目（如 Python：可变默认参数、裸 except、mutable 共享状态；Go：error 忽略、goroutine 泄漏；JS/TS：未处理 Promise、any 滥用）
- 内置清单存 `codewiki/mcp/tools/review_checklist.py`（数据文件）；**项目扩展机制**：模板 `codewiki/templates/review_checklist.yaml` 由 `init_wiki` 拷贝至 `<repo>/repowiki/review_checklist.yaml`（已存在则跳过，不覆盖用户自定义）；prepare 时读取并合并（同 id 条目项目覆盖内置，新 id 追加）

### 4.4 submit 落盘

- 校验 findings 结构（`_validate_report`）：字段缺失/类型错/axis 与 severity 枚举非法 → 拒绝并说明原因；`rule_ref.source` 指向的文件已不存在 → 不拒绝，降级为 warning（报告是历史记录，引用失效可容忍）
- 写 `<workspace>/review_reports/<timestamp>-<slug>.json`（评审报告全量）
- 返回 `{"status": "submitted", "report_file": ..., "note_hint": "关键发现可用 ingest_note 沉淀（需用户确认）"}`

## 5. 评审报告 Schema（submit 的 `report` 参数）

```json
{
  "title": "payment.py 变更评审报告",
  "summary": {
    "total_findings": 6,
    "by_severity": {"blocker": 1, "major": 2, "minor": 2, "nit": 1},
    "by_axis": {"spec": 2, "convention": 2, "module_knowledge": 1, "general": 1},
    "evidence_coverage": {"spec": true, "convention": true, "module_knowledge": true, "general": true}
  },
  "findings": [
    {
      "id": "F-01",
      "axis": "spec",                    // spec | convention | module_knowledge | general
      "severity": "blocker",             // blocker | major | minor | nit
      "file": "payment.py", "line": 24,
      "title": "退款重试缺少幂等键，违反 SPEC §3.2",
      "evidence": "retry 逻辑每次生成新 refund_id",
      "rule_ref": {"source": "docs/specs/payment.md", "quote": "退款须幂等，同一订单重复调用返回同一结果"},
      "suggestion": "以 order_id 派生幂等键并在入口处判重"
    }
  ]
}
```

严重度定义：
- **blocker**：违反 SPEC 核心条款 / 会引入生产事故（数据丢失、安全漏洞、幂等破坏）
- **major**：违反项目 wiki 规范或模块历史教训 / 明显正确性缺陷
- **minor**：偏离约定但可运行（命名、日志格式、异常类型选择）
- **nit**：风格建议，不影响行为

**轴间裁决顺序**（冲突时）：`spec` > `convention` > `module_knowledge` > `general`。
- SPEC 是业务正确性硬约束，高于一切工程约定；convention 含 Doctrine（L3 项目原则），高于历史笔记提醒；module_knowledge 是经验提醒而非禁令；general 是基线，只作参考
- 冲突时按高优先轴定严重度，在 finding 的 `rule_ref` 中同时引用两方依据并标注冲突，不擅自合并为一条

## 6. Prompt 扩展：change-review 增加评审步骤

在 `_prompt_change_review` 现有四步后追加第五步（不新建独立 prompt，保持"修改后评估"一个入口）：

```
## 步骤 5: 代码评审（review_changes）
调用 review_changes(mode="prepare", repo_path=..., since=<可选，留空=未提交变更>, spec_paths=[<可选>])
- evidence.spec: SPEC 命中情况——逐条比对变更是否覆盖需求、有无超范围
- evidence.convention: 项目规范 hits——检查变更是否违反（doctrine 为最高优先级）
- evidence.module_knowledge: 历史 pitfall/lesson——检查是否重蹈覆辙
- evidence.general: 通用清单——逐项过一遍
评审产出 findings 后，可选 review_changes(mode="submit", report=...) 落盘；
对值得复用的发现，经用户确认后 ingest_note 沉淀（pitfall/decision）。
```

同时更新 prompt 的 `description` 字段（list_prompts 条目），把"代码评审"纳入能力描述。

## 7. 知识闭环（评审 → Wiki）

评审不是终点，与知识飞轮衔接：

| 评审产出 | 沉淀方式 | note_type |
|---------|---------|-----------|
| 通用易错点（与项目无关） | 不落盘（通用知识无沉淀价值） | — |
| 项目级坑（违反模块约定/历史教训） | 用户确认后 `ingest_note` | `pitfall` |
| 评审中做的技术取舍 | 用户确认后 `ingest_note` | `decision` |
| SPEC 与实现的偏离清单（长期） | `ingest_note` | `known_issue` |

遵循确认闸门：**必须用户确认后 ingest**，绝不静默落盘。

## 9. 边界与限制（诚实声明）

1. **评审质量依赖 LLM 调用方**：工具只做确定性收集，不持模型；评审深度 = 调用方 Agent 的能力
2. **规范检索是 BM25 关键词检索**：语义不匹配会漏检（可经 spec_paths 显式传入 SPEC 缓解）
3. **SPEC 自动发现是文件名匹配**：无法理解文档内容相关性，复杂场景须 `spec_paths` 显式传入
4. **不执行代码**：并发/内存/性能问题只能静态推断，不运行测试或分析器
5. **通用 checklist 是基线**：不能替代团队定制的 lint/CI 规则；项目侧约定以 wiki 规范轴为准
6. **review 报告不进 query_wiki 检索**：报告落盘于 workspace（per-repo 共享，跨会话可见但只读），手动回看；有长期价值的内容须经 ingest_note 提升为笔记才可检索

## 10. 与既有工具的边界

| 场景 | 用哪个 |
|------|--------|
| 改动影响哪些函数、该测什么 | `analyze_changes` |
| 改动是否符合 SPEC/规范/历史教训 | `review_changes`（本方案） |
| 改某个函数前评估影响 | `analyze_impact` |
| 文档与代码一致性 | `lint_wiki` |

`analyze_changes` 保持"结构影响"，`review_changes` 负责"质量评审"，两者输入同源（同一 diff 语义）但职责分离，响应互不膨胀。
