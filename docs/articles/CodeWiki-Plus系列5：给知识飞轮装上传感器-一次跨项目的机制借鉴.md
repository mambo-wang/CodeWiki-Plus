# CodeWiki-Plus 系列 5：给知识飞轮装上传感器——一次跨项目的机制借鉴

> 前四篇我们建起了完整的"记忆金字塔"：对话采集、经验蒸馏、笔记评审、场景聚合、团队 Doctrine。但飞轮搭好之后，一个问题始终悬着：**它转得怎么样，没人知道。** 这一篇讲一次完整的跨项目借鉴——我们调研了腾讯开源的 teamai-cli，没有抄它任何一行代码的功能，却把它的三个机制精髓搬了回来，给知识飞轮装上了触发器、反馈回路和一颗诚实的心。

---

## 引子：飞轮在转，但我们是闭着眼睛在推

系列 4 上线分层提取后，知识库进入了"自动生长"状态。但某天复盘时我们发现了三个尴尬的事实：

- **该沉淀的经验，靠运气才能沉淀。** "纠正识别"写在 AGENTS.md 里，靠 Agent 自觉遵守——用户骂了三次、Agent 返工三遍的会话，事后谁也没想起来该记一条笔记。什么时候该沉淀，全凭模型心情；
- **检索热度在记账，但账本没人看。** `retrieval_stats.db` 忠实地记录了每个文档被查过几次，但这些数据写进去之后就再没出来过——不影响排序、不影响复核优先级、不影响任何决策。一本只记不读的账；
- **Agent 检索完，分不清"找到了"和"找对了"。** 搜索返回十条结果，哪条真正命中了查询意图？分数本身说不清。Agent 拿着一堆"主题相邻"的结果当答案用，错了都不知道该去哪纠正。

更麻烦的是第四个问题：当第二个人开始用这个知识库，整套机制突然全是窟窿——队友 pull 下来的新笔记，他本机的检索索引里没有，**搜不到刚拉下来的知识，且没有任何提示**。

带着这四个问题，我们去调研了腾讯开源的 teamai-cli。结论出乎意料：**这个项目和 CodeWiki 定位完全不同（它是"团队 AI 配置分发工具"，我们是"代码知识库"），但它在"知识飞轮运营"上的机制设计，恰好是缺的那几块拼图。**

先看全景。这次借鉴分三波落地：

```mermaid
flowchart TB
    subgraph P0["第一波 P0：传感器（3 天落地）"]
        A[摩擦信号触发<br/>纠正/打断/重复 自动评分<br/>≥20 分提示优先蒸馏] --> B[使用反馈回流<br/>检索热度接入 BM25 排序<br/>热升冷降]
        B --> C[检索透明化<br/>命中词/缺失词明示<br/>check 预检 + token 预算]
    end
    subgraph P1["第二波 P1：从曝光度到有用度（2 天落地）"]
        D[采纳信号<br/>Agent 声明"我真正用了哪条"<br/>权重 2 倍于单纯召回] --> E[低采纳检查<br/>高频召回零采纳 =<br/>内容相关但不够 actionable]
        E --> F[promote 晋升<br/>被反复采纳的笔记<br/>AI 重写去个人化 转正入 Wiki]
    end
    subgraph T["第三波：团队共享正确性（3 天落地）"]
        G[索引自愈<br/>拉取后自动检测重建<br/>project.json 相对化] --> H[遥测共享<br/>per-user jsonl 入库<br/>热度变团队口径]
        H --> I[冲突面治理<br/>秒级可重建的索引出库<br/>md 是唯一事实源]
    end
    P0 --> P1 --> T
```

三波改造，测试从 140 项涨到 292 项，总投入约 8 个人日。下面逐环节讲。

## 一、摩擦信号：让"该记笔记的时刻"变成客观检测

**业务问题**：什么会话值得沉淀经验？人记得的时候会记，忘了就流失。靠 prompt 提醒（"被纠正时要反思"）的漏报率高得离谱。

**teamai 的答案**给了我们很大启发：它不在"提醒"上做文章，而是直接检测**摩擦信号**——用户打断（×20 分）、拒绝工具调用（×20）、纠正性发言（×20）、工具反复失败（分档 10~25 分）。分数过阈值才提示"这个会话可能值得记录"。最妙的是它的防误报设计：**规模加分封顶 10 分，永远凑不满 20 分的阈值**——一个"又长又顺"的会话（工具调用很多但没有摩擦）在数学上就不可能触发提示。真正较劲过的会话才会被记住。

**我们的落地**（适配了一个关键差异）：CodeWiki 的对话采集管线会过滤掉工具调用流量，只留纯对话——所以工具层的信号在我们这拿不到。v1 只用对话层信号：纠正关键词 ×20、打断标记 ×20、重复提问（同一句话说了两遍，说明 Agent 没听懂）×15，硬门槛"用户发言 ≥4 轮"防短会话误报。

摩擦分写进对话档案的 frontmatter，在三个地方被消费：蒸馏清单按分数降序排列（高分对话优先处理）、任务上下文携带分数、**新会话开始时 hook 自动提示**"上次会话摩擦分 35（纠正 2 次），建议先补蒸馏"。

一个重要的边界：摩擦分只是**提示**，永不自动蒸馏、永不绕过人工评审闸门。传感器只负责喊一声，动不动手还是人说了算。

## 二、热度回流：让只写不读的账本活起来

**业务问题**：检索热度数据躺在本机 SQLite 里，除了占地方什么都不干。

**teamai 的机制**是"投票"：每次检索命中记一张隐式票，实际引用记一张显式票，票数乘进搜索排序。我们把它简化成一个 heat 公式接入 BM25：

```
heat = 1 + min(0.15, 0.03·ln(1+命中数)) − 冷惩罚
```

三个设计要点：**对数饱和**（命中最多的文档增益封顶 15%，热度永远压不过相关性）；**冷惩罚只打"热过后来冷"的文档**（命中过 3 次但 180 天没人查才降权——新文档保持中性，避免"排名低→没命中→排名更低"的马太循环）；**蒸馏去重召回豁免**（判断两条笔记是否重复是相似度问题，不能被热度扭曲）。

配套的还有检索透明化三件套：结果附上"命中了哪些查询词/缺了哪些词"（Agent 自己判断这条结果是真答案还是主题相邻）、check 轻量预检模式（先花 200 token 判断值不值得深查）、内容预算参数（按任务复杂度取量）。

## 三、采纳信号：从"曝光度"到"有用度"

第二波解决的是 heat 公式的输入质量问题。热度只度量"被检索到"（曝光），度量不了"被用上"（采纳）。一条每次都被搜到、从来没人用的笔记，和一条每次都被搜到且真正解决问题的笔记，在数据上无法区分。

**方案是一个极简的约定**：Agent 在最终回复里声明"我实际引用了哪几条检索结果"——一行 HTML 注释，路径与检索返回完全一致：

```
<!-- codewiki:referenced-docs: ["notes/pitfall-port-conflict.md"] -->
```

会话结束时采集器解析这行声明，记一次**采纳事件**。heat 公式升级：采纳权重是单纯召回的 2 倍，仍被总封顶压住。

这个信号是**下界信号**——忘了声明会漏报（可容忍），但没人会声明一条没用过的文档（误报罕见）。做排序权重够用，做严格考核不行。这个定位要写清楚。

采纳数据随后点亮了两个新机制：

- **低采纳检查**（lint 第 17 项）：一条笔记被高频召回（≥5 次）但零采纳，说明它的标题相关但**内容不够 actionable**——用户搜到了它，却没法照着做。这是"内容质量"的全新维度信号，与时间维度（过期检查）、数量维度（聚类合并检查）正交；
- **promote 晋升**：一条笔记被反复采纳（≥3 次）且存活超过 14 天，就该"毕业"了——AI 把它从"经验体"（上周三那个订单超时）重写为"知识体"（支付超时的典型根因与排查步骤），抹掉日期、人名、一次性事件，转正为正式 Wiki 页面。原笔记保留作审计锚点，新页面照走人工确认闸门。

至此飞轮的信号链完整了：**摩擦触发沉淀 → 召回计量曝光 → 采纳计量有用 → 低采纳驱动重写 → 高采纳驱动晋升。**

## 四、团队场景：md 是唯一事实源

第三波是被一个问题逼出来的："这个形态支持团队吗？"答案是：知识本身能共享（repowiki 随 git 走，clone 即得），但**整条信号链路是本机视角的**——而且藏着一个静默 bug：队友 pull 了新笔记，他本机的检索索引不含这些内容且优先命中，**搜不到刚拉下来的知识，无任何提示**。

这次从 teamai 借鉴的只有一样东西（它的分发基建对我们不适用——知识资产随业务仓走是我们的天然优势）：**per-user 文件的并发写解法**。每人只写自己的文件，git 文件级合并天然零冲突。

落地成三条：

- **索引自愈**：每次搜索前做一次廉价检查（文件数对不对、清单匹不匹配、抽样 mtime 是否晚于索引构建时间），不一致就自动重建，60 秒节流，重建失败降级继续用旧索引——检索永不因自愈失败而中断。顺手把 project.json 的绝对路径改成相对路径，根治"换台机器配置失效"的老毛病；
- **遥测共享**：本机 SQLite 账本退役，改为 `telemetry/<user>.jsonl` 事件流（入库）——每人一本自己的流水账，各记各的，git 合并零冲突，pull 之后自动汇总。热度、低采纳、晋升判定全部升级为**团队口径**：一条笔记两个人各自采纳过两次，在谁的单机上都到不了 3 次门槛，团队聚合后 4 次——"不同的人都觉得有用"才是真正的晋升证据；
- **冲突面治理**：把"md 文件是唯一共享事实源，一切秒级可重建的索引都是本机派生"定为总原则——搜索索引移出版本库（消灭最大的全量重写冲突面），昂贵的代码分析产物继续共享。

**一句话总结团队方案**：不是把单机版改成团队版，而是把"本机派生状态"和"共享事实源"的边界画清楚——边界之内怎么折腾都是缓存问题，边界之外才需要协作语义。

## 五、怎么用：面向用户的操作指南

这三波机制有个共同的体验特征：**大部分是零操作的**——它们在后台自转，用户能感知到的只是"检索结果变准了"、"该记的提醒自动出现了"。需要用户主动参与的只有四处。

### 日常（零操作，自动发生）

摩擦评分、热度排序、索引自愈、采纳计数——全部随日常使用自动积累和生效。你唯一会"看见"它们的地方：

- **新会话开始时**，如果上次会话摩擦分 ≥20，IDE 会收到一行提示：`[codewiki] 上次会话摩擦分 35（纠正 2 次），建议先 distill_conversation 补蒸馏再开始新任务`——看到这行字，说明有一个值得沉淀的会话在排队等你处理；
- **检索结果里**，每条结果多了一个 `usage` 字段（被查过几次、被采纳过几次），以及 `matched_tokens`（这条结果实际命中了你查询里的哪几个词）。它们不需要你做任何事，只是让排序的"为什么"变得可见。

### 需要主动做的四件事

**1. 采纳声明（唯一需要养成的新习惯）**

当你通过 `query_wiki` 检索并**真正使用了**某条结果（作为决策依据、修改参照或答案来源），在最终回复里加一行：

```
<!-- codewiki:referenced-docs: ["notes/pitfall-xxx.md", "wiki/modules/yyy.md"] -->
```

路径照抄检索返回的 `file` 字段。这是整个"有用度"信号链的入口。纪律只有一条：**忘了声明没关系（漏报可容忍），但别声明没用过的（误报不可容忍）**。这条约定已写入 AGENTS.md，装了 CodeWiki-Plus 的 Agent 会自动遵守。

**2. 低采纳体检（每月一次即可）**

```
lint_wiki(checks=["low_adoption"])
```

报告会列出"被高频召回但零采纳"的笔记——标题相关但内容不够 actionable 的信号。对着报告把这几条笔记改得更可操作（补步骤、补命令、补预期结果），检索质量会立竿见影地提升。

**3. 晋升操作（看到候选再做）**

```
wiki_stats()   # 看 promotion_candidates 列表
```

当某条笔记被采纳满 3 次、树龄超 14 天，它会出现在晋升候选里。在 IDE 的 Prompt 面板触发 **`promote-note`** 工作流，Agent 会读完原笔记 → 按类型路由（踩坑笔记 → 排查记录页，经验教训 → 概念页）→ 去个人化重写（"上周三那个订单超时"变成"支付超时的典型根因"）→ 以草稿状态写入 Wiki 等你确认。你只需最后点一次确认。

**4. 团队成员接入（一次性）**

新成员 `git clone` 仓库 + 安装 codewiki-plus 即可——索引自动构建（索引自愈）、团队热度自动聚合（telemetry jsonl 随 git 到位）。唯一建议的个性化设置：不想用 git 真名署名遥测的成员，设一个环境变量 `CODEWIKI_USER=花名`。单人用户不想要入库遥测，schema.yaml 里 `telemetry.enabled: false` 一键关回纯本机模式。

## 六、使用举例：一天的完整体验

用一个虚拟开发者的周一来串一遍全流程。

**上午 9:50，小王打开 CodeBuddy 继续"支付重构"任务。** 会话一启动，屏幕上出现一行提示：*上次会话摩擦分 40（纠正 2 次），建议先补蒸馏*。他想起上周五确实跟 Agent 较劲了一下午——连接池参数怎么调都不对。他跑了一下 `distill_conversation`，蒸馏清单里那条摩擦分 40 的对话排在最前面，提取出一条 pitfall 笔记《连接池 maxTotal 低估导致高并发超时》，确认入库。

**上午 10:20，写代码前检索。** 小王让 Agent 查"连接池 超时 参数"：

```json
{
  "query": "连接池 超时 参数",
  "query_coverage": {"matched": ["连接池", "超时"], "missing": ["参数"]},
  "results": [
    {"file": "notes/pitfall-连接池超时.md", "matched_tokens": ["连接池", "超时"],
     "usage": {"hit_count": 6, "last_hit": "昨天", "adopted_count": 2}, ...},
    ...
  ]
}
```

刚入库的那条笔记已经在结果里了（笔记写入时索引同步增量更新，立等可查）。`missing` 提示"参数"这个词全库没有匹配——提醒他结果里没有真正讲参数配置的内容，得自己判断够不够用。

**中午，他基于那条笔记改完了连接池配置。** 回复末尾按约定加了一行：

```
<!-- codewiki:referenced-docs: ["notes/pitfall-连接池超时.md"] -->
```

这条笔记的采纳计数 +1，团队累计 3 次——达到晋升门槛。

**下午，例行体检。** `wiki_stats` 里那条笔记出现在 `promotion_candidates`（adopted=3，树龄 15 天，建议转 `concept` 页）。小王触发 `promote-note`，Agent 把"我上周调连接池踩的坑"重写成《连接池容量规划：从现象到根因的排查方法》——没有日期、没有"我"、没有具体工单号，只有可复用的方法。小王 review 后确认，一条个人经验毕业成了团队知识。

**晚上，同事小张 pull 了代码。** 小张机器上没有索引文件（索引已出库），他的第一次 `query_wiki` 触发自动构建，秒级完成；小王的遥测 jsonl 也随 pull 到位，那条连接池笔记在小张的检索里同样带着团队热度。两边各查各的、各采各的，明天 merge 时两人的 jsonl 互不冲突——因为从来没有人写别人的文件。

这就是"装上传感器"之后的一天：**该记的有人提醒、查到的原因可见、用过的心里有数、好的经验会毕业、团队的数据自动汇合**——用户没有多做任何"管理知识库"的工作，只是正常干活。

## 七、方法论复盘：调研一个开源项目，到底在调研什么

这次借鉴最值得复述的，可能不是任何具体机制，而是**调研姿势**：

- **抄机制，不抄功能**。teamai 的"摩擦评分"如果照抄功能，会连它的 IDE hook、transcript 扫描一起搬——但那是它的架构。我们抽出的机制内核是"摩擦主导评分 + 规模封顶凑不满阈值"这个数学结构，落地时适配了自己的管线；
- **失败史比功能清单值钱**。teamai 的 CHANGELOG 里记着它**砍掉了**第一代"每次工具调用后自动检索"的 hook（噪音大、命中率低），改成任务开始前的主动检索。这条"不做什么"的记录，帮我们避开了同一条弯路；
- **判断哪些不能抄，比判断哪些能抄更重要**。teamai 的孤儿分支、worktree 分发协议、角色命名空间，是为"知识资产与业务仓分仓"设计的整套基建——我们 repowiki 天然随代码走，一整套都不需要。最后只吸收了它的 per-user 并发写思想，其余全部划入"明确不做"。

照例用一张表收尾：

| 业务问题 | 设计决策 | 拿到什么 |
|---|---|---|
| 该沉淀的时刻靠模型自觉 | 摩擦信号客观评分，规模封顶防误报 | 遗漏不再无声 |
| 热度账本只写不读 | 对数饱和 heat 接入排序，冷惩罚防马太 | 常用的知识自己浮上来 |
| 检索结果真假难辨 | 命中词/缺失词明示 + check 预检 | Agent 能分清"找到了"和"找对了" |
| 曝光度≠有用度 | 声明式采纳信号，权重 2 倍于召回 | 排序知道哪条真被用了 |
| 相关但不 actionable 的内容 | 高频召回零采纳 → lint 检查 | 内容质量有了效用维度 |
| 好笔记困在 notes 目录 | 采纳达标 → AI 去个人化重写转正 | 经验会毕业成知识 |
| 团队 pull 后索引静默过期 | 三层判据自愈 + 60s 节流 | 检索永远新鲜 |
| 遥测本机碎片化 | per-user jsonl 单一事实源 | 团队口径的信号链 |
| 聚合文件必冲突 | md 是唯一事实源，廉价索引本机派生 | 冲突面归零 |

回头看这三波改造，本质上是在重复同一条我们一直坚持的原则，只是这次用在了知识库自己身上：**确定性交给工具（信号采集、聚合、自愈），判断力留给 Agent（重写、晋升、去个人化），决定权留给人（闸门、确认、退役）。** 飞轮从此不是"搭好了"，而是"会反馈了"——它转得快不快、哪一环在空转，第一次变得可见、可测、可调。

下一篇，我们聊这波改造之后浮现的新课题：当遥测数据开始积累，知识库的"资产治理"（置信分层、负反馈闭环、知识退役）如何从拍脑袋走向数据驱动。敬请期待。
