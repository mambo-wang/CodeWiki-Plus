# CodeWiki-Plus 系列 14：使用全景与最佳实践——从初始化到知识飞轮的完整路线图

> **本篇导读：** 前面 13 篇分别讲了双层 Prompt、零依赖检索、知识写入、任务记忆、记忆分层、四维评审、多仓工作区、知识可信度、技能编译、团队化改造……这一篇把它们串起来：一个新项目从零开始，CodeWiki-Plus 应该按什么顺序用、哪些能力按需开启、每一步的最佳实践和常见误区是什么。可以当作团队的「上手手册」和「验收清单」。

**TL;DR:** CodeWiki-Plus 的正确打开方式是一条渐进式路线：**安装接线（一次性）→ 初始化工作区 → 按需生成代码 Wiki → 让 Wiki 参与日常开发 → 按需启用任务记忆 → 运转知识飞轮 → 定期体检**。核心原则有三条：工具做确定性簿记、推理决策在 Agent 和人手里；入库必经显式确认闸门；能力按需开启，不要一上来全量拉满。

---

## 一、先看全景：53 个工具，其实只有 7 件事

CodeWiki-Plus 把 MCP Server 拆成了 53 个细粒度工具，初看容易眼花。但按「你什么时候会用到它」来分组，其实只有 7 件事：

| 阶段 | 你要做的事 | 核心工具 / Prompt |
|------|-----------|------------------|
| 0. 安装接线 | 装 CLI、配 MCP、接 Hook | `pip install` + MCP 配置 + `codewiki install-hooks` |
| 1. 初始化 | 建工作区骨架 | `init_wiki`（单仓）/ `init_workspace`（多仓） |
| 2. 生成 Wiki | 代码 → 结构化文档 | `analyze_repo` → 聚类 → `write_doc_file` → `close_session`；增量用 `analyze_changes` |
| 3. 日常消费 | 检索驱动开发 | `query_wiki`（渐进式阅读）、`analyze_impact`、`review_changes` |
| 4. 任务记忆 | 长线任务跨会话延续 | `create_task` / `set_session_task` / `get_task_context` / `add_task_memory` |
| 5. 知识飞轮 | 经验 → 笔记 → 场景块 → 共识 → 技能 | `ingest_note` → `confirm_note` → `consolidate_notes` → `refresh_doctrine` → `skill_creator` |
| 6. 治理体检 | 保真、保鲜、可信 | `lint_wiki`、`wiki_stats`、`report_outcome`、`flag_conflict` |

一个关键认知：**这张表从上到下是「依赖递增」的，但不是「必须全开」的**。你可以只用阶段 0-3（一个会自我更新的文档引擎），也可以一路开到阶段 6（一个自生长的团队知识库）。下面逐阶段展开。

## 二、阶段 0：安装与接线（一次性，10 分钟）

### 2.1 三步安装

```bash
# 1. 安装（Python 3.12+；Node.js 可选，用于 Mermaid 校验）
pip install codewiki-plus
codewiki --version

# 2. 在 IDE 的 MCP 设置中添加
#    command: codewiki, args: ["mcp"]

# 3. （可选，团队记忆/任务引导）接线 Hook
codewiki install-hooks --repo-path <你的仓库>
```

第三步值得多说一句：`install-hooks` 会自动检测项目根目录存在哪些 IDE 配置目录（`.codebuddy/`、`.claude/`、`.qoder/`、`.trae/`），检测到哪个就为哪个接线——拷贝 hook 脚本、幂等合并 settings.json、写入 AGENTS.md 引导段。命令路径一律用项目相对形式，队友克隆到任意目录都能直接工作。

### 2.2 环境变量：真正需要设的只有 2 个

开箱即用，默认零配置。真正值得设的只有：

- `CODEWIKI_LANG`：想用英文界面时设 `en`（默认中文）；
- `CODEWIKI_USER`：遥测署名花名——不想用 git 真名署名的成员设一个。

注意环境变量要写在 MCP 配置 JSON 的 `env` 块里（MCP 进程只在启动时读一次），写 `.bashrc` 对它不可见。

**最佳实践：**
- 团队协作时统一约定花名，遥测数据（谁检索了什么、谁采纳了哪条知识）才有可读性；
- `CODEWIKI_RAW_TOOL_DETAIL` 默认开启，**除非排障否则别关**——关掉会导致后续无法编译出含完整步骤的技能。

## 三、阶段 1：初始化——先搭骨架，再谈内容

初始化分两条路，取决于你的仓库形态：

### 3.1 单仓库：`init_wiki`

新项目或第一个仓库，先执行初始化（对话里说「初始化 Wiki 工作区」即可，Agent 会走 `init-wiki` Prompt）：

- 创建 `repowiki/` 完整目录骨架（wiki/、notes/、tasks/、raw/、.meta/ 等）；
- 生成项目级 `schema.yaml`——这是项目的文档「宪法」，包含 purpose 定位、命名规范、page_types 路由表、code_routing 代码路由规则。

**最佳实践：初始化后第一件事是改 `purpose`。** 把项目的一句话定位写进去，后续所有文档生成、检索路由都会参考它。这是整个知识库里「杠杆率最高」的一次人工投入。

### 3.2 多仓库：`init_workspace`

如果你面对的是多个业务仓（微服务群、前后端分离），用多仓 Harness 工作区：

- 首次初始化会**强制征询知识布局选择**：`colocated`（知识随仓走）还是 `centralized`（知识集中在工作区顶层）——这个决策会持久化，之后重跑零配置幂等；
- 自动生成 bootstrap 克隆脚本、repo-map 导航、工作区级 AGENTS.md 约定（两跳检索路由）；
- 业务仓登记走 `add_workspace_repo`，移除走 `remove_workspace_repo`（注意：会删除本地克隆目录，不可恢复）。

**最佳实践：** 布局选择没有标准答案，看团队的检索习惯——「查知识时先想到仓库」选 colocated，「先想到主题」选 centralized。选错了可以重新初始化，但趁早定，避免知识树长歪后再搬家。

## 四、阶段 2：按需生成代码 Wiki——全量一次，增量常伴

### 4.1 首次全量生成

对 Agent 说：

```
帮我分析当前仓库并生成 Wiki 文档，输出到 repowiki 目录。请使用中文撰写文档。
```

Agent 会走五阶段流水线：`analyze_repo`（AST 解析 + 依赖图 + monorepo 子服务检测）→ 聚类分组（3-8 个逻辑模块）→ 叶优先逐模块写文档（自动注入 BFS 调用上下文 + 约束索引表）→ 合成 overview.md → `close_session`（建 BM25 索引 + wikilink 图谱）。

生成质量上有三个内置增强值得知道：

1. **Evidence-Based 断言**：每条业务规则要求附代码证据（文件:行号 + 置信度），`lint_wiki` 的 `unsupported_claims` 检查会抓超过 30% 断言无证据的页面——这是识别 LLM 幻觉的第一道网；
2. **代码路由分类**：business 组件全量注入、boilerplate 只留签名、infra 摘要级描述，典型 Java 仓库省 30%+ token；
3. **方法级增量检测**：之后每次 `analyze_repo` 自动比对 content_hash，只有真正变化的方法才标记 stale。

### 4.2 日常增量更新

代码改完后说一句「代码有改动，帮我更新受影响的模块文档」即可。增量链路：Git diff（回退 SHA256 指纹）→ 方法级 stale 检测 → 只重生成受影响模块 → overview 按实际引用关系精确判定是否需要刷新。

**最佳实践：**
- **不要每次提交都全量重生成**——增量检测就是为「高频小改」设计的，全量是浪费；
- 大仓库首次生成建议挑一个业务空闲时段，生成完跑一次 `lint_wiki` 留下基线 health_score；
- `schema.yaml` 的 `code_routing` 规则可以按项目定制（比如把你们仓库里大量的生成代码标成 boilerplate），定制一次，每次生成都受益。

## 五、阶段 3：让 Wiki 参与日常开发——检索驱动，而不是生成完就吃灰

**Wiki 生成出来只是开始。它真正的价值在「被用」——每次检索命中、每次实际引用、每次使用后的成败反馈，都会进入遥测，反过来驱动知识排序和淘汰。** 这一阶段没有任何新工具要装，改变的是工作习惯：

### 5.1 改代码之前，先查知识

```
我要修改订单状态机的流转逻辑，先查一下项目里相关的知识和约束。
```

Agent 会走渐进式阅读协议：`query_wiki(mode=overview)` 了解全貌 → `mode=directory` 定位目标 → 关键词 + `hop=1` 图谱扩展深入。改某个文件前还可以 `query_wiki(by_file=<路径>)` 拉出该文件的历史决策与踩坑记录。

### 5.2 评估影响、评审变更

- 改动前：「评估一下修改 X 组件的影响范围」→ `analyze_impact`（BFS 传递性遍历 + 高风险组件识别）；
- 提交前：「评审一下这次的变更」→ `review_changes` 四维评审，评审清单来自团队沉淀的 pitfall 笔记——**你踩过的坑，自动变成你同事的检查单**（系列 8 的主题）。

### 5.3 无 MCP 环境的检索

CI 脚本或不支持 MCP 的工具里，用 CLI：`codewiki query "<关键词>"`，与 `query_wiki` 同一引擎，输出 Agent 友好的定界文本块。

**最佳实践：**
- 把「改前查、提交前评审」写进团队 AGENTS.md，让 Agent 每次主动执行而不是等人提醒；
- 检索结果里注意 `source_type` 标注：`auto_generated` 可直接引用，`developer_note` 要看确认状态，draft 笔记带 `[unconfirmed]` 前缀——**别把未确认知识当定论用**。

## 六、阶段 4：按需启用任务记忆——长线任务的跨会话延续

任务记忆解决的是「长线工作跨会话断片」：一个重构任务持续数天、横跨多个会话，Agent 每次重启都从零开始。它与 Wiki 笔记互补——**Wiki 笔记沉淀跨任务的通用经验，任务记忆保存任务范围内的进度知识**。

### 6.1 启用与工作流

Hook 接线后（阶段 0 的 `install-hooks`），SessionStart 会自动提示任务关联。标准工作流：

```
会话开始：
  弹框选择关联任务 / 新建 / 跳过
  → set_session_task 绑定会话
  → get_task_context 恢复上下文（任务描述 + 分层记忆 + 关联笔记）
  → 若有未蒸馏积压：后台 subagent 补蒸馏，不阻塞干活

会话过程中（主动沉淀，停顿点即写）：
  任务里程碑 / 关键决策落定 / 话题转向时
  → add_task_memory 直写进度记忆（无需确认）
  → 通用经验走 ingest_note 落草稿（需 confirm 确认）

会话收尾：
  → report_outcome 报告本次使用知识后的成败
```

### 6.2 两条通道，两种闸门

这是任务记忆设计里最值得理解的区分（ADR-0002）：

| 通道 | 内容 | 闸门 |
|------|------|------|
| 任务记忆（`add_task_memory`） | 任务内进度事实：做了什么、下一步、待办 | **直写**——可逆操作（archive 兜底），免确认 |
| 经验笔记（`ingest_note`） | 跨任务通用知识：踩坑、决策、模式 | **确认闸门**——draft 起步，`confirm_note` 后才进正式语料 |

为什么不同？笔记是全队共享的知识，错了会误导所有人，必须评审；记忆是任务内的进度事实，写错了大不了改，archive 里原文可找回。

**最佳实践：**
- **不要每轮对话都写任务记忆**——记忆追加无去重，每轮都写会灌爆压缩阈值（40 条 / 24KB）。只在停顿点写：里程碑、决策落定、话题转向、收尾轮；
- 记忆超阈值时 `get_task_context` 会携带压缩工作，Agent 顺手提交即可，原文进 archive 永远可搜（`search_task_memories`）；
- 短平快的一次性任务（改个 bug、问个问题）直接「跳过」关联，别为半小时的活建任务。

## 七、阶段 5：运转知识飞轮——从经验碎片到可执行技能

这是 CodeWiki-Plus 区别于「文档生成器」的核心：知识不是写完就静止，而是沿一条五级流水线不断晋级：

```
L0 对话/调试中的经验碎片
  → ingest_note（draft，weak 置信，检索带 [unconfirmed]）
  → confirm_note（stable；带 test_ref/commit_ref 证据升 strong）
  → consolidate_notes（L2 场景块：可复用工作方法，带容量治理）
  → refresh_doctrine（L3 doctrine.md：团队工作方式共识）
  → skill_creator（把确认知识编译成 SKILL.md 行为指令，两区制：草稿区进索引进 lint、不生效；用户确认后 install 进生效区）
```

配套的治理机制：

- **置信分层**（strong/weak/shadow，与状态正交）：检索排序叠加置信权重（strong +0.10 / shadow −0.30），`wiki_stats` 监控 strong 占比（北极星指标 >60%）；
- **冲突治理**：两条笔记矛盾时 `flag_conflict` 立案（顶级 conflicts/ 案卷），`adjudicate_conflict` 裁决，败方自动降级（ADR-0007）；
- **使用结果信号**：任务收尾 `report_outcome` 报告成败，失败用例自动进入蒸馏提示的 negative_examples——**用错的知识会在新知识提取时被规避**。

**最佳实践：**
- 沉淀前过「四问过滤」：下次对话还能用到？其他同事能直接受益？`query_wiki` 确认未覆盖？属于事实/决策/模式/教训而非临时状态？四问全过才记录；
- **宁可漏报不可误报**地做采纳声明：真正用到的文档才声明引用，零采纳高频笔记会被 `low_adoption` 检查标记出来提示重写；
- 场景块有容量上限（红 12 / 橙 9），满了先 MERGE 腾位再新增——这是刻意设计，逼着知识收敛而不是无限膨胀；
- 技能 install 前务必人工审一遍 SKILL.md——草稿区不生效就是给你留的审查窗口。

## 八、阶段 6：定期体检——知识库的「健康度运营」

知识库和代码一样会腐化，需要定期体检：

| 频率 | 动作 | 工具 |
|------|------|------|
| 每次收尾 | 报告知识使用成败 | `report_outcome` |
| 每周 | 跑一次全面体检：25 项检查 + health_score | `lint_wiki` |
| 每周 | 看统计：检索热度、冷笔记、晋级候选、strong 占比 | `wiki_stats` |
| 随时 | 发现矛盾立即立案 | `flag_conflict` → `adjudicate_conflict` |
| 发现问题 | 标记质量问题，驱动 health_score | `flag_issue` |

`lint_wiki` 的 25 项检查覆盖结构完整性（断链、stale_refs、布局违规）和内容质量（无证据断言、过期笔记、低采纳笔记、超期冲突案卷）。health_score = `100 - Σ(error×10 + warning×3 + info×1)`，建议把它纳入团队周会的固定议题——**分数下降比分数绝对值更重要**。

**最佳实践：**
- 聚合操作（consolidate/refresh_doctrine）之后必跑一次 `lint`；
- `stale_notes`（90 天未检索的已确认笔记）不要无脑删，先判断是「过时了」还是「太冷门」——前者 reject，后者考虑合并进场景块。

## 九、一页纸最佳实践清单

把全文收敛成一张可以贴在团队 Wiki 里的清单：

**初始化期**
- [ ] `purpose` 字段认真写——杠杆率最高的一次人工投入
- [ ] 多仓布局（colocated/centralized）趁早定，按团队检索习惯选
- [ ] `code_routing` 按项目定制，生成代码标记为 boilerplate

**生成期**
- [ ] 全量生成一次留基线，之后一律增量
- [ ] 生成完跑 `lint_wiki` 记录基线 health_score
- [ ] 断言必须带证据，`unsupported_claims` 警告当回事

**日常期**
- [ ] 改前查（by_file + 渐进式阅读）、提交前评审（四维清单）
- [ ] 注意 `source_type` 与 `[unconfirmed]` 标注，未确认知识不当定论
- [ ] 「改前查、提交前评审」写进 AGENTS.md，让 Agent 主动执行

**任务期**
- [ ] 长线任务才关联，短任务跳过
- [ ] 只在停顿点写任务记忆（里程碑/决策/转向/收尾）
- [ ] 进度走 `add_task_memory` 直写，经验走 `ingest_note` 过确认闸门

**飞轮期**
- [ ] 沉淀前过四问过滤，四问全过才记录
- [ ] 采纳声明宁漏勿误，`report_outcome` 每次收尾必报
- [ ] 场景块满了先 MERGE，技能 install 前人工审查

**治理期**
- [ ] 每周 `lint_wiki` + `wiki_stats`，health_score 纳入周会
- [ ] 冲突随时立案、限期裁决（默认 14 天）
- [ ] 冷笔记先判「过时」还是「冷门」，再决定 reject 还是合并

## 十、三个常见误区

**误区一：一上来全量拉满。** 刚装好就把 Hook、任务记忆、飞轮全套开启，结果每个会话都在弹框、沉淀、确认，正事没干几件。正确姿势是渐进式：先跑通阶段 0-3（文档引擎 + 检索消费），团队尝到甜头再开任务记忆，飞轮最后启动——它依赖前面积累的检索和采纳数据才能转起来。

**误区二：把 Wiki 当一次性交付物。** 生成完就归档吃灰，三个月后 `lint_wiki` 满屏 stale。Wiki 是活的知识库，它的价值随使用次数增长——检索命中、采纳引用、成败反馈，每个信号都在让它变得更准。不用，它就只是占磁盘的 Markdown。

**误区三：绕过确认闸门。** 觉得 draft → confirm 流程麻烦，让 Agent 批量自动确认所有笔记。确认闸门是整个信任模型的基石（机器写的知识必须经人评审才能进正式语料），绕过它，知识库会以「可信」的姿态传播未经验证的结论——比没有知识库更危险。

---

## 结语

CodeWiki-Plus 的 53 个工具、23 个工作流 Prompt，背后是一条清晰的主线：**确定性的事交给工具，推理的事交给 Agent，入库的事交给人确认。** 使用全景的每个阶段都是这条主线的具体化——初始化定骨架、生成定事实、检索定消费、任务定延续、飞轮定进化、体检定保鲜。

按需启用、渐进深入。一个人用，它是不会断片的记忆；一群人用，它是越用越准的资产。
