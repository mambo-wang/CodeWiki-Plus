# 任务记忆多人协作分片设计方案

> 状态：P0 已实施（2026-08-25，分层加载 + 分片存储 + 文件域压缩 + user_id email 链 + union driver）；P1 已实施（2026-08-25，index 可重建：读侧廉价 id 集校验，失配/损坏时扫 task.md frontmatter 重建回写）；P2 观察项未动
> 关联：《任务记忆存储与加载扩展性设计方案》（前作，P0/P1 已实施；本方案是其多人协作续篇）
> 决策记录：ADR-0001（markdown 不迁 JSONL）、ADR-0002（任务记忆直写不走 confirm 闸门）继续有效；本方案不改条目格式，零新增 frontmatter 字段
> 蓝本：`codewiki/mcp/tools/telemetry.py`（每用户一文件的 git 冲突消解模式已在遥测链路验证）

## 1. 背景与问题

前作方案解决了单机扩展性（时间戳头切条 + 截断加载 + 压缩归档），但所有写入仍落在**同一个** `memories.md`。多人协作开发同一个任务（或同一人多机）时，git 合并面临三类冲突：

1. **尾部追加冲突**（最高频）：两人各自 append，同一位置加行，git 报冲突。memories-archive.md 同理。
2. **压缩语义冲突**：compaction 是"重写主文件"而非 append，发起者会把队友的条目一并移走；即使 git 行级不冲突，union 合并也会把已归档条目 resurrect 回主文件。
3. **`.index.json` 冲突**：全局单 JSON，两人各自建新任务时整文件相撞（本方案第二刀，独立于分片）。

单机并发已被防住（temp + os.replace 原子写 + 串行化），本文不重复处理；本文只解决**跨机器 git 合并**层面的冲突。

分片之后第二个问题浮出：**加载范围**。若"每人只加载自己的记忆"，任务记忆退化为个人日记（Bob 看不到 Alice 定的方案，必然重复劳动）；若全员全量合并，token 随人数线性膨胀且活跃者挤掉他人条目。本方案以分层加载回答（Q4）。

## 2. 现状事实（已核实）

- 写入方：`add_task_memory`（MCP 工具）、`append_task_memories_direct`（蒸馏 memories 直写，ADR-0002），均走 `_append_memory_atomic`，落 `_memories_path` 单文件。
- 读取方：`get_task` / `get_task_context` → `_load_memories_limited`，单文件 read + `_split_memories` 切条 + 截断。
- 压缩：`compact_task_memories` 两段式，重写主文件为"早期记忆（摘要）+ 近期条目"，原文 append 到 `memories-archive.md`。
- 可复用蓝本：telemetry 的 `user_id()`（`src/config.py`：`CODEWIKI_USER` > git user.name > 登录名 > `local`，明确声明"命名空间不是鉴权"）与 `_iter_user_files` 多文件 fold 聚合模式，已在 `.meta/telemetry/*.jsonl` 生产运行。

### 2.1 竞品佐证（2026-08-25 补充调研）

对本仓既有调研文档（TAM / teamai-cli / OpenViking / CBM 等 7 份）就四个悬决问题的横向核实：

- **TencentDB Agent Memory**：加载不走"自己 vs 共享"二选一，而是**作用域路由**——ACL 过滤 → 固定绑定层 + 浮动召回层 → Token 预算装配 Memory Pack；L2/L3 巩固刻意去 userId（团队共享）、由系统后台管线互斥执行。启示：作用域过滤 + 分层渐进披露。
- **teamai-cli**：知识库刻意不分命名空间（全员共读），遥测数据严格 per-user 文件（`sessions/<user>/`、"每人只写自己的 `<user>.yaml`"）。启示：**读共享、写分片**——与 telemetry→memories 路线同构的先例。
- **OpenViking**：每个记忆单元写时生成 L0（~100 token 摘要头），注入超预算的条目**降级为 URI + score**（不丢线索只降信息量）。启示：分层加载的工程化模板。
- TAM/teamai 的巩固均无"作者归属权"（系统管线/全局信号驱动）——但它们是中心化服务有锁可用；git 文件级世界的等价物是"文件所有权即锁"（Q6 的裁决依据）。

## 3. 设计决策（2026-08-25 grilling 定案）

| # | 决策 | 备选与否决理由 |
|---|------|------|
| Q1 | 采纳 telemetry 模式：每人只写自己的文件，git 走文件级新增/追加 | 时间戳+session 分片（键冗余、无归属）；union driver 单用（救不了 JSON 与压缩重写）；流程约束拆子任务（降概率不消除） |
| Q2 | user_id 复用 `config.user_id()`；默认链改为 `CODEWIKI_USER` > **git user.email** > git user.name > 登录名 | email 全局唯一且几乎人人配置，一行代码消除最大碎片源（telemetry 目录实测同人三个文件：Administrator/mambo-wang/local）；不设强制警告，保持"命名空间不是鉴权"轻量定位 |
| Q3 | 存储：`memories/<user_id>.md` + `memories-archive/<user_id>.md`；存量 `memories.md` 只读兼容不迁移 | 一次性迁入当前用户文件会伪造归属（blame 失真）且动历史 |
| Q4 | **分层加载**（hot/warm）：自己的文件全量（含摘要 + 最近 max_memories 条）；他人文件只注入摘要段（各 ≤2KB）+ 最近 2 条；他人层超预算时**降级为一行线索** | 纯"只加载自己的"（协作视野归零，任务粒度失去意义）；全局合并截断（活跃者挤掉他人全部近期条目）；依据 TAM 作用域路由 + OpenViking 渐进披露 |
| Q5 | 条目格式**不变**：头部仍是 `### YYYY-MM-DD HH:MM`，归属由文件名承载、渲染时注入 | 改头部格式会触碰 hook/解析边界（ADR-0001 的切条依据），收益仅是"单文件自含归属"，不值 |
| Q6 | 压缩**文件域 + 作者独占**：每人压自己的文件（各自的摘要段 + archive 文件），任何人永不动他人文件 | TAM/teamai 巩固均无作者权，但它们有分布式锁；git 世界的无中心互斥原语只有文件所有权。缺席者文件膨胀/摘要陈旧的代价低（他人层本就只是导航，深挖走 archive），不值得为低频场景拆承重墙 |
| Q7 | 同人多机残留冲突：`.gitattributes` 给 `memories/`、`memories-archive/` 声明 `merge=union`，加载端按时间戳排序吸收乱序 | 概率远低于跨人冲突，接受 union 后可能的重条，不做内容哈希去重（留作 P2 观察项） |
| Q8 | `.index.json` 改为**可重建生成物**：读侧校验失效/缺目录项时扫 `tasks/*/task.md` frontmatter 重建 | 手工解冲突不可规模化；仍保留文件本体作缓存，避免每次全目录扫描。CBM"单写者快照分发"路线不采纳（引入写者协调问题，比可重建贵） |
| Q9 | 分层参数：自己热层维持 20 条（单人场景零变化）；他人注入 2 条近期条目（TAM 固定绑定层启示——他人**最新动态**比摘要更能防重复劳动）；`get_task` 共用分层函数，默认 5 条且他人层只留摘要不注入条目 | 热层下调会破坏存量零回归；他人 0 条省的 token 不值得 |
| Q10 | **legacy `memories.md` 归热层**（按自己的文件全量加载，存量单人任务行为零变化）；首次压缩时保留条目与摘要并入发起者自己的文件、原文归档 `memories-archive/legacy.md`，从此归属明确 | 当他人层处理语义纯净，但"自己写了一年记忆的人升级后只看到 2 条"，违背前作立下的存量零回归验收基线 |
| Q11 | 他人 2 条近期条目按**纯时间戳**取最近，不引入热度信号 | teamai 的 promote 热度有 votes 数据兜底，任务记忆层无消费回路，热度只能是拍脑袋权重；时间戳是唯一诚实信号 |
| Q12 | 降级线索渲染为一行式：`- @alice 08-20：<条目首行截断> … → memories/alice.md` | 纯时间戳列表等于降级成噪音；OpenViking 原则是"不丢线索只降信息量"，首行截断是最小信息量 |
| Q13 | user_id 变更（改名/换邮箱）不提供 merge 工具：新身份=新文件，旧文件以他人层可见（信息不沉没），压缩归档后自然收敛 | Q2 改 email 链后变更源只剩显式改 `CODEWIKI_USER`，频率极低；merge 脚本是给假想用户写的假想需求 |
| Q14 | 多人正确性验收以**双用户 fixture 断言**为准（排序/截断/降级/legacy 标注逐项锁死），本仓 `CODEWIKI_USER=alice` E2E 为辅只验管线不炸 | "测试全绿实为 35 failed"教训：子代理口头报告不作数，断言必须落在 fixture 上 |

### 3.1 决策理由摘录

**Q1（telemetry 模式胜出）**：telemetry.py 模块 docstring 已写明该模式的全部要点——"每个用户只 append 自己的文件，聚合时 replay 全目录重建状态，git 天然走普通文件级流程"。任务记忆的写入形态（低频、append-only、消费者是 LLM）与遥测事件流同构，直接继承已验证的机制，比自创分片键便宜一个量级。

**Q4（分层加载）**：任务记忆的定位是"任务范围内的进度知识"，多人共做任务时接续的不只是自己的进度——Alice 上周定的方案和教训，Bob 开工时必须可见，否则任务记忆退化成个人工作日记。但全员全量随人数线性膨胀且全局排序截断会让活跃者挤掉他人条目。分层方案：协作视野保住（他人摘要 + 最新 2 条），token 随人数只按"每人 ≤2KB 摘要 + 2 条"线性增长且有硬上限，他人层降级分支把"永不超预算"变成硬保证。与调研共识同构——"存储格式不重要，加载策略才重要"，关键策略就是按归属分层。

**Q5（格式不变，归属外置）**：时间戳头是切条/截断/压缩三处共用的解析边界（前作 Q3、ADR-0001），动它牵连 hook 兼容与存量回退解析。归属信息文件名天然携带且渲染时可注入 `（@alice）`，单文件自含归属的唯一收益场景是"文件被单独拷走"，任务记忆不存在该场景。

**Q6（文件域压缩）**：本方案的核心不变量是"**每个用户只写自己的文件**"——压缩若做任务级统一摘要，发起者必然重写队友文件，不变量破裂，第 1 节三类冲突全部回归。竞品调研确认 TAM（分布式锁）和 teamai（中心化仓）的巩固都不需要文件所有权，但它们有锁；git 文件级世界的"锁"只能由文件所有权扮演。文件域压缩的代价是摘要按作者碎片化，但摘要本就是进度性内容的有损压缩，按作者分片反而保留"谁做了什么早期工作"的脉络；且压缩阈值按文件独立计算，单人长期任务不受队友文件体积拖累。压缩 prompt 可要求摘要"去个人化"（teamai promote 条款启示），提高陈旧摘要的复用性。

**Q8（index 可重建）**：`.index.json` 当前是 `_read_index`/`_write_index` 直读直写的唯一事实源。改为"目录扫描为准、index 为缓存"后，合并冲突的最坏结果是一次静默重建，与 telemetry 的"replay 全目录重建状态"哲学一致。不直接删掉 index 是因为 `list_tasks` 是高频路径，全目录 frontmatter 解析有成本。

## 4. 方案设计

### 4.1 存储布局（P0）

```
repowiki/tasks/<task_id>/
  task.md                      # 不变
  pending-memories.json        # 不变（会话级暂存，冲突概率低，暂不处理）
  memories.md                  # 存量只读兼容（热层，Q10）
  memories/<user_id>.md        # 新写入唯一路径
  memories-archive.md          # 存量归档只读
  memories-archive/<user_id>.md
```

`.gitattributes`（新增，仓库根）：

```
repowiki/tasks/*/memories/*.md merge=union
repowiki/tasks/*/memories-archive/*.md merge=union
```

### 4.2 身份与写入路径（P0）

`config.user_id()` 默认链改为 `CODEWIKI_USER` > git user.email > git user.name > 登录名（Q2）。**注意 user_id() 是 telemetry 共用函数**：改链后同人存量 telemetry 文件"换名"，但 telemetry fold 读全部 `*.jsonl`、旧文件仍被聚合，无损；任务记忆侧旧 per-user 文件转为该用户的新身份视角下的他人层，符合 Q13 的收敛语义。

`_append_memory_atomic` 的目标路径从 `_memories_path` 改为 `_memories_path_for(output_dir, task_id, user_id())`；`append_task_memories_direct` 同。原子写与串行化机制原样保留（防同机多进程）。`delete_task` 级联删除整目录，天然覆盖新布局。

### 4.3 分层加载路径（P0）

`_load_memories_limited` 改造为 hot/warm 两层（Q4/Q9/Q10/Q11/Q12）：

1. **身份与文件收集**：解析当前 `user_id()`；收集 `memories/*.md`（按文件名排序保证稳定序）+ legacy `memories.md`；
2. **热层（自己 + legacy）**：全部"早期记忆（摘要）"段 + 近期条目按时间戳排序取最近 max_memories 条（默认 20）——单人存量任务（只有 legacy 文件）输出与改造前逐字节等价；
3. **温层（每个他人文件）**：摘要段（标注 `（@user）`，各 ≤2KB）+ 按时间戳取最近 2 条条目（Q11，无热度加权）；
4. **温层预算降级**：他人条目注入会使总输出超出预算时，降级为一行线索：`- @alice 08-20：<条目首行截断> … → memories/alice.md`（Q12）；摘要段永不降级（它是他人层的最小信息单元）；降级次序为最新条目优先全量、逐条扣减预算（2048 字/作者独立），放不下的才降为线索；
5. **渲染顺序**：各摘要段（含 legacy）在前 → 自己热层条目 → 各他人温层条目（按作者文件名序、作者内按时间倒序）；
6. **元数据**：`memories_total` = 各文件条目数之和（摘要段不计）；`memories_truncated` 语义不变（热层截断时置位）；温层条目不计入截断计数。

`get_task` 共用同一分层函数（Q9）：热层取最近 5 条，他人层**只注入摘要、不注入条目**。时间戳排序键复用现有解析（`### YYYY-MM-DD HH:MM`）；legacy 无头条目时间为 null，稳定排末尾（与现状回退解析行为一致）。

### 4.4 压缩路径（P0，必须与存储改造同批）

`compact_task_memories` 两段式协议不变，`mode="prepare"` 返回**逐文件**的待压清单（每文件各自的 existing_summary 与条目数），`mode="submit"` 校验后逐文件执行：归档进 `memories-archive/<该文件归属>.md` → 重写该文件为"摘要 + 保留条目"。压缩范围仅发起者**自己的文件 + legacy 文件**（Q6 不变量：永不动他人 per-user 文件）；legacy 压缩时保留条目与摘要并入发起者自己的文件、原文归档 `memories-archive/legacy.md`（Q10），存量文件自此收敛、归属明确。压缩 prompt 要求摘要去个人化措辞。

### 4.5 index 可重建（P1）

`_read_index` 增加**校验+重建**：目录下存在 `tasks/<id>/task.md` 而 index 缺项，或 index JSON 解析失败时，扫描全部 task.md frontmatter 重建并回写。`create_task` / `complete_task` / `delete_task` 写路径不变。合并冲突（双方各自加任务）的最坏结果是下次读取时触发重建，两人建的任务都保留。

## 5. 影响面与同步义务

- `task_manager.py`：docstring 存储布局说明、写入/加载/压缩三个 handler；`src/config.py`：user_id 默认链。
- **三副本教训适用**：`prompts.py` 的 `_TASK_MEMORY_AGENTS_SECTION` 模板与仓库 `AGENTS.md` 中"存储：`repowiki/tasks/.index.json` + `<task_id>/task.md` + `<task_id>/memories.md`…"一行必须同步改，否则下次 install-hooks upsert 回滚滞后模板。
- `.gitattributes` 新增（仓库根，进 git）。
- 前作文档《任务记忆存储与加载扩展性设计方案》§1 布局描述加互引注记。
- 测试：tests/ 白名单问题仍在——新增测试文件须 `git add -f`（`test_task_manager.py` 本身未被 git 跟踪，扩展它同样需要）。

## 6. 测试计划

**双用户 fixture（验收主体，Q14）**：构造 alice/bob 各有"摘要 + 多条带时间戳条目"的文件 + legacy 文件，逐项断言：热层含自己全部摘要与最近 20 条；温层含两份摘要 + bob 最近 2 条；降级分支触发时输出线索行格式；legacy 归热层不进温层；`memories_total`/`memories_truncated` 计数正确；null 时间戳 legacy 条目排末尾。单元另测：union 乱序注入后加载端排序收敛；文件域压缩各文件独立成摘要、legacy 并入发起者文件；user_id 换名后旧文件以他人层可见（Q13）；index 重建幂等。**E2E（辅助）**：本仓 `repowiki/tasks/` 真实数据上 `CODEWIKI_USER=alice` 跑一轮追加+压缩+加载，对存量任务回归（legacy 路径渲染不炸）。**验收口径**：存量单用户任务 `get_task_context` 输出与改造前偏差 <5%（理想为逐字节等价）。

## 7. 分期

- **P0**：分片存储 + 分层加载 + 文件域压缩 + user_id 链改造 + union driver + legacy 兼容（一个不可拆的原子批次——存储/加载/压缩三处任一不同步都会破坏不变量或炸加载）。
- **P1**：`.index.json` 可重建。
- **P2（观察项，暂不做）**：同人多机 union 重条的内容哈希去重；`pending-memories.json` 分片（当前冲突场景未出现）。
