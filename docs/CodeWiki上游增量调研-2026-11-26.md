# CodeWiki 上游增量调研：自上次合并后值得借鉴的机制

> 调研日期：2026-11-26
> 上游：`FSoft-AI4Code/CodeWiki`
> 对比范围：`050dd263c211fee36fd34eb45790cf0a8eab77ee..f07bb460b737c060745bf69514ee8302750e28ee`
> 本地基线：`develop@7cd5740`；下文本地路径默认以 `codewiki/` 为根。
> 结论：**不建议整仓 merge；优先移植小体积 correctness 修复，再把上游 updater 的确定性机制补进本地 MCP 增量链路。**

## 一、结论先行

上游这段增量有 191 个提交、256 个文件、约 4.5 万行新增 / 3.6 万行删除。数量很大，但多数集中在两条本地已经分叉的路线：

1. 上游 legacy CLI / 内置 LLM backend / Web 交付链；
2. 上游组件级增量 updater 与其内部 agent 编排。

本地当前主线是 **MCP 工具 + 宿主 Agent 执行 + 文件态 job/change_plan**。因此不能把“上游新增”直接等同于“本地该补”。

建议按以下顺序借鉴：

| 优先级 | 候选 | 处置 | 理由 |
|---|---|---|---|
| P0 | parse timeout 异常基类 | 借鉴 | 一个继承关系修复，避免分析器吞掉超时导致单文件永久卡住 |
| P0 | 构造器纳入组件 + C/C++ declarator 修复 | 借鉴 | 直接修复函数漏识别、调用边丢失，改动局部、收益确定 |
| P0 | Git 子进程脱离 stdin + Mermaid daemon thread | 借鉴 | 修复 MCP stdio 被 Git 抢占、远程 Mermaid 校验挂住进程退出 |
| P1 | nested Git checkout 边界过滤 | 借鉴 | 防止未声明的嵌套仓库污染文件树、gitignore 与索引 |
| P1 | 反向引用索引 + stale 候选清单 | 借鉴并适配 | 本地有 `lint_wiki(stale_refs)`，但缺少“哪些页面引用了变更组件”的增量反向索引 |
| P1 | tree repair + 写入边界 | 借鉴并适配 | 本地已有 change_plan，但没有上游那种按图 diff 修复模块树、限制只能写计划页的硬边界 |
| P1 | 最小模块体积 + 完整文件归属 | 借鉴并适配 | 避免微页、漏文件；本地 MCP 聚类由宿主 Agent 完成，应落成确定性校验而非再造一个 LLM 聚类器 |
| P1/P2 | LLM 调用成本台账 | 条件借鉴 | 只覆盖 CodeWiki 自己发起的 LLM 调用；宿主 Agent 的 token 成本必须由宿主回传 |
| P2 | Ruby / Rust / Scala / Dart / Go / Vue / Zig / Lean | 按需求逐个移植 | 都是真增量，但整合成本差异大，不应一次引入八种 |
| P2 | artifact analyzer | 条件借鉴 | 对构建、CI、容器、部署文档价值大，但上游实现超过千行，需独立适配层 |
| 暂缓 | Google provider、TechDocs、Docker CLI、模型 flags、输出语言、prompt caching、聚类批缓存 | 暂缓 | 只在恢复 standalone/CI 生成路线，或有明确用户场景时优先 |
| 不借 | 删除 Web、整份依赖升级、`CAW@main` 可变依赖、整包覆盖 dependency_analyzer | 排除 | 与本地产品边界不一致，或会破坏本地独有能力 |

## 三、P0：应该优先移植的正确性与稳定性修复

### 3.1 parse timeout 不应被分析器吞掉

上游 [`1a7d690`](https://github.com/FSoft-AI4Code/CodeWiki/commit/1a7d690aa65d4e5f8dea4b3f7227ab4fcd2cf967) 将自定义 `TimeoutError` 从 `Exception` 改为 `BaseException`。原因很具体：语言分析器内部大量 `except Exception`，SIGALRM 触发的超时一旦先被这些块吞掉，一次性 alarm 已经用掉，后续解析就没有超时保护。

本地现状：

- `codewiki/src/be/dependency_analyzer/analysis/call_graph_analyzer.py:36-39` 仍继承 `Exception`；
- `:267-310` 的分派层已经分别捕获 `TimeoutError` 与普通 `Exception`；
- 本地已有 Windows / 非主线程跳过 SIGALRM 的保护，这一点比上游完整，不能覆盖掉。

建议只改异常基类并补回归测试：构造一个分析器内部会吞 `Exception` 的慢路径，断言超时仍能在分派层被捕获、后续文件继续分析。不要引入更重的线程超时方案。

### 3.2 构造器也是组件

上游 [`9674413`](https://github.com/FSoft-AI4Code/CodeWiki/commit/9674413be35c4829b080f396d81722444cd658f8) 让 JS/TS/Ruby/Java/C#/Kotlin/Dart 的构造器进入组件图。构造器经常承载主要初始化逻辑；不纳入组件时，构造器内部的调用边也会被丢弃。

本地仍明确排除：

- JavaScript：`analyzers/javascript.py:193-195`；
- TypeScript：`analyzers/typescript.py:611-617`；
- Java 等语言尚未完整覆盖构造器语义。

这项应按语言逐个改，保留本地既有 Node ID 规则。验收不能只数节点，还要验证构造器内部调用以构造器为 caller 出现在 `call_relationships` 中。

### 3.3 C/C++ 指针、引用与函数指针返回类型

上游 [`4aaf139`](https://github.com/FSoft-AI4Code/CodeWiki/commit/4aaf139444eeee458ea0f3ca7eeeb1e806b4bcc7) 新增共享 `c_declarators.py`，沿 `pointer_declarator` / `reference_declarator` / `parenthesized_declarator` 等包装层找到真正的 `function_declarator`；[`8d6a56c`](https://github.com/FSoft-AI4Code/CodeWiki/commit/8d6a56c) 又补了 export macro + typedef 返回类型的函数名识别。

本地 `analyzers/c.py:74-81` 仍只找直接子节点中的 `function_declarator`，所以 `const char *f()`、`T &f()`、函数指针返回类型都会漏掉整个函数。

建议直接借共享 helper 的结构，但不要整文件覆盖 C/C++ analyzer；本地还有自己的外部符号、路由与增量逻辑。回归样例至少覆盖：

- 一级 / 二级指针返回；
- C++ 引用返回；
- 函数指针返回；
- `API lua_Integer f()` 这类 export macro；
- 类内方法、命名空间限定函数。

### 3.4 Git 子进程不要继承 MCP stdio

上游 [`68cde6c`](https://github.com/FSoft-AI4Code/CodeWiki/commit/68cde6c1dfbc64ad768ffd5bc79a7266f95b6d52) 给剩余 clone/config/checkout 子进程补 `stdin=subprocess.DEVNULL`。本地 `analysis/cloning.py:84-112` 的 config/clone 还没有该参数。

MCP server 的 stdin 是 JSON-RPC 通道，Git 若等待认证或终端输入，可能直接破坏协议；交互终端下也可能挂住。建议全仓审计所有 `subprocess.run([... git ...])`，统一补 `DEVNULL`，而不是只修 clone 一处。

### 3.5 Mermaid 远程校验不能阻塞解释器退出

上游 [`fd43f9c`](https://github.com/FSoft-AI4Code/CodeWiki/commit/fd43f9c6bcb5f8174a538676b4ced0a6a5feceec) 用 daemon thread 替代 `asyncio.to_thread`。`mermaid-py` 内部请求没有超时；`asyncio.wait_for(15s)` 只能停止等待，不能停止那个工作线程，解释器退出时仍会 join，上游实际案例因此卡了约 13 小时。

本地 `src/be/utils.py:361-364` 仍是 `asyncio.to_thread`。建议：

1. 借 daemon-thread helper；
2. 保留本地 15 秒超时与 broken latch；
3. 验证 `valid / invalid / unavailable` 三态，unavailable 不应被当作“图一定有效”；
4. 增加“远端请求永久挂起，主任务超时后进程仍能退出”的测试。

### 3.6 跳过未声明的嵌套 Git checkout

上游 [`090d3ef`](https://github.com/FSoft-AI4Code/CodeWiki/commit/090d3efb5dda4d7387a3cd107c5564452e1ebd86) 新增 `RepositoryBoundaryFilter`：保留 `.gitmodules` 声明的子模块，跳过其他嵌套 `.git`。同时让 gitignore fallback 遍历也遵守该边界。

本地 `analysis/repo_analyzer.py:214-269` 只拒 symlink 和逃逸路径，仍会递归进嵌套 checkout。对 monorepo、本地试验仓、嵌套 worktree 容易污染：

- 文件树与总规模；
- gitignore 规则归属；
- 组件索引与变更检测；
- 生成文档的模块边界。

建议先独立移植边界 filter，测试正常子模块仍纳入、未声明嵌套仓跳过、`.gitmodules` 路径逃逸被拒。

## 四、P1：补强本地 MCP 增量链路，而不是替换它

### 4.1 本地已经有什么

本地不是“没有增量”：

- `analyze_repo` 有 SQLite 缓存与未变更文件跳过：`mcp/tools/analysis.py:119-163`；
- ADR-0020 已有 `.meta/job.json` 页面级续跑；
- `.meta/change_plan.json` 已有 `add_subtree / replan_subtree / delete_subtree / update_page`；
- `write_doc_file` / `edit_doc_file` 落页时结算算子；
- `module_tree.py:90-107` 已校验未知 component ID 与未分配 component；
- `wiki_lint.py:311-380` 已有 stale refs / broken links。

参见 `docs/adr/0020-update-path-operator-plan-and-job-state.md:21-46`。

所以上游 [`7bc15b7`](https://github.com/FSoft-AI4Code/CodeWiki/commit/7bc15b7) 的整套组件级 updater 不应直接替换本地实现。它的 4,337 行增量把图 diff、页面改写、LLM agent、成本记录和回滚都包在一起，与本地“工具做确定性簿记，LLM 改写留给宿主”的 Doctrine 相反。

### 4.2 反向引用索引：最值得抽的 updater 机制

上游 `updater/reference_index.py` 做三件事：

1. 从页面提取 Markdown 链接、component ID、代码片段中的唯一符号名；
2. 建立 `页面 -> 引用对象`；
3. 反转成 `被引用对象 -> 引用页面集合`。

这恰好补上本地增量更新的一个缺口：当前 change_plan 能知道“哪些模块页因源文件变更而过期”，但不能直接回答“还有哪些页面提到了被删除 / 改名的组件”。

建议适配方式：

- 复用本地 `wiki_lint` 的链接 / wikilink 解析语义，避免再造一套 Markdown 真源；
- 索引只存 `.meta` 下可重建缓存，不进知识语料；
- 在 `incremental-update` 的 prepare 结果中返回 `referencing_pages`；
- 最终仍由宿主 Agent 决定是否改写这些页面；
- 不自动改正文，不绕过现有 confirm / lint 闸门。

这是“把 LLM 从全库扫描里解放出来”的确定性优化，比照搬 updater 更符合本地架构。

### 4.3 ownership closure：变更组件没有模块 owner 时怎么办

上游 [`1436182`](https://github.com/FSoft-AI4Code/CodeWiki/commit/1436182) 的 `updater/ownership.py` 把 owner 从部分函数补成总函数：未进入 module tree 的变更组件，也按“同文件、同目录、邻居多数票、路由 agent”找到有效 owner。

本地 module tree 只跟踪部分 component，`module_tree.py:90-107` 会把未分配 component 作为 leftover 报告，但没有进一步归因。大仓库里，“组件确实变了，但不属于任何页面”会让增量漏掉它。

建议先借规则 1-3 的确定性部分，输出 `effective_owner_candidates` 供宿主确认；规则 4 的 LLM 路由不要内置到工具里。删除组件无法归属时，应明确列为 `unresolved_deletions`，不能静默忽略。

### 4.4 tree repair：把确定性修复从 Agent 手里收回工具

上游 `updater/tree_repair.py` 的处理顺序很清楚：

1. 重命名：原地替换 component ID；
2. 删除：移除 component，再剪空节点；
3. 新增：同文件 → 同目录单 leaf → 邻居多数票；
4. 剩余 orphan 才交给 routing agent；
5. 输出每一步决策与未放置清单；
6. leaf 增长超过阈值只标记，不直接触发 LLM 重聚类。

本地 change_plan 已覆盖“页面增删改”，但树结构修复主要依赖宿主 Agent。建议把 1-3、5 抽成纯函数，并入 `save_module_tree` 前的校验 / 修复阶段；4 保持显式候选，6 只返回 warning。

### 4.5 write guard：限制 Agent 只能写本轮计划页

上游 updater 的 `allowed_write_paths` 会限制每次 agent 只能改当前页面；本地 `doc_writer.py:209-233` 已防目录逃逸，但没有“本轮 change_plan 是否允许写这一页”的约束。

建议新增**默认 observe、可升级 enforce** 的计划写入门：

- 观察期：写计划外页面时返回 warning，仍允许；
- 明确不属于任何算子的页面：记录 `unplanned_write`；
- 强制期：仅允许 `pending_pages` 与当前 agent 的 target；
- 所有拒绝 / 降级都要可见，不能静默失败。

不要把路径安全校验换成 plan 校验，两者解决不同问题。

## 五、P1/P2：生成质量与成本

### 5.1 最小模块体积与完整文件归属

上游 [`15603f7`](https://github.com/FSoft-AI4Code/CodeWiki/commit/15603f7b396ae924bb2696871af2793f7be39677) 修正了聚类判据：

- 不再只数 leaf prompt token，而是按完整 scope 文件估算代码 token；
- leaf 覆盖不足时先补同文件代表，再决定是否聚类；
- 按完整文件分区，避免同文件组件被拆到互斥模块；
- 用 `ast.literal_eval` 替代 `eval`；
- LLM 返回结果再做 partition normalization 与覆盖率校验。

随后 [`b2d3d70`](https://github.com/FSoft-AI4Code/CodeWiki/commit/b2d3d7085a2cc0a3a0164647883824375fb9dd85) 增加最小模块 token 数，过小模块合并，无法形成两个有意义模块时保留整模块文档。

本地 MCP 聚类由宿主 Agent 完成，因此适合借的是**确定性 validator**，不是上游 LLM 聚类实现：

- `save_module_tree` 校验同文件组件是否跨模块；
- 返回微页、未覆盖文件、未知 ID；
- 给宿主 Agent 明确的修复建议；
- 先 observe，不自动重排，避免破坏人工模块设计。

### 5.2 大仓库 prompt 应传路径，不要内联全部子文档

上游 [`fac643f`](https://github.com/FSoft-AI4Code/CodeWiki/commit/fac643fdc6214b1f0a060e01cb03c7356ae00fa4) 把 overview prompt 从“内联子文档全文”改为传 `docs_path`；上游 wazuh 实测约 2.2M → 83K 字符。[`bbcac24`](https://github.com/FSoft-AI4Code/CodeWiki/commit/bbcac24ae6132167b8a588496775aaa46a2cce4f) 又加 900k 字符上限：先裁剪 module tree 到 names-only，再截断代码正文。

本地 legacy `documentation_generator.py:176-203` 仍把子文档全文放入 `child_info["docs"]`。但 MCP 主线本来就是让宿主 Agent 按 prompt 读代码、写页面，所以这项对 MCP 不是首要缺口。

仅在恢复 standalone / 无人值守生成时优先做。若做，必须保证 reader tool 可用，否则“传路径”会退化成信息缺失。

### 5.3 聚类批缓存不能只搬原子写

上游 `f93ceaf / cbd3bdb / 6275c13 / 3e59b85` 把聚类缓存做成了完整机制：

- 指纹包含 repo、provider/model、完整 prompt、节点集合；
- `fsync + replace` 原子写；
- 只缓存有效 LLM 结果，fallback 不污染缓存；
- 按 scope 失效；
- 返回 deepcopy，避免调用方改坏缓存。

本地没有等价的 LLM 聚类批缓存，只有通用 `atomic_write`。MCP 主线的聚类由宿主执行，工具侧没有这份缓存可搬；如果 standalone 路线恢复，应整套移植，而不是只加一个 JSON cache 文件。

### 5.4 LLM 调用成本台账是真缺口，但边界要划清

上游 [`e4ad1d9`](https://github.com/FSoft-AI4Code/CodeWiki/commit/e4ad1d9635e766f8802d354642cc2d7998d27e94) 新增 `UsageLedger`：

- 每次调用记录 phase / kind / target / model / seconds / tokens / cost；
- 线程安全，兼容嵌套 agent；
- 按 phase 汇总；
- 有 token 但无价格时列 `unpriced_models`，不把 `$0` 当免费；
- metadata 保留 usage，CLI 输出报告；
- 订阅模式明确标为 API-equivalent。

本地 `src/be/backend.py:37-66` 只有抽象接口，`cli/models/job.py:33-39` 只有累计 `total_tokens_used`，没有逐调用成本台账。

建议未来实现时：

1. 先覆盖 CodeWiki 自己发起的调用（Mode B、standalone backend）；
2. 复用现有 job / metadata，不新增第二套 run 真源；
3. pricing 可配置，未知价格必须显式 unknown；
4. 宿主 Agent 调用成本不能凭空推算，需宿主回传或标为 `external`；
5. 不要与本地检索 `est_tokens` 混为一谈：后者只是展开内容预算提示，不是账单。

## 六、新语言分析器：按仓库需求逐个引入

上游分析器相关增量约 1.2 万行以上。按 `dependency_analyzer/analyzers/`、`analysis/call_graph_analyzer.py` 与 `utils/grammars.py` 统计，共 24 文件、+12,332 / -2,162 行（不含测试）。这些主要是真功能，不是 README 扩表。但本地已有 10 种语言分析器，且保留了自己的跨服务路由、增量缓存、PageRank / transitive impact 等能力，不能整包覆盖。

| 语言 / 机制 | 上游增量 | 本地现状 | 建议 |
|---|---|---|---|
| Ruby | 类 / module / mixin / 调用与继承边 | 只识别 `.rb` 扩展名，无 analyzer 分派 | 有 Ruby 仓库时移植；成本中等 |
| Rust | trait / impl / macro 等结构 | 只识别 `.rs`，无 analyzer；不能算已支持 | 有 Rust 仓库时优先于 Lean；需 grammar wheel |
| Scala | case class / object / enum 等 | 只识别 `.scala`，无 analyzer | 按需求移植 |
| Dart / Flutter | import/part/export、library 隐私、widget/state/Bloc/Riverpod | 完全缺失 | 成本最高；需要 visible-scope resolver，适合独立项目 |
| Go package-aware | directory/package ID、go.mod/local replace、隐式 interface method-set | 已有基础 Tree-sitter Go 与本地 route extractor | 借 package index 思路，保留本地路由；不要直接替换 |
| Zig | 容器、泛型、`@import`、build.zig | 缺失 | 有 Zig 仓库时再做 |
| Vue SFC | script/template 切分，补模板组件边 | 缺失 | 对前端仓价值直接，成本中等 |
| Lean 4 | header scanner + Tree-sitter + 精确名称解析 | 缺失 | 专用性强，不作为通用默认能力 |

引入任何依赖 `tree-sitter-language-pack` 的语言前，先借上游 [`fdeb1b7`](https://github.com/FSoft-AI4Code/CodeWiki/commit/fdeb1b7) 的 grammar preflight：pack 1.x 首次加载要下载 grammar，离线环境必须在构建期预下载，否则 analyzer 的逐文件 `except` 会把下载失败吞成“该语言没有节点”。

## 七、条件借鉴与明确不做

### 7.1 artifact-aware generation

上游 [`2531801`](https://github.com/FSoft-AI4Code/CodeWiki/commit/2531801) 把 Make、CI、Docker、Compose、manifest、schema、脚本纳入依赖图，并补构建模块。对“代码 + 部署 + CI 一起文档化”很有价值，但上游 `analyzers/artifact.py` 本身超过千行，还涉及 Node 模型、leaf 规则、拓扑、prompt、配置等一片联动。

本地当前只有服务拓扑与组件图，没有 artifact 节点。建议只在部署密集 monorepo 的明确需求下做独立适配层：先抽取构建 / CI / 容器事实，不照搬整份 analyzer。

### 7.2 provider / CLI / 交付形态

以下都是上游真实增量，但默认不应进入本地 MCP 核心：

- Gemini API / Vertex ADC 原生 provider；
- 三个模型的逐次命令行覆盖；
- 多语言文档生成 `--language`；
- MkDocs / Backstage TechDocs 导出；
- Docker 从 Web 服务改成 CLI job 容器；
- prompt caching、订阅 provider 成本优化。

恢复条件分别是：确有 Gemini/Vertex 用户、确有 CI 参数化需求、确有多语言文档合同、确有 Backstage 发布、确有无人值守容器作业、确有支持缓存代理的 standalone 生成。没有这些触发条件时，它们会增加 provider 矩阵与维护面，不提升当前知识库/检索能力。

### 7.3 明确不借

1. **不整体删除 Web**。上游 PR #167 下线 Web，但本地 Docker 仍依赖 Web；这是产品退役决策，不是上游同步动作。
2. **不整份照搬依赖版本**。上游安全下限包含 protobuf、MCP、GitPython、aiohttp 等调整，但本地部分依赖已经更高。应基于本地依赖图与审计结果逐项升级，不能覆盖 lock。
3. **不采用 `CAW@main` 这类可变依赖**。可复现构建与供应链风险都不适合。
4. **不覆盖整个 `dependency_analyzer`**。本地独有的 cross-service routes、`skip_file_paths` 增量、reverse graph、PageRank / transitive impact、GitIgnoreFilter 不能被上游旧实现冲掉。
5. **不把上游 updater 的内部 LLM 编排搬进工具层**。本地 ADR-0020 已明确工具做确定性簿记，编排归宿主 Agent。

## 八、建议的落地切片与验收

### 切片 A： correctness / stability（小 PR，优先）

- parse timeout 基类；
- JS/TS 构造器；
- C/C++ declarator helper；
- Git subprocess `DEVNULL`；
- Mermaid daemon thread；
- nested Git boundary filter。

验收：单测覆盖异常吞噬、构造器调用边、复杂 C/C++ 声明、stdio 不被 Git 读取、Mermaid 挂起可退出、子模块与嵌套 checkout 边界。

### 切片 B： MCP 增量可解释性（中 PR）

- 可重建的 reference index；
- `changes.referencing_pages` / `unresolved_deletions`；
- ownership 规则 1-3 候选；
- tree repair 纯函数；
- 计划外写入 observe warning。

验收：同输入产生相同清单；索引删除后可重建；renamed/deleted 组件能找到引用页；未归属组件不会静默消失；观察期不改变既有写入行为。

### 切片 C： 聚类质量 validator（中 PR）

- 完整文件 token 估算；
- 同文件组件跨模块检查；
- 微页与未覆盖文件报告；
- 默认 observe。

验收：构造微页、重复文件归属、漏文件三类坏树，工具均给出确定性诊断；不自动改树，不调用 LLM。

### 切片 D： 成本与语言（按需求单独立项）

- CodeWiki 自有 LLM 调用 ledger；
- 逐个语言 analyzer；
- artifact facts；
- standalone provider / TechDocs / Docker。

验收：unknown pricing 不显示为零；外部宿主成本标为 external；新语言具备正反样例与离线 grammar 准备说明；artifact 不改变既有源码组件 ID。

## 十、最终建议

如果只做一件事：**先落 correctness / stability 小修，尤其是 timeout、构造器、C/C++、stdio、Mermaid 这五项。** 它们风险低、收益直接，不需要重新讨论产品架构。

如果准备继续加强增量更新：**借上游 reference index、ownership closure、tree repair、write guard 四个确定性机制，补到现有 job/change_plan 旁边，不要引入整套 updater。** 这条路线既保留本地 MCP 哲学，也能获得上游最有价值的工程闭环。
