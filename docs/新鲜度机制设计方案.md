# 新鲜度机制设计方案（Phase 5 · T7 专项）

> 从 Phase 5 拆解中独立出来的专项方案，只解决一个问题：**知识过期判定从"按天龄粗判"升级为"按验证状态精判"**。不涉及置信分层与负反馈闭环。
> 日期：2026-08-21 · 状态：待评审 · 预计工作量：**2–3 人日**
> 修订记录：v2（2026-08-21）——按评审意见去掉 `valid_to` 显式有效期字段，只保留激活的 `stale_after` + 类型感知窗口，实现零新增字段。

---

## 一、背景：两个真实问题

**问题 1：确认不生效（bug 级）。** `confirm_note` 会刷新 `stale_after`（knowledge_loop.py:563），但 `_check_stale_notes` 判定读的是 `metadata.date`（创建日期，wiki_lint.py:972）——`stale_after` 是个只写不读的字段。后果：**无论确认多少次，知识都从创建日起一路变老**，复核闸门在过期判定上形同虚设。

**问题 2：一刀切 90 天。** 所有类型笔记共用 90 天窗口，且 lint dispatch 根本没读配置（wiki_lint.py:1545 直接调默认值）——`conventions.default_stale_days` 只被 ingest/confirm 读取，lint 永远用硬编码 90/60。后果：临时 workaround 和长期架构决策用同一个保鲜期，要么误报、要么漏报。

---

## 二、新鲜度模型

核心转变：**"这条知识多老了" → "这条知识多久没被验证了"。**

字段设计（**零新增字段**，只激活一个现有字段）：

| 字段 | 状态 | 语义 |
|---|---|---|
| `stale_after` | 现有，**激活** | 滚动复核期限：ingest/confirm 按类型窗口写入，lint 真正读取并执行 |
| `verified[]` | 现有 | 验证审计轨迹（最新事件的 `at` 即最近验证时间，回填脚本的依据） |

**不引入 `valid_to`（显式有效期）**：评审决定不做。理由：① 它引入第二条期限语义（显式 vs 滚动）和"过期后必须显式续命"的额外治理规则，复杂度与收益不成比例；② 有期限的知识（如"有效期至 v3 迁移"）可以把期限写进正文与 `stale_after` 的窗口设置里，由复核动作兜底；③ 零新增字段意味着零 frontmatter 漂移风险。
**也不引入 `last_verified_at`**：可从 `verified[-1].at` 派生。frontmatter 写入点已有 5 个（3 个显式 + `_apply_status_to_file` / `_merge_okf_sources` 两个 yaml 重 dump），不加字段就不加风险。

**判定级联**（对每条 stable/confirmed 笔记）：

```
1. stale_after 已过  → warning「复核期已过」
   └─ 但 retrieval_defer 天内被检索过 → 顺延（保留现有活跃度豁免）
2. 否则              → fresh
```

严重度只设 warning：没有显式有效期后，超期都是**概率性提醒**（可能还有效，只是没人验证），不存在"确定性过期"，不设 error 级。

## 三、类型感知的新鲜窗口（取代一刀切 90 天）

`schema.yaml` 新增配置节：

```yaml
conventions:
  default_stale_days: 90        # 保留：freshness 未配置时的回退
  freshness:
    default_window_days: 180    # 全局默认窗口（从 90 放宽）
    retrieval_defer_days: 60    # 近期被检索则顺延复核（保留现有机制）
    by_type:                    # 类型感知窗口
      workaround: 45            # 临时方案天然短命
      known_issue: 60           # 已知问题通常随修复而失效
      general: 120
      pitfall: 180              # 坑的保质期较长
      lesson: 180
      bug_fix: 180
      decision: 365             # 决策长期有效，除非被新决策推翻
      architecture: 365         # 架构事实最长寿
```

窗口含义：**confirm 之后，这类知识在窗口内被视为新鲜；超窗后需要人来复核（confirm 续期或 reject 退役），而不是自动作废。** 窗口类型在 ingest/confirm 时按 note_type 查表（缺失类型回退 default_window_days，配置节整体缺失回退 default_stale_days——完全向后兼容）。

有明确期限的知识怎么办：把期限意图写进正文（如"有效期至 v3 迁移"），并让作者按期限选择确认节奏——workaround 类型 45 天的短窗口本身就是对"临时知识"的兜底提醒。

## 四、写入侧改动

- **`handle_ingest_note`**：`stale_after` 改用类型窗口计算（替换 knowledge_loop.py:413-417 的固定 90 天逻辑）。无新增参数。
- **`handle_confirm_note`**：`stale_after` 同样改用类型窗口（替换 :560-563）——confirm 即续期，这是修复问题 1 的关键动作。无新增参数。
- **共享 helper**：`freshness_window_days(note_type, schema)` 放 knowledge_loop.py，ingest/confirm/lint/回填脚本四处共用，窗口语义单点定义。
- **写入点盘点**（5-writer 约束核对）：零新增字段 → 零新增写入点；`_apply_status_to_file` 的 yaml 重 dump 本来就会刷新 stale_after，行为不变。
- **hook 安全性**：`.codebuddy/hooks/task_session_start.py` 是 stdlib-only 行扫描，但只扫 `conv-*.md` 的 `status:` / `task_id:`；本方案只改 notes/ 的 frontmatter 写入逻辑，不触碰 raw 文件，零影响。

## 五、lint 升级（`_check_stale_notes` 重写）

- 读取 `conventions.freshness` 配置（回退链：freshness → default_stale_days → 硬编码 90/60），修复 dispatch 不读配置的问题；
- 按第二节判定级联实现：判定基准从 `metadata.date` 天龄换成 `stale_after` 是否已过，保留 retrieval_defer 活跃度豁免；
- suggestion 文案：「复核期已过（stale_after=<日期>）。确认内容仍然准确用 confirm_note 续期，已过时用 reject_note 退役。」
- **检查名保持 `stale_notes`**：不新增检查项，registry 的 checks 枚举无需同步，存量调用不受影响；
- 检查范围：本期只做 notes/（scenarios/doctrine 有各自的聚合/刷新机制驱动更新，后续再议）。

## 六、配套小项

- **wiki_stats 新鲜度分布**：新增 `freshness: {due, fresh}` 计数（复用 lint 的判定函数，避免两套逻辑），作为健康度指标。
- **存量回填**：`scripts/migrate_freshness.py`（幂等一次性脚本）：对每条 stable 笔记，`stale_after = max(现值, verified[-1].at + 类型窗口)`——让历史确认在新机制下生效；无 verified 事件的笔记保持现值。同时输出统计（多少条被续期、多少条仍超期）供批量复核排期。
- **告警风暴缓解**：切换后会有大量存量笔记 stale_after 已过期（它们过去从未被真正判定过）。预案：先跑回填脚本，再对仍超期的用 batch_set_status 批量组织复核，不一次性倾倒。

## 七、任务拆解与验收

| 任务 | 内容 | 改动文件 | 工作量 |
|---|---|---|---|
| **F1 lint 判定升级 + 配置接线** | freshness 配置读取与回退链；判定基准换成 stale_after + 检索顺延；suggestion 文案 | wiki_lint.py | 0.5–1 日 |
| **F2 写入侧类型窗口** | `freshness_window_days` 共享 helper；ingest/confirm 两处 stale_after 计算替换；schema.yaml 模板加 freshness 配置节 | knowledge_loop.py、schema.yaml | 0.5 日 |
| **F3 回填 + 统计 + 测试** | migrate_freshness.py（幂等）；wiki_stats freshness 分布；测试矩阵 | scripts/、knowledge_loop.py、tests/ | 1–1.5 日 |

**依赖**：F1 ← F2 共享类型窗口 helper（先写 helper 再两边接）；F3 在 F1/F2 之后。

**验收标准**：
- stale_after 超期 → warning；retrieval_defer 内被检索 → 顺延不报
- confirm_note 后 stale_after 按类型窗口刷新，**确认过的旧笔记不再被判 stale**（修复问题 1）
- 类型窗口生效：workaround 45 天 vs decision 365 天（可配、可回退到 default_stale_days）
- lint dispatch 读取 schema 配置（改 schema 能影响判定结果）
- 回填脚本幂等（跑两次结果一致），历史 verified 事件转化为新鲜度
- 全量测试保持全绿（当前基线 119）+ 新增 tests/test_freshness.py 覆盖上述矩阵

**风险**：唯一触碰存量数据的操作是回填脚本——先分支执行 + 全量测试 + lint 三重验证再合入；窗口默认值（180/45/365 等）是拍脑袋初值，上线后按误报/漏报率校准，配置化已留好调整通道。
