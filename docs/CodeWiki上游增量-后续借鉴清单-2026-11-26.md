# CodeWiki 上游增量后续借鉴清单

> 整理日期：2026-11-26
> 状态：backlog，尚未立项
> 依据：[CodeWiki 上游增量调研](CodeWiki上游增量调研-2026-11-26.md)
> 已落地基线：`a546780`（六项 correctness/stability 薄适配）
> 适用范围：CodeWiki-Plus 的 MCP 工具 + 宿主 Agent + 文件态 `job/change_plan` 主线

## 一、结论

首批六项 correctness/stability 修复已经完成，不再列入本清单。剩余值得借鉴的内容分成三层：

1. **P1：补强 MCP 增量链路**——反向引用、ownership、tree repair、write guard、聚类 validator；
2. **P2：按明确需求引入**——调用成本台账、语言分析器、artifact facts；
3. **条件项：仅在 standalone/CI 路线恢复后考虑**——大 prompt 路径化、聚类批缓存、provider/CLI/交付形态扩展。

建议的前三个落地切片依次是：**B1 反向引用索引 → B2 ownership + tree repair → B3 write guard + 聚类 validator**；之后再考虑 UsageLedger 与语言/artifact。

这些项目共享同一条边界：工具做确定性簿记、校验与修复；LLM 正文改写、聚类与路由仍由宿主 Agent 完成。默认 observe 的修复只输出计划/候选，不自动改正文或模块树；不绕过 confirm/lint 闸门。

已落地、不再列入 backlog 的六项：

| 项目 | 已落地内容 |
|---|---|
| parse timeout | 自定义 `TimeoutError` 继承 `BaseException` |
| JS/TS constructor | constructor 进入组件图并保留调用边 |
| C/C++ declarator | 共享 helper 处理指针、引用、函数指针返回与冗余括号 |
| Git stdin | 11 个产品调用点补 `subprocess.DEVNULL` |
| Mermaid | daemon thread + `valid/invalid/unavailable` 三态 |
| nested Git | 根 `.gitmodules` 边界过滤，文件树与 fallback gitignore 同边界 |

## 二、P1：MCP 增量链路

| ID | 机制 | 核心价值 | 触发条件 | 建议优先级 |
|---|---|---|---|---|
| B1 | 反向引用索引 | 回答“哪些页面引用了被删除/改名的组件” | 增量更新出现 rename/delete，或宿主需要缩小改写范围 | 最高 |
| B2 | ownership closure | 变更组件没有模块 owner 时给出确定性候选 | module tree 有 leftover/unassigned component | 高 |
| B3 | tree repair 纯函数 | 把重命名、删除、简单新增的树修复收回工具 | 模块树与组件图发生确定性漂移 | 高 |
| B4 | 计划写入门禁 | 限制 Agent 只能写本轮计划页，并暴露计划外写入 | change_plan 页面较多或需要强约束执行 | 中 |
| B5 | 聚类质量 validator | 诊断微页、漏文件、同文件跨模块 | 宿主完成聚类后、保存 module tree 前 | 中 |

### B1：反向引用索引

**要解决的问题**

当前 change_plan 能知道哪些模块页因源文件变更而过期，但不能直接回答“还有哪些页面提到了被删除或改名的组件”。宿主 Agent 往往需要全库扫描 Markdown。

**薄适配方案**

- 从页面提取 Markdown 链接、wikilink、component ID、代码块中的唯一符号名；
- 复用 `wiki_lint` 的链接/wikilink 解析语义，不另造 Markdown 真源；
- 建立可重建的 `页面 -> 引用对象` 与 `被引用对象 -> 引用页面` 索引；
- 索引只放 `.meta` 下，删除后可全量重建，不进知识语料；
- 在 `incremental-update` prepare 结果中返回 `referencing_pages`；
- 宿主 Agent 决定是否改写，工具不自动编辑正文。

**验收**

- 同一输入产生相同引用页清单；
- renamed/deleted component 能找到所有引用页；
- 索引删除后可从现有页面完整重建；
- 不改变现有 confirm/lint 行为。

**明确不做**

不搬上游整套组件 updater，不把索引作为第二份页面真源，不自动修复正文。

### B2：ownership closure

**要解决的问题**

module tree 只跟踪部分 component。大仓库中可能出现“组件确实变了，但不属于任何模块页”，当前只会作为 leftover 报告，增量链路可能漏掉它。

**薄适配方案**

先实现三条确定性规则：

1. 同文件已有组件继承 owner；
2. 同目录多数 owner 作为候选；
3. 邻居模块多数票作为候选。

输出 `effective_owner_candidates` 供宿主确认。删除组件无法归属时显式进入 `unresolved_deletions`，不得静默忽略。

多数票平局时保留全部并列候选，按 component ID 排序；没有多数时不指定唯一 owner，转入 unresolved。阈值与邻居范围在立项时用目标仓库实测标定，不在工具里预造脱离数据的常量。

**验收**

- 同文件、同目录、邻居多数票三类样例得到稳定候选；
- 未分配 component 不会从 changes 中消失；
- 无法归属的删除项明确列出；
- 同输入产生相同候选顺序。

**明确不做**

不把上游第 4 条 LLM routing agent 内置进工具；不自动把候选写成最终 owner。

### B3：tree repair 纯函数

**要解决的问题**

当前 change_plan 已覆盖页面增删改，但模块树结构修复主要依赖宿主 Agent。确定性规则应由工具完成，避免不同 Agent 给出不同结果。

**薄适配方案**

按顺序实现纯函数：

1. rename：原地替换 component ID；
2. delete：移除 component，并剪掉空节点；
3. add：同文件 → 同目录单 leaf → 邻居多数票；
4. 剩余 orphan 只输出候选，不调用 LLM；
5. 输出每一步决策与未放置清单；
6. leaf 超过阈值只返回 warning，不触发自动重聚类。

可并入 `save_module_tree` 前的校验/修复阶段。observe 模式只返回 repair plan 和候选，不直接改树；显式 apply 模式才执行纯函数修复。

**验收**

- rename/delete/add 三类输入得到确定性修复结果；
- orphan 与超阈值 leaf 均有显式输出；
- 观察期不改变既有模块树；
- 修复过程不调用 LLM。

**明确不做**

不在工具内调用 LLM 重聚类，不默认执行 apply，不静默丢弃 orphan。

### B4：计划写入门禁

**要解决的问题**

`doc_writer` 已防目录逃逸，但不知道“这一页是否属于本轮 change_plan”。Agent 可能改写计划外页面，扩大影响范围且难以审计。

**薄适配方案**

采用“默认 observe、可升级 enforce”的计划写入门：

- observe：计划外写入返回 warning，仍允许；
- 明确不属于任何算子的页面记录 `unplanned_write`；
- enforce：仅允许 `pending_pages` 与当前 Agent target；
- 所有拒绝/降级都可见，不静默失败。

**验收**

- observe 模式保持既有写入行为；
- enforce 模式拒绝计划外页面并返回明确原因；
- 路径逃逸仍由原安全校验拦截；
- 计划内写入不受影响。

**明确不做**

不用 plan 校验替换目录逃逸校验；两者解决不同问题。

### B5：聚类质量 validator

**要解决的问题**

MCP 聚类由宿主 Agent 完成，工具侧缺少确定性质量诊断。微页、漏文件、同文件组件跨模块等问题只能在人工审查时发现。

**薄适配方案**

- 按完整 scope 文件估算代码 token，而不是只数 leaf prompt token；
- 检查同一文件组件是否被拆到互斥模块；
- 返回微页、未覆盖文件、未知 component ID；
- 给出宿主可执行的修复建议；
- 默认 observe，不自动重排模块树。

**验收**

- 构造微页、重复文件归属、漏文件三类坏树，工具均能诊断；
- validator 不调用 LLM；
- 不自动修改 module tree；
- 诊断结果可由测试稳定复现。

## 三、P2：成本、语言与 artifact

### C1：CodeWiki 自有 LLM 调用成本台账

**适用条件**

恢复或扩展 Mode B、standalone backend 等由 CodeWiki 自己发起 LLM 调用的路线。MCP 主线中宿主 Agent 的调用成本不能由工具凭空推算。

**薄适配方案**

- 复用现有 job/metadata，不新增第二套 run 真源；
- 每次调用记录 phase、kind、target、model、seconds、tokens、cost；
- pricing 可配置；未知价格显式标为 unknown，不显示为 `$0`；
- 宿主 Agent 成本标为 `external`，等待宿主回传；
- 不与检索 `est_tokens` 混为一谈，后者只是内容预算提示。

**验收**

- unknown pricing 不显示为零；
- 外部宿主成本不会混入 CodeWiki 自有调用账单；
- 线程安全并支持嵌套 agent；
- 按 phase 汇总与逐调用明细一致。

**明确不做**

不推算宿主 Agent 成本，不把 `est_tokens` 当账单，不为未知价格填零。

### C2：语言分析器按需求逐个引入

下表是初排，实际顺序按目标仓库语言占比与 grammar 准备成本复核；“成本最高”指相对整合成本，不是通用性能结论。

| 语言/机制 | 建议顺序 | 触发条件 | 边界 |
|---|---:|---|---|
| Rust | 1 | 仓库有实质 Rust 代码 | 优先于 Lean；需 grammar wheel 与离线预下载 |
| Ruby | 2 | Ruby 仓库 | 补类/module/mixin/调用与继承边 |
| Vue SFC | 3 | 前端仓库 | 切分 script/template，补模板组件边 |
| Go package-aware | 4 | Go monorepo/多 module | 借 package index 思路，保留本地 route extractor |
| Scala | 5 | Scala 仓库 | case class/object/enum 等结构 |
| Dart/Flutter | 6 | 明确 Flutter 需求 | 成本最高，需 visible-scope resolver，独立项目 |
| Zig | 7 | Zig 仓库 | 容器、泛型、`@import`、build.zig |
| Lean 4 | 8 | 专用 Lean 仓库 | header scanner + Tree-sitter + 精确名称解析 |

**共同验收**

- 正反样例覆盖核心语法与调用边；
- 不替换或删除本地已有跨服务路由、增量缓存、PageRank/transitive impact；
- 使用 `tree-sitter-language-pack` 前先实现 grammar preflight；
- 离线环境在构建期预下载 grammar，不能把下载失败吞成“该语言没有节点”；
- 每个语言独立测试、独立回退，不一次引入八种。

**明确不做**

不整包覆盖 `dependency_analyzer`，不把 grammar 下载失败降级为空节点，不为扩表一次性引入全部语言。

### C3：artifact facts 独立适配层

**适用条件**

部署密集 monorepo，需要把 Make、CI、Docker、Compose、manifest、schema、脚本与源码一起文档化。

**薄适配方案**

先抽取构建、CI、容器与部署事实，建立轻量 artifact 节点或事实表；不照搬上游超过千行的 `analyzers/artifact.py`，也不改变既有源码 component ID。

**验收**

- 构建/CI/容器事实可追溯；
- 不破坏既有源码组件图与 ID；
- artifact 缺失不阻断源码分析；
- 由独立测试覆盖解析失败与部分可用场景。

**明确不做**

不照搬上游整份 artifact analyzer，不让 artifact 节点重写既有源码 component ID。

## 四、条件项：恢复 standalone/CI 路线后再评估

| 机制 | 恢复条件 | 暂缓原因 |
|---|---|---|
| 大仓库 prompt 路径化 + 体积上限 | standalone/无人值守生成恢复 | MCP 主线由宿主按 prompt 读代码，不是当前缺口 |
| 聚类批缓存 | 上游 LLM 聚类实现被采用 | 本地聚类由宿主执行，单独搬原子写没有意义 |
| Gemini/Vertex provider | 明确用户需求 | 增加 provider 矩阵，不提升当前知识平台能力 |
| 逐模型 CLI flags | CI 参数化需求 | 当前 MCP 主线不需要 |
| 多语言文档 `--language` | 多语言文档合同 | 需要完整输出语言约束 |
| MkDocs/Backstage TechDocs | 明确发布目标 | 属交付形态扩展 |
| Docker CLI job | 无人值守容器作业 | 与当前 Web/MCP 产品边界不同 |
| prompt caching | 支持缓存代理的 standalone 生成 | 依赖具体 provider/代理能力 |

## 五、建议落地切片

### 切片 B1：反向引用索引

- 先做索引构建与重建；
- 再接入 `incremental-update` prepare；
- 最后补 renamed/deleted 引用页回归。

### 切片 B2：ownership + tree repair

- 先实现确定性候选与纯函数；
- 以 observe 模式接入；
- 宿主确认候选后再决定是否自动修复。

### 切片 B3：write guard + 聚类 validator

- 两类机制都先返回 warning/diagnostic；
- 不改变既有写入与模块树行为；
- 有真实使用反馈后再升级 enforce。

### 切片 C：成本与语言/artifact

- UsageLedger 只在 CodeWiki 自有调用链落地；
- 语言 analyzer 每个独立立项；
- artifact 先做事实抽取，不做整包移植。

## 六、共同验收门槛

- 每项先补可复现缺陷或缺失能力的回归测试，再实现；
- 同输入产生相同清单/诊断，不依赖 LLM 随机性；
- 不自动改正文、不自动确认笔记、不绕过 lint；
- 未知价格、未归属组件、未放置节点、不可用 grammar 都必须显式可见；
- 聚焦 pytest、ruff、变更文件 mypy；
- 最后跑全量 pytest；MCP 契约基线为 `121 passed / 5 failed`，运行 `uv run python tests/okf_regression_test.py`，不得新增失败；
- 不运行会写真实 `repowiki/` 的 `tests/smoke_test_mcp.py`；
- 触发条件中的“较多/实质代码/前端仓库”等定性门槛，在立项时用目标仓库实测标定，本清单不预造脱离数据的阈值；
- 不顺手清理无关存量失败，不扩入 provider/CLI/交付形态。

## 七、证据与边界

- 本清单来自调研报告第四至七节，未把上游 README 宣传当作功能证据；
- 上游性能、prompt 体积与缓存数字仍是上游自测，未在本仓复现；
- “值得借鉴”以本地 MCP 知识平台主线为准；legacy CLI 能力默认降一档；
- 已落地的 timeout、JS/TS constructor、C/C++ declarator、Git stdin、Mermaid daemon/三态、nested Git boundary 不再重复列入；
- 本清单是排序与边界记录，不代表这些项目已经立项或承诺实现。
