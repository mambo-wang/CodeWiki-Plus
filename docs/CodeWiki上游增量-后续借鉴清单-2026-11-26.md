### B1：反向引用索引

**要解决的问题**

当前 change_plan 能知道哪些模块页因源文件变更而过期，但不能直接回答“还有哪些页面提到了被删除或改名的组件”。宿主 Agent 往往需要全库扫描 Markdown。

**薄适配方案**

- 从页面提取 Markdown 链接、wikilink、component ID、代码块中的唯一符号名；
- 复用 `wiki_lint` 的链接/wikilink 解析语义，不另造 Markdown 真源；
- 建立可重建的 `页面 -> 引用对象` 与 `被引用对象 -> 引用页面` 索引；
- 索引只放 `.meta` 下，删除后可全量重建，不进知识语料；
- 在 `incremental-update` prepare 结果中返回 `referencing_pages`；
- 宿主 Agent 决定是否改写，工具不自动编辑正文。

**验收**

- 同一输入产生相同引用页清单；
- renamed/deleted component 能找到所有引用页；
- 索引删除后可从现有页面完整重建；
- 不改变现有 confirm/lint 行为。

**明确不做**

不搬上游整套组件 updater，不把索引作为第二份页面真源，不自动修复正文。

**实施状态（2026-11-26）**

- 实现位于 `codewiki/mcp/tools/reference_index.py`，作为内部模块接入 `analyze_repo` 的 `changes`，不新增 MCP 工具。
- 默认布局索引为 `repowiki/.meta/reference_index.json`；centralized member repo 使用既有 per-repo 元数据布局。索引被 `.gitignore` 与 `TEAM_LAYOUT_REBUILDABLE_FILES` 排除，写入时明确关闭 auto-stage。
- `changes.component_changes` 稳定返回 `added/deleted/renamed`；`changes.referencing_pages.components` 返回删除/改名组件的引用页。宿主 Agent 决定是否改写，工具不编辑正文。
- rename 仅认同一 `relative_path + start_line + end_line + component_type` 且一对一的新旧组件；代码符号只从 fenced/inline code 提取，同名胜者不建立反向引用。
- 历史唯一符号基线存入 SQLite `repo_meta.reference_symbols`；删除反向索引文件后仍可重建旧符号引用。索引本身不写时间戳，key 与页面清单均排序。
- `incremental-update` prompt 与 `analyze_repo` 工具描述已补充消费方式；confirm/lint 闸门未改。
- 验证：反向索引专项 7 项、索引/初始化/团队布局/auto-stage 周边回归 37 项通过；全量 `1434 passed, 2 skipped`；MCP 契约 `121 passed, 5 failed`（与既有基线一致，无新增失败）；ruff 与 `git diff --check` 通过，新增索引模块 mypy 无错误。

### B2：ownership closure

**要解决的问题**

module tree 只跟踪部分 component。大仓库中可能出现“组件确实变了，但不属于任何模块页”，当前只会作为 leftover 报告，增量链路可能漏掉它。

**薄适配方案**

先实现三条确定性规则：

1. 同文件已有组件继承 owner；
2. 同目录多数 owner 作为候选；
3. 邻居模块多数票作为候选。

输出 `effective_owner_candidates` 供宿主确认。删除组件无法归属时显式进入 `unresolved_deletions`，不得静默忽略。

多数票平局时保留全部并列候选，按 component ID 排序；没有多数时不指定唯一 owner，转入 unresolved。阈值与邻居范围在立项时用目标仓库实测标定，不在工具里预造脱离数据的常量。

**验收**

- 同文件、同目录、邻居多数票三类样例得到稳定候选；
- 未分配 component 不会从 changes 中消失；
- 无法归属的删除项明确列出；
- 同输入产生相同候选顺序。

**明确不做**

不把上游第 4 条 LLM routing agent 内置进工具；不自动把候选写成最终 owner。

**实施状态（2026-11-26）**

- 实现位于 `codewiki/mcp/tools/ownership.py`，作为内部纯函数接入 `analyze_repo` 的 `changes`，不新增 MCP 工具，也不进入 `change_plan/job_state`。
- owner 取 module tree 节点的完整层级路径；组件未直接登记时，按 `file::Class.method` 逐级回溯 enclosing class。
- 规则顺序固定为同文件 → 同目录 → 一跳正反依赖邻居；只有严格多数才形成唯一候选，最高票并列时保留全部并列候选，唯一相对多数不冒充多数。
- 删除项使用删除前组件图归因；SQLite incremental 与 legacy/full 都在覆盖缓存前保存旧图，避免删除项漏报；无法唯一归属时进入 `unresolved_deletions`，未分配组件不会从 changes 消失。
- 候选返回 `rule`、`votes/total` 与完整 `module_path`；`ownership_tree_status` 区分 `loaded/missing/invalid`，树文件损坏时通过 `ownership_warning` 与日志显式告警，并保持分析非致命。
- 当前仓库校准发现 `first_module_tree.json` 的 1153 个 ID 与 SQLite 缓存 2108 个组件交集为 0，因此不硬编码经验阈值；采用严格多数与一跳邻居，并把票数交给宿主判断。
- `incremental-update` prompt 与 `analyze_repo` 工具描述已补充消费方式；工具不修改 module tree 或文档正文，confirm/lint 闸门未改。
- 验证：B2 专项 9 项、相邻回归 47 项通过；全量 `1444 passed, 2 skipped`；MCP stdio 工作流验证通过；MCP 契约 `121 passed, 5 failed`，与既有基线一致；ruff 通过，`ownership.py` mypy 无错误，`analysis.py` 仅保留 1 条既有 `langs` 注解错误。

### B3：tree repair 纯函数

**要解决的问题**

当前 change_plan 已覆盖页面增删改，但模块树结构修复主要依赖宿主 Agent。确定性规则应由工具完成，避免不同 Agent 给出不同结果。

**薄适配方案**

按顺序实现纯函数：

1. rename：原地替换 component ID；
2. delete：移除 component，并剪掉空节点；
3. add：同文件 → 同目录单 leaf → 邻居多数票；
4. 剩余 orphan 只输出候选，不调用 LLM；
5. 输出每一步决策与未放置清单；
6. leaf 超过阈值只返回 warning，不触发自动重聚类。

可并入 `save_module_tree` 前的校验/修复阶段。observe 模式只返回 repair plan 和候选，不直接改树；显式 apply 模式才执行纯函数修复。

**验收**

- rename/delete/add 三类输入得到确定性修复结果；
- orphan 与超阈值 leaf 均有显式输出；
- 观察期不改变既有模块树；
- 修复过程不调用 LLM。

**明确不做**

不在工具内调用 LLM 重聚类，不默认执行 apply，不静默丢弃 orphan。

**实施状态（2026-11-26）**

- 实现位于 `codewiki/mcp/tools/tree_repair.py`，作为纯函数接入 `analyze_repo.changes.tree_repair` 与 `save_module_tree`，不新增 MCP 工具。
- 处理顺序固定为 rename → delete → 后序剪空节点 → add；rename 只原地替换，目标 ID 冲突时保留原树并输出 `conflict`，不把未知 ID 猜成删除。
- add 只处理本轮 diff 中选为 tracked 的组件：同文件严格多数 → 同目录唯一 leaf → 一跳正反依赖邻居严格多数；最终仍无法唯一归属时，平局、唯一相对多数、orphan 与 untracked 均显式保留，不指定虚假 owner。
- 默认 `repair_mode="observe"`：分析阶段只返回计划，保存阶段原样保存宿主提交的树；显式 `repair_mode="apply"` 才应用修复，且要求本轮 fresh `analyze_repo` 会话提供 component diff。
- `tree_repair_status/warning` 区分 `loaded/missing/invalid`；损坏树不阻断分析。`growth/growth_flagged` 按实际新增组件占 leaf 的大小计算，默认阈值 0.33 来自上游 `UpdateOptions.tau_grow`，只告警、不重聚类。
- 与 B1 共用 `component_changes` 和唯一跨度 rename 判定，与 B2 共用 owner map、enclosing class 解析、严格多数和邻居投票实现，避免规则漂移。
- `incremental-update` prompt 与两个工具描述已补充 observe/apply 消费方式；confirm/lint 闸门未改。
- 独立审查后补了安全边界：重复组件归属显式报错；同仓重分析选最新代次；缓存恢复会话缺少本轮 diff 时拒绝 apply；rename 源缺失时目标重新进入 add/orphan；同文件无严格多数时继续后续规则；邻居投票保留非 leaf owner；位置证据共用分隔符、`./` 与平台大小写规范化。
- 专项与相邻回归 **43 passed**（tree repair 21、ownership 9、module tree validation 6、reference index 7）；提示词专项 **19 passed**；`tree_repair.py`、`ownership.py` 与专项测试 mypy 为 **0 error**；真实 stdio 验证 `save_module_tree.repair_mode` 默认 observe、可选 apply，增量 prompt 包含 observe/apply、unplaced 与 growth 消费说明。
- MCP handler 契约回归 **121 passed / 5 failed**，与 B2 既有基线一致，没有新增失败；5 条仍为 OKF/frontmatter/confirm gate 的存量问题。
- 全量 pytest **1465 passed, 2 skipped**；最终会话选择、watch 与清理聚焦回归 **40 passed**，ruff 与 `git diff --check` 通过。未运行会写真实 `repowiki/` 的 `tests/smoke_test_mcp.py`。

### B4：计划写入门禁

**要解决的问题**

`doc_writer` 已防目录逃逸，但不知道“这一页是否属于本轮 change_plan”。Agent 可能改写计划外页面，扩大影响范围且难以审计。

**薄适配方案**

采用“默认 observe、可升级 enforce”的计划写入门：

- observe：计划外写入返回 warning，仍允许；
- 明确不属于任何算子的页面记录 `unplanned_write`；
- enforce：仅允许 `pending_pages` 与当前 Agent target；
- 所有拒绝/降级都可见，不静默失败。

**验收**

- observe 模式保持既有写入行为；
- enforce 模式拒绝计划外页面并返回明确原因；
- 路径逃逸仍由原安全校验拦截；
- 计划内写入不受影响。

**明确不做**

不用 plan 校验替换目录逃逸校验；两者解决不同问题。

**实施状态（2026-11-26—27）**

- 实现位于 `codewiki/mcp/tools/write_guard.py`，作为内部纯模块接入 `write_doc_file/edit_doc_file`，不新增 MCP 工具。
- `write_guard_mode` 默认 `observe`；`enforce` 放行非 `done` 的非删除算子与精确 `target`。`failed/skipped` 仍视为待处理，`delete_subtree` 不能授权重建。
- 分类显式区分 `pending/planned_not_pending/unplanned/delete_only/unavailable`；缺/坏计划在 observe 下保持兼容，enforce 失败关闭，但精确当前 target 是已确认的显式例外。
- 计划外允许或拒绝的写入进入 `change_plan.write_guard.unplanned_writes`；摘要返回审计计数，审计不带时间戳且不进入 `plan_hash`。
- 路径解析先于门禁；centralized 编辑按当前仓分区路由，显式目录路径不再 basename 回跳，symlink 逃逸显式拒绝。模块算子与 `target` 必须匹配实际 module 路径，query/entity 同 stem 不能借用算子或误结算。
- 独立审查后补齐边界：结构算子优先匹配自身 `page_key`；centralized 的算子与 target 都不能跨仓分区；计划校验接受 `page_key: null`，并核对 schema 与 `plan_hash`；审计读写失败只告警，不改变 enforce 裁决；组件页按大小写精确结算，无 `page_key` 的旧算子不结算任意嵌套同 stem 页。
- 最终审查又纠正了同 stem 账本归因：plan 构建、删除、replan 与 manifest 文件归因均按当前仓分区查找模块页，不再从共享池取首个同 stem 项；删除执行前再次拒绝跨仓目标；`mark_op_done` 对结构算子始终校验实际页归属；`doc_writer` 向 job ledger/change plan 传递实际 `page_key` 与分区，query/entity 或他仓模块页只计 `other_written`，不能把缺页 job 误关为 done。
- 旧计划兼容边界同时收口：overview 算子只选 canonical `wiki/overview.md`；无 `page_key` 的删除拒绝带目录的 query 路径；无 key 的 update 仅在有唯一安全匹配时授权/结算，显式路径优先于 bare stem，歧义保持 pending；canonical overview 的实际路径可被默认 module 类型调用正确结算。
- 验证：B4 专项 **43 passed**；跨仓与旧计划修复后，plan/job/guard/centralized/写入路由联合 **172 passed**；ruff 通过，`write_guard.py`、`change_plan.py`、`job_state.py` mypy 为 **0 error**；真实 stdio 验证 write/edit 均暴露 observe/enforce 与 target schema。
- 这是宿主 Agent 的操作性闸门，不是安全边界；有直接文件系统权限的宿主仍可绕过 MCP。

### B5：聚类质量 validator

**要解决的问题**

MCP 聚类由宿主 Agent 完成，工具侧缺少确定性质量诊断。微页、漏文件、同文件组件跨模块等问题只能在人工审查时发现。

**薄适配方案**

- 按完整 scope 文件估算代码 token，而不是只数 leaf prompt token；
- 检查同一文件组件是否被拆到互斥模块；
- 返回微页、未覆盖文件、未知 component ID；
- 给出宿主可执行的修复建议；
- 默认 observe，不自动重排模块树。

**验收**

- 构造微页、重复文件归属、漏文件三类坏树，工具均能诊断；
- validator 不调用 LLM；
- 不自动修改 module tree；
- 诊断结果可由测试稳定复现。

**实施状态（2026-11-27）**

- 实现位于 `codewiki/mcp/tools/clustering_validator.py`，作为内部模块接入 `save_module_tree.clustering_validation`，不新增 MCP 工具、不调用 LLM、不改提交的树。
- 按完整 scope 文件当前文本分块计数；父模块 scope 是自身与后代 leaf 文件并集。缺失、不可读、非文件与逃逸仓库的文件显式进入 `unmeasured_files`，不当 0 token；部分缺测不宣判微页。
- 诊断覆盖微页、超大 leaf、同文件跨互斥 leaf、漏文件、未知/无路径组件和不可测文件，并返回所有模块估算。空 leaf 与 unknown-only leaf 分开处理，0 阈值关闭对应尺寸诊断。
- 阈值来自本仓 `first_module_tree.json` 22 个 leaf 的完整文件实测：`chars_per_token=4`、`min_leaf_tokens=1000`、`max_leaf_tokens=32000`；可在 `conventions.clustering_validation` 覆盖，不是跨仓库通用结论。
- 使用 `LazyComponentStore.items()` 的轻量路径元数据，避免逐组件反序列化完整 Node；会话内按文件签名缓存计数，文件未变时跳过重复读取。schema/config/诊断/工作区写入异常统一降级为 `unavailable`，不把已保存的树变成失败。
- 历史 Windows 分隔符 ID 在唯一规范化后兼容解析，module tree validation 与 B5 使用同一兼容口径；精确 ID 优先，不猜测歧义归属。
- 验证：B5 专项 **20 passed**，与 module tree validation、B1/B2/B3 联合 **63 passed**；最终 B4/B5、增量链路与提示词联合 **125 passed**；ruff 通过，validator 与 module tree mypy 为 **0 error**；真实 stdio 工具清单 **53** 个。
- 最终全量回归（清除本机代理环境，避免 `NO_PROXY=[::1]` 被 httpx 误解析）：**1538 passed, 2 skipped, 1 warning**；MCP handler 契约 **121 passed / 5 failed**，与既有 OKF/frontmatter/confirm gate 基线一致，无新增失败；最终 `git diff --check` 通过。未运行会写真实 `repowiki/` 的 `tests/smoke_test_mcp.py`。

## 三、P2：成本、语言与 artifact

### C1：CodeWiki 自有 LLM 调用成本台账

**适用条件**

恢复或扩展 Mode B、standalone backend 等由 CodeWiki 自己发起 LLM 调用的路线。MCP 主线中宿主 Agent 的调用成本不能由工具凭空推算。

**薄适配方案**

- 复用现有 job/metadata，不新增第二套 run 真源；
- 每次调用记录 phase、kind、target、model、seconds、tokens、cost；
- pricing 可配置；未知价格显式标为 unknown，不显示为 `$0`；
- 宿主 Agent 成本标为 `external`，等待宿主回传；
- 不与检索 `est_tokens` 混为一谈，后者只是内容预算提示。

**验收**

- unknown pricing 不显示为零；
- 外部宿主成本不会混入 CodeWiki 自有调用账单；
- 线程安全并支持嵌套 agent；
- 按 phase 汇总与逐调用明细一致。

**明确不做**

不推算宿主 Agent 成本，不把 `est_tokens` 当账单，不为未知价格填零。

### C2：语言分析器按需求逐个引入

下表是初排，实际顺序按目标仓库语言占比与 grammar 准备成本复核；“成本最高”指相对整合成本，不是通用性能结论。

| 语言/机制 | 建议顺序 | 触发条件 | 边界 |
|---|---:|---|---|
| Rust | 1（已实施） | 仓库有实质 Rust 代码 | 独立 grammar wheel + 一次性 preflight；保留路径与 trait 身份 |
| Ruby | 2（已实施） | Ruby 仓库 | 独立 grammar + 词法作用域；保留类/module/mixin、调用与继承边 |
| Vue SFC | 3 | 前端仓库 | 切分 script/template，补模板组件边 |
| Go package-aware | 4 | Go monorepo/多 module | 借 package index 思路，保留本地 route extractor |
| Scala | 5 | Scala 仓库 | case class/object/enum 等结构 |
| Dart/Flutter | 6 | 明确 Flutter 需求 | 成本最高，需 visible-scope resolver，独立项目 |
| Zig | 7 | Zig 仓库 | 容器、泛型、`@import`、build.zig |
| Lean 4 | 8 | 专用 Lean 仓库 | header scanner + Tree-sitter + 精确名称解析 |

**Rust 实施状态（2026-11-27）**

- 接入点核实：`.rs` 已被文件收集与语言白名单接受，但此前没有 analyzer 分派，会导致 Rust 仓库产出零源码组件。现在 `CallGraphAnalyzer` 在解析任何文件前执行 grammar preflight，并分派到独立 `analyzers/rust.py`；`AnalysisService` 的 supported languages 同步补上 Rust。
- 使用独立 `tree-sitter-rust==0.23.3` wheel，不走 `tree-sitter-language-pack` 首次运行下载。grammar 缺失或 ABI 不兼容时显式抛出 `GrammarUnavailableError`，不退化成空组件列表；Language 对象缓存，单文件 parser 独立创建。
- 提取 struct/union/enum/trait、自由函数、impl/trait 方法、字段类型、trait 实现、结构体实例化与调用边。`src/` 下的文件模块路径、`crate/self/super`、import/alias 与跨文件同名符号参与解析；trait impl 方法使用 `Type.Trait.method` 唯一逻辑名。
- 调用解析保留 `::` 路径与接收者类型：外部 `tokio::spawn()` 不会尾名绑定本地 `spawn`，未知接收者方法不猜测目标；已知项目类型即使方法名与标准库噪声相同（如 `push`）也保留边。局部变量按词法作用域由近到远推断，`cfg(test)` 只匹配真实 test 条件，不误跳 `feature="contest"`。
- 当前边界：macro token tree 内部调用无法由 tree-sitter 直接看到；glob import、复杂 re-export、函数块内 import 的完整词法作用域与完整 Rust 类型推导不在本切片内。既有增量链路只解析变更文件，因此“仅变更 impl 文件、类型与 trait 留在未变更文件”时的跨文件 trait 回填尚未覆盖；需在后续增量索引切片验证，不能把全量结果直接当作增量保证。每种后续语言仍独立测试、独立回退。
- 独立审查后补齐外部同名调用、未知接收者、跨文件同名符号、trait 方法 ID 冲突、变量遮蔽、项目 `push` 方法与 `cfg(feature="contest")` 反例；另补跨文件 trait impl 的类型回填。最终复核又修复内联模块外→内顺序、模块内 import 遮蔽、impl 内嵌套自由函数误归为方法、`pub use` alias 漏记，四项均有先红后绿回归。
- 验证：Rust 专项 `25 passed`，相邻联合 `38 passed`；ruff check、ruff format --check 与两个新增模块 mypy 通过。Rust 阶段最终全量回归为 **1602 passed, 2 skipped, 1 warning**。正式 stdio MCP 新鲜临时仓得到 10 个 Rust 组件，包含 `a.b.f`、`p.make.inner`、`x.Foo.new`、`logger.Logger.warn`，覆盖本轮四项边界；新增 `Logger.info` 的增量分析得到 7 个组件，`component_changes.added` 仅包含新方法。MCP 契约保持既有 `121 passed / 5 failed`，无新增失败。
- 决策草稿为 `repowiki/notes/2026-11-27-rust-analyzer-应保留模块路径与调用身份.md`，保持 draft，未自动确认。

**C2 增量接入复核（2026-11-27）**

- Ruby 正式 stdio 增量复测发现：analyzer 已能解析 `.rb`，但 SQLite `AnalysisCache._SRC_EXTS` 未包含 `.rb/.rs`，指纹扫描会把缓存文件全部当成删除后新增，导致无改动也反复报告全量变更。两语言回归先红后绿，现已补齐扩展名。
- 修复后同一 Ruby 临时仓无改动响应为 `changed_files=[]`、`no_changes=true`；仅新增 `Runner.Executor#report` 时，`changed_files=['lib/support.rb']`，`component_changes.added` 只包含新方法。此前“组件 diff 只有新增方法”不足以证明文件级增量缓存正确，必须同时核对 `changed_files`。

**Ruby 实施状态（2026-11-27）**

- 使用独立 `tree-sitter-ruby==0.23.1` wheel，并复用 C2 grammar preflight；CLI 扩展名、语言检测、prompt 映射、mtime 元数据、`AnalysisService` 白名单与 `CallGraphAnalyzer` 分派同步接入。grammar 缺失或坏语法不伪装成空组件。
- 类/module 保留完整词法命名空间，重开类复用同一身份；实例方法、单例方法与顶层方法分别使用 `#`、`.` 身份，例如 `Shop.Worker#run`、`Shop.Worker.run`、`#run`、`.run`。限定声明保留 lexical namespace，`class ::B` 保持顶层；superclass 在 enclosing scope 求值。
- 接收者只按调用点之前、同一词法执行路径上可确定的 `Const.new` 赋值推断。条件分支、未知或运算符重赋值会清除旧类型；方法参数与 block 参数（含解构、splat、keyword/block 参数）遮蔽外层名字；方法默认参数不假定构造器类型。
- 常量引用一旦找到词法命名空间，剩余路径不跨层回退；`A.run/B.run` 不跨 owner 绑定，`Missing.run` 不按尾名猜测。项目自定义 `String/JSON/send/map` 不按内置噪声删除，`send/public_send/define_method/属性宏` 不凭空生成方法或调用边。
- 直接分析器保持未知裸标识符无边；仓库分析模式用内部 deferred candidate 跨文件解析裸方法，并保留实例/单例/顶层身份。解析失败的 candidate 不进入最终依赖图，行为不依赖文件分析顺序。
- 两轮独立审查覆盖条件重赋值、def 边界、限定声明、顶层方法冲突、跨文件裸调用、解构赋值、运算符赋值、继承作用域、splat 参数与 namespace 回退，均有先红后绿回归。
- 验证：Ruby 专项 **43 passed**（含 `.rb/.rs` 指纹缓存 2 项），Ruby/Rust 联合 **68 passed**，再加入 analyzer correctness 与 latest compat 的联合回归 **81 passed**；ruff check、ruff format --check、`git diff --check` 通过，Ruby/Rust/grammar 与 Ruby 测试 mypy 无错误。
- 真实语料使用系统 Ruby 2.6 标准库 19 个样本，得到 **956 个组件、2823 条关系，约 1.404 秒**，无解析失败或重复 component ID。正式 stdio MCP 首次得到 16 个组件、4 个 leaf，跨文件实例调用、继承与 mixin 边正确；修复指纹缓存后，无变更与单文件增量响应均符合预期。
- MCP 契约为 **121 passed / 5 failed**，与既有 OKF/frontmatter/confirm gate 基线一致，无新增失败；最终全量回归为 **1645 passed, 2 skipped, 1 warning**。未运行会写真实 `repowiki/` 的 `tests/smoke_test_mcp.py`。
- 当前边界：不执行 Ruby，不承诺 `send` 等动态派发、默认参数类型推断、完整 Ruby 类型推导或所有元编程语义；新增语言的缓存扩展名、mtime、白名单与分派必须作为同一接入切片验收。
- 决策草稿为 `repowiki/notes/2026-11-27-ruby-analyzer-应保留命名空间与调用身份并保守推断接收者.md`，保持 draft，未自动确认。

**共同验收**

- 正反样例覆盖核心语法与调用边；
- 不替换或删除本地已有跨服务路由、增量缓存、PageRank/transitive impact；
- 使用 `tree-sitter-language-pack` 前先实现 grammar preflight；
- 离线环境在构建期预下载 grammar，不能把下载失败吞成“该语言没有节点”；
- 每个语言独立测试、独立回退，不一次引入八种。

**明确不做**

不整包覆盖 `dependency_analyzer`，不把 grammar 下载失败降级为空节点，不为扩表一次性引入全部语言。

### C3：artifact facts 独立适配层（已实施）

**适用条件**

部署密集 monorepo，需要把 Make、CI、Docker、Compose、manifest、schema、脚本与源码一起文档化。

**薄适配方案**

已实现独立 `artifact_facts.json` 事实表：从 Make、GitHub/GitLab 等 CI、Docker/Compose、package/pyproject/requirements 与通用 manifest、OpenAPI/proto/JSON Schema、shell/PowerShell 脚本抽取确定、稳定排序且带 path/line 溯源的事实。artifact ID 使用独立 `artifact:` 命名空间，不进入源码 components、SQLite component 表、依赖边、leaf 或 module tree；不照搬上游 artifact Node/拓扑模型，也不改变既有源码 component ID。

发现阶段复用仓库边界与 gitignore 过滤，排除 symlink、嵌套 Git checkout、lockfile、依赖/构建目录与凭据类文件。默认限制 250 文件、每文件 64 KiB、每文件 100 单元、总计 2000 事实；文件/单元/事实上限、不可读、解析失败、截断与旧索引损坏均显式返回。采集或持久化失败 fail-open，不阻断源码分析。

事实按文件指纹比较，artifact-only 改动会合并进 `changes.changed_files` 与 `changes.artifact_changed_files`，即使源码缓存返回 `no_changes` 也会进入增量流程。centralized 布局通过 `analysis_meta_dir()` 按成员仓隔离。事实表是可重建派生物，不进入 git；schema 增加构建入口、CI、容器运行与部署拓扑文档维度。

**安全与执行边界**

不执行 Make、CI、Docker、Compose 或脚本；不导出 Compose environment 键值、命令正文、package script 命令正文或 CI `run` 正文，只保留结构化属性与有限路径/模块/action 引用。

**验收**

- 构建/CI/容器事实可追溯；
- 不破坏既有源码组件图与 ID；
- artifact 缺失、不可读、解析失败或持久化失败不阻断源码分析；
- 独立测试覆盖核心解析、敏感信息不导出、部分可用、截断/上限、指纹增删改、确定性与 artifact-only 增量。

**实施与验证（2026-11-27）**

- 核心位于 `codewiki/mcp/tools/artifact_facts.py`，接入 `codewiki/mcp/tools/analysis.py`；不新增 MCP 工具。全量与无变更响应均暴露 `artifact_facts` 和 `files.artifact_facts`，增量响应返回 `changes.artifact_changed_files`。
- 独立审查修复了 Make 行内配方与 shell 展开泄漏、路径引用正则双点、FIFO 阻塞、未知 CI 形状误报、TOML 跨 section 行号、损坏旧索引与持久化失败等边界；每项均有回归覆盖。
- 专项与相邻回归 `76 passed`（其中 artifact facts `39 passed`）；ruff check、ruff format --check、`git diff --check` 通过，核心新增模块 mypy 无错误。

- 决策草稿为 `repowiki/notes/2026-11-27-artifact-facts-应作为源码图外的确定性事实层.md`，保持 draft，未自动确认。

**明确不做**

不照搬上游整份 artifact analyzer，不让 artifact 节点重写既有源码 component ID，不把事实层扩展成第二张依赖图，不执行工程命令或自动改写文档。
