# 知识飞轮增强设计方案（P2 三项：目录级摘要 · 注入预算 · 字段级预合并）

> 来源：`docs/OpenViking-调研与借鉴分析.md` 借鉴清单 P1 部分 #1/#2/#3（OpenViking 机制思想借鉴，**不涉代码复制**——其主项目为 AGPLv3）。
> 日期：2026-08-22 · 状态：**候选（评审中，未实施）** · 预计工作量：**3–4 人日**（A/B/C 三线相互独立，可并行）。
> 前置：P1-A 采纳信号已落地（adoption_hint、agents_md.py 约定段）；reading_guide / query_wiki / consolidate_notes 均为现状工具。
> 范围约束：沿用 P0/P1 哲学——不新增 MCP 工具、能力长在现有工具上；**零 LLM 依赖**（三项全部规则实现，不引入 embedding/摘要模型）；评审闸门不动摇（C 线只做"合并后过闸"，不做"免闸直写"）。

---

## 一、背景：从"转起来"到"转得省"

P0（摩擦触发/使用反馈/检索透明）让飞轮转起来，P1（采纳信号/低采纳检查/promote）让飞轮转得准。P2 三项解决三处**显性成本**，各自独立、互不依赖：

| 线 | 成本点 | 现状 | 借鉴的 OpenViking 机制 |
|----|--------|------|----------------------|
| A 目录级摘要 | Agent 预读 token | 渐进式阅读展开即读正文段，预展开阶段无轻量层 | L0/L1/L2 分层加载（L0 约 100 token） |
| B 注入预算 | IDE 上下文占用 | adoption_hint 与检索结果全量文本注入，无预算控制 | auto-recall 超预算降级为 URI+score |
| C 字段级预合并 | 人的确认次数 | 同主题多条 draft 各过一次 confirm，闸门是规模化瓶颈 | 12 类记忆 schema 的字段级 merge_op |

三项共同的实现姿态：**借粒度不借管线，借模式不借哲学**。OpenViking 用 LLM 写时生成摘要、无闸门直写——这两点明确不学；它"分层加载的梯度""预算降级的形态""字段合并的粒度"三点直接吸收。

## 二、A 线：目录级摘要 abstract（#1）

### 2.1 机制形态：frontmatter 字段，规则抽取，不建 sidecar

OpenViking 的 L0 是独立 sidecar 文件（`.abstract.md`）。本方案改放 **frontmatter `abstract:` 字段**，理由两条：repowiki 文件由人和 Agent 共同编辑，sidecar 易漂移，frontmatter 是单一事实源；现有新鲜度机制（stale_after 复核）以文档为粒度，摘要随文档刷新天然同步，零额外调度。

**抽取规则（纯函数，幂等）**：取正文第一个 `## ` 标题之前的段落，截前两句、上限 160 字符。无正文段落时回退 frontmatter 既有摘要字段（若有），再无则留空——不阻塞，不报错。

### 2.2 写入点与三处同步（关键约束）

abstract 生成挂在两个既有写入路径上：generate_docs / write_doc_file 落盘时抽取；lint 或独立维护命令对存量文档**幂等回填**（已有合法 abstract 且正文首段未变则跳过）。

已知坑必须写进实现约束：frontmatter 实有 5 个 writer（3 个显式 + `_apply_status_to_file` / `_merge_okf_sources` 两个 yaml 重 dump）。新增字段须**三处同步**：`repowiki/schema.yaml`（或根模板）字段声明、文档模板、`schema_generator.py`——漏一处会被重 dump 洗掉或 okf_conformance 告警。若 OKF 顶层白名单不含 `abstract`，须扩白名单（顶层单键，不进 metadata——它是一等语义字段，非派生标记，与 `promoted_to` 性质不同）。

### 2.3 消费点

两处，均只读 frontmatter，不重复抽取：

1. **reading_guide**：预展开清单从"标题 + 章节列表"升级为"标题 + abstract"，Agent 在展开任何正文前先扫一批 L0，选中再深入。
2. **query_wiki**：结果条目在预算内可含 abstract（与 B 线联动，见 3.3），命中相关性的判断粒度从文件名降到内容级。

### 2.4 验收

存量 repowiki 回填幂等（跑两遍第二遍零 diff）；5 个 writer 路径下 abstract 均不丢失；抽取纯函数对空文档/无段落文档不抛错。

## 三、B 线：注入预算降级（#2）

### 3.1 机制形态：预算内全文，预算外一行线索

OpenViking auto-recall 对超预算条目降级为"URI + score"——**不丢线索，只降信息量**。本方案落到两个注入点：

1. **AGENTS.md 约定段**（`agents_md.py`）：检索建议/采纳约定段给定字符预算（默认 400 字符，配置化），超预算的推荐条目压为 `路径 | 相关性` 一行。
2. **query_wiki 结果组装**（`wiki_search.py`）：结果条目含摘要文本的部分按预算裁剪——预算内 top-N 给完整内容，其余压为 `file | score` 单行，Agent 需要时再读（view_repo_file / reading_guide 均可达）。

预算估算不引 tokenizer：中文场景按字符数近似（len(text)），配置键提供倍率。这是排序提示的预算，不是计费精度，容忍近似。

### 3.2 配置

`schema.yaml` conventions 段新增 `injection_budget`（两键：`agents_md` / `search_result`，单位字符，0 = 关闭降级保持现状）。**注意既有坑**：repowiki/schema.yaml 配置必须插在 conventions 段内——追加文件末尾缩进失效会静默回退默认值。

### 3.3 与 A 线、P1-A 的联动

A 线 abstract 天然是 B 线预算内的最优填充物——"一行线索"从 `路径 | 分数` 升级为 `路径 | 分数 | abstract`，降级条目也带内容判断依据。adoption_hint 走降级格式（它是"提示存在"而非"提供内容"）。

### 3.4 验收

超预算条目全部出现在降级行且路径可解析；预算为 0 时输出与现状逐字节一致（回归保障）；hint 不占预算不丢内容。

## 四、C 线：字段级预合并（#3）

### 4.1 机制形态：预合并后过闸，一次确认

OpenViking 对记忆直接 upsert 靠 merge_op 兜底质量——**闸门我们不借**，借的是粒度。现状 consolidate_notes 对同主题多条 draft 是整条级操作；升级为：同主题多条 draft 先按字段策略预合并为**一条** draft，人只 confirm 一次。库内转正知识仍然条条过审，变的只是"确认次数"，不变的是"审过才转正"。

### 4.2 字段策略映射

| note 字段 | merge_op | 规则 |
|-----------|----------|------|
| note_type / related_modules | replace | 取最新一条（树龄最小） |
| title | replace | 同上 |
| 正文 body | append | 按树龄升序拼接，段间加来源标记（`> 合并自 <note-id>`） |
| 计数类（如引用次数类派生字段） | sum | 累加 |
| stale_after / status | immutable | 预合并阶段不改，合并后重算 |

首版只做 replace / append / sum 三档（OpenViking 另有 patch + search-replace diff 算法，实现重、收益边际，明确不做）。策略表作为常量放 `note_consolidation.py` 顶部，不进配置——这是机制而非约定，没有按仓库定制的选择空间。

### 4.3 合并边界

- 仅对**同 note_type 且主题相同**（现有 consolidate 的判定标准不变）的 draft 组生效；单条不动作。
- 合并产物是 draft（status 不变），走既有 confirm_note 闸门；被合并的原多条 draft 在 confirm 后批量置 superseded（复用 batch_set_status，不新造状态）。
- 合并可逆：confirm 前拒绝合并产物，原 draft 组原样保留（预合并只产副本语义，不就地改写）。

### 4.4 验收

三条同主题 draft 合并后人工确认一次即全部转正；拒绝路径原 draft 零变化；immutable 字段（status/stale_after）在合并产物中取值正确；不同 note_type 混组不触发合并。

## 五、任务拆解与顺序

| # | 任务 | 线 | 依赖 |
|---|------|----|------|
| 1 | abstract 抽取纯函数 + 三处同步 + 存量回填命令 | A | 无 |
| 2 | reading_guide / query_wiki 消费 abstract | A | #1 |
| 3 | injection_budget 配置 + agents_md / wiki_search 两处降级 | B | 无（联动收益依赖 #1） |
| 4 | merge_op 常量表 + 预合并 + superseded 联动 | C | 无 |
| 5 | 测试（跑法：`python -m pytest tests/ -o addopts=""`）+ 真实 repowiki E2E | 全 | #1–#4 |

三线独立可并行；若串行，建议 A → B（B 的降级行吃到 A 的 abstract）→ C。

## 六、风险与明确不做的事

**风险三条**：abstract 回填对存量 repowiki 产生大 diff（回填前 git 干净起步，diff 单独一笔提交）；预算降级可能砍掉 Agent 真需要的内容（预算可配 0 关闭 + 降级行保留路径即逃生门）；预合并的 append 语义在正文冲突（同一事实两种说法）时会同时保留两说——这是有意的：矛盾留给 confirm 闸门的人裁决，机器不裁决事实冲突。

**明确不做**（与调研报告对齐）：不做 LLM 写时摘要（零模型依赖是检索层卖点）；不建独立 sidecar 文件（漂移风险）；不学无闸门直写；不做 patch/search-replace diff 级合并；不引 token 精确计数。
