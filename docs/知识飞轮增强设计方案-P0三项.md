## 一、背景：飞轮上的三个断点

teamai-cli 调研的核心结论是：CodeWiki 的知识飞轮**触发靠 prompt 自觉、反馈回路在 retrieval_stats.db 处断开、检索输出对 Agent 不够诚实**。对应三个断点：

1. **不知道什么时候该沉淀。** AGENTS.md 的"纠正识别"规则依赖模型自觉，漏报无感知。teamai 用摩擦信号评分（打断/纠正/工具失败）把"值得沉淀的会话"变成客观检测，且从数学上保证"又长又顺的会话不触发"。
2. **检索热度只写不读。** `retrieval_stats.db` 每次 query_wiki 都在记录 hit_count/last_hit，但除了新鲜度专项的 retrieval_defer 豁免外，不参与任何决策——不影响排序、不影响复核优先级。
3. **Agent 无法判断检索结果的覆盖度。** query_wiki 返回 snippet，Agent 不知道"这条结果到底命中了我的哪几个查询词"，容易把主题相邻的结果当成答案，也缺少低成本的相关性预检手段。

三项都不改变架构，是给现有飞轮装传感器（K 线）、接反馈回路（U 线）、让输出更诚实（T 线）。

## 二、K 线：摩擦信号触发机制

### 2.1 关键约束：capture 看不到工具流量

设计前必须承认的现状：`_ide_hook.py` 与 `capture_conversation._extract_transcript` 只保留 `{user, assistant}` 对话轮次，tool-call/tool-result/reasoning 块在 `_NOISE_BLOCK_TYPES` 阶段被丢弃（这是刻意设计——raw 必须无噪音）。teamai 的 toolError/toolReject 两类信号**在现有管线下不可得**。

因此分两步：

- **v1（本方案）：对话层信号。** 只用 user/assistant 文本即可检测的信号（纠正、打断标记、会话规模），零 capture 改动。
- **v1.5（后续可选）：工具层计数。** 在 hook 的块遍历处（`_text_from_content_blocks` / `_try_expand_codebuddy_index`）**只计数、不留内容**地统计 tool-result 错误块，把计数并入摩擦分。格式依赖性强（CodeBuddy index 格式 vs inline 格式），单独排期。

### 2.2 评分模型（移植 teamai 并适配）

新模块 `codewiki/mcp/tools/friction.py`（纯函数、stdlib + 既有依赖、全量单测）：

| 信号 | 检测方式 | 分值 |
|------|----------|------|
| `correction` | user 轮次命中纠正词表（不对/你搞错/不是这样/错了/应该是/不用这样/wrong/incorrect/that's not/redo…词表可配），每个 user 轮次最多计 1 次 | ×20 |
| `interrupt` | user 轮次含 `[Request interrupted` 标记（CodeBuddy/Claude 系通用） | ×20 |
| `repeat` | 相邻两个 user 轮次归一化后相似度 ≥0.8（说了两遍=Agent 没听懂） | ×15 |
| 规模加分 | user_turns ≥ 8 → +5；总轮次 ≥ 20 → +5 | **封顶 10** |

```
friction_score = correction×20 + interrupt×20 + repeat×15 + min(规模加分, 10)
判定门槛：user_turns < 4 → 直接 0 分（会话太短，摩擦无意义）
达标阈值：score ≥ 20 → verdict = "suggest_distill"
```

三条防误报约束照搬 teamai 的数学结构：

1. **规模加分封顶 10 < 阈值 20**：又长又顺的会话（轮次多、无摩擦）永远不触发；
2. **硬门槛 user_turns ≥ 4**：短会话不提示；
3. **输出只是提示，不是动作**：摩擦分只影响"蒸馏优先级与提示文案"，永不自动蒸馏、永不绕过 confirm_note 闸门（与"raw 只落盘不蒸馏"的既有硬约束一致）。

### 2.3 存储：raw frontmatter 两个新键

capture 时对收到的 turns 计算摩擦分，写入 `raw/conv-*.md` frontmatter（顶层单行）：

```yaml
friction_score: 35
friction_signals: correction=2,interrupt=0,repeat=0,user_turns=9
```

兼容性核对：

- `task_session_start.py` 是 stdlib-only 行扫描，只认 `status:` / `task_id:` 两个键——新增键无影响（该 hook 的硬约束保持）；
- supersede 重捕时重算（content_hash 变 → 重写，摩擦分自然刷新）；
- **不触碰 notes/ 与 wiki/**：OKF 5-writer 约束零新增写入点；
- `_iter_raw_files` 的 `status:` 正则、`_peek_frontmatter` 的单行解析都能直接读新键。

### 2.4 呈现链路（四处）

| # | 位置 | 行为 |
|---|------|------|
| 1 | `capture_conversation` 返回 JSON | 增加 `friction: {score, signals, verdict}` 字段；hook 打印（IDE 日志可见） |
| 2 | `distill_conversation(mode="prepare")` | `_iter_raw_files` 结果按 friction_score 降序；返回清单每条附摩擦摘要；清单头部加一行提示「friction≥20 的会话优先蒸馏（更可能含值得沉淀的经验）」 |
| 3 | `get_task_context` | pending raw 列表携带 friction_score（补蒸馏排序依据） |
| 4 | `task_session_start.py` | 行扫描最近一个 `raw/conv-*.md` 的 `friction_score:`，≥20 时打印单行提示「上次会话摩擦分 N（纠正 x 次），建议先 distill_conversation 补蒸馏」。保持 stdlib-only |

### 2.5 配置

`schema.yaml` 可选配置节（缺省走代码默认，整体缺失不影响任何现有行为）：

```yaml
conventions:
  friction:
    enabled: true
    threshold: 20
    min_user_turns: 4
    correction_keywords: [不对, 你搞错, 不是这样, 错了, 应该是, wrong, incorrect]
```

## 三、U 线：使用信号反馈（排序 + 复核联动）

### 3.1 与新鲜度专项的边界

新鲜度专项（已落地）解决"**何时到期**"：stale_after 类型窗口 + retrieval_defer 检索顺延。本线解决"**谁排前面、谁先复核**"：把 hit_count/last_hit 接进排序与复核优先级。两线共用同一份 `retrieval_stats.db` 数据，不新增字段、不新增表。

### 3.2 heat 模型

```
heat(doc) ∈ [0.8, 1.2]
  无检索记录            → 1.0（中性，保护新文档——移植 teamai hot-cold 的"无数据中性"原则）
  boost                → min(boost_cap, 0.03 × ln(1 + hit_count))，命中越多越靠前，对数饱和
  cold penalty         → 仅当 hit_count ≥ cold_min_hits 且 last_hit 距今 > cold_days 时 −cold_penalty
final = BM25 × authority × heat
```

默认参数：`boost_cap=0.15, cold_penalty=0.2, cold_days=180, cold_min_hits=3`。

设计取舍：

- **区间刻意保守（±0.2）**：热度是弱信号，不能压过相关性。teamai 的投票加分同样封顶（min(votes×0.5, 5)）；
- **cold penalty 只打"热过后来冷"的文档**（hit≥3 且 180 天未被召回）：从未被检索过的新文档不受罚，规避"排名低→没命中→排名更低"的马太效应闭环；
- **乘法位置与 authority 一致**：BM25 之后、note 标题 floor 之前（floor 是对短笔记的兜底保护，heat 不应绕过它，与 authority 的处理位置对齐）。

### 3.3 改动点

| 位置 | 改动 |
|------|------|
| `cache.py search()` | 新增 `apply_usage: bool = True` 参数；加载 retrieval_stats 映射（按 db mtime 进程内缓存，避免每次搜索开库）；评分处乘 heat |
| `wiki_search.py search()` | JSON 回退路径同等实现（两路径排序语义必须一致——历史教训：两套 BM25 行为漂移） |
| distill 去重召回 | `_bm25_recall_candidates` 传 `apply_usage=False`（与 `apply_authority=False` 同款豁免：相似度召回不应被热度扭曲，dedup 语义保持） |
| `handle_query_wiki` | 结果条目附带 `usage: {hit_count, last_hit}`（透明化，Agent 可见为什么它排在这） |
| `_check_stale_notes` | 判定逻辑不变；输出排序改为 (overdue_days desc, last_hit asc)，message 附 hit_count——"超期最久且最没人查"的先复核 |
| `wiki_stats` | 增加 `cold_candidates`（hit≥3 且 last_hit>cold_days 的文档列表）作为健康度信号 |

### 3.4 配置

```yaml
conventions:
  usage_ranking:
    enabled: true        # 总开关（关闭后 search 行为与现状完全一致）
    boost_cap: 0.15
    cold_penalty: 0.2
    cold_days: 180
    cold_min_hits: 3
```

说明：`retrieval_stats.db` 是 gitignore 的本机遥测，因此 heat 是**本机跨会话视角**——同一台机器上"我反复查的东西"排更前。团队共享热度依赖 P2 的分发模型（per-user votes 同步），不在本方案。

## 四、T 线：检索透明化三件套

### 4.1 query_coverage 与 matched_tokens（词级透明）

现状：BM25 评分循环里已经在做逐 token 的 df 查询与逐文档 tf 查询——信息全在，只是没输出。

改动（SQLite 与 JSON 两路径同步）：

- 顶层返回 `query_coverage: {tokens, matched, missing}`：`missing` = 索引中 df=0 的查询词（完全不存在），`matched` = df>0 的查询词。ontology/expand_terms 扩展出的词标注 `(expanded)`；
- 每条结果附 `matched_tokens`（该文档实际命中的查询词子集，评分循环顺手收集，零额外查询）。

Agent 判断规则写入 query_wiki description 与 `search-wiki` workflow prompt（移植 teamai README 原话的语义）：**"若关键区分词全在 missing 里，说明该结果只是主题相邻，并非答案——这个判断由调用方做，分数本身无法表达。"**

### 4.2 mode="check" 相关性预检

registry inputSchema 的 mode 枚举加 `"check"`，handler 同步（**枚举同步教训**：type_filter 曾漏 scenario 导致 MCP 校验先于 handler 拒绝合法输入——本次 schema 与 handler 常量必须同提交修改）。

```json
// query_wiki(query="端口冲突", mode="check") 返回（轻量，无 snippet）
{
  "relevant": true,
  "top_score": 3.42,
  "top_results": [{"file": "notes/pitfall-port-conflict.md", "title": "..."}],  // ≤3 条
  "query_coverage": {"tokens": ["端口","冲突"], "matched": ["端口","冲突"], "missing": []}
}
```

约束：check 模式**不记录 retrieval_stats**（预检不算真实消费，防止污染热度数据）、不做图扩展、不读 frontmatter 详情。用途：Agent 任务开始前快速判断"值不值得深入检索"（对应 teamai recall --check 的 subagent 预检）。

### 4.3 max_chars 内容预算

现状 expand=true 固定截断 3000 字符。新增 `max_chars` 参数（默认 3000 保持现状，上限 20000），对应 teamai 的 depth 预算思想——Agent 按任务复杂度取量：

| 场景 | 建议用法 |
|------|----------|
| 快速定向 | `mode="check"`（~200 token） |
| 常规检索 | 默认 snippet（现状） |
| 深读单页 | `expand=true, max_chars=3000`（现状默认） |
| 全页精读 | `expand=true, max_chars=12000~20000` |

registry 同步：mode 枚举 + max_chars 参数 + description 文案，与 handler 同一提交。

## 六、风险与明确不做的事

| 风险 | 缓解 |
|------|------|
| heat 马太效应（排名高→命中多→排名更高） | boost 对数饱和 + 新文档中性 + cold penalty 仅作用于"热过后来冷"文档 |
| correction 词表误报（"不用了"被算成纠正） | 输出只是提示不参与写入路径；词表 schema 可配，上线后按误报率收敛 |
| 两套 BM25 路径行为漂移 | U1/T1 强制双路径同步实现 + 一致性单测（同一索引两路径结果逐条比对） |
| check 模式被当成常规搜索滥用 | description 明确"预检用途"；不记 stats、无 snippet，功能上就不适合当常规搜索 |
| friction 提示打扰 | 每个 raw 只在 prepare/会话开始提示一次（supersede 去重天然保证）；enabled 可关 |

**明确不做（本期）：**

- 工具层摩擦信号（tool error/reject 计数）——v1.5 单独排期，需处理 CodeBuddy/inline 两种 transcript 形态；
- 采纳信号（referenced-doc-ids → upvoted）与"召回多采纳少"质量检查——P1 项，依赖本期 heat 基建先行验证；
- notes → wiki 页面 promote 晋升——P1 项；
- 团队共享热度（per-user votes 同步）——依赖 P2 团队分发模型；
- 任何绕过 confirm_note 闸门的自动写入——不做，闸门哲学不变。
