# 参考项目记忆存储与压缩机制对比（2026-09-12 源码核实）

## 背景与问题

用户问：参考对象的记忆如何保存管理？也像本仓一样存 Markdown 吗？有没有压缩机制？

方法：两个子代理实读六个本地克隆源码（所有论断带 文件:行号），主 Agent 抽读复核关键文件（OpenViking merge_policy.py / retention.py 亲读确认）。

## 压缩四分类（先辨析再对比）

「压缩」在不同项目里指四种不同机制，不可混用：

1. **写入时压缩** — 捕获即摘要（LLM 在入库前把原文变短）
2. **归纳式压缩** — 多条→一条新条目，源保留（many-to-one induction）
3. **上下文预算裁剪** — 只管当前会话窗口装多少，不碰长期存储
4. **衰减/过期** — 不删数据，只降分、清向量或降状态

本仓对应物：`compact_task_memories`（旧条目有损压缩成摘要+原文进 archive）与 `consolidate_notes`（UPDATE>MERGE>CREATE、源置 deprecated）属第 2 种；无 1/3/4（第 4 种 = Phase5 已排除的 C11）。

## 三点结论

### 1. 本仓两个机制有独立收敛先例

- OpenViking merge_policy（"相似/同类/主题重叠只算候选，永不构成同 identity 的证据"，merge_policy.py:5-19）⇔ 本仓 Doctrine「合并判定 related ≠ same，拿不准就不合并」，几乎逐句对应。
- consolidate_notes（源置 deprecated 保留）⇔ HL-Mem supersede 链——双方都是追加式语义 + 账本兜底。
- HL-Mem Mental Model 归纳 ⇔ compact_task_memories（旧条目→摘要，原文进 archive），同一形态。

### 2. 「随业务仓版本化」全场仅两家，是双刃剑

只有 teamai-cli self 模式与本仓把知识放进业务仓 git。代价已付过（repowiki 是随代码版本化的资产）；HL-Mem/claude-mem/mem0 用独立库 append-only 换「永不丢历史」，本仓用 git 历史等价获得且更便宜。

### 3. CBM workspace manifest 误读修正（作废既有转注）

整体调研报告 deferred 项 #10「CBM workspace manifest 审批键 → 转多仓工作区」建立在误读上：CBM 的 workspace manifest 实为 **Rust Cargo.toml workspace 清单**（跨 crate 导入解析，pass_lsp_cross.c:478-488），与审批/多仓无关。该 deferred 项作废，多仓工作区任务中的对应转注已撤。

## 对本仓的启示

- 本仓无「写入时压缩」：capture_conversation 存完整 transcript 进 raw（暂存区），蒸馏时才提炼——与 claude-mem（session end 即压）不同路线，是「延迟压缩换无损暂存」的主动选择，勿当缺口。
- 本仓无「上下文预算裁剪」问题面：注入侧已有 injection_budget（OpenViking auto-recall 借鉴已落地）。
- 第 4 类（衰减）维持 Phase5 C11 排除结论不变。
