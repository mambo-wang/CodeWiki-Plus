## 工作场景
Windows 环境下 Python 包发布、依赖升级、CI 修复、构建后端迁移与 GitHub 凭据/编码治理。适用于发布受阻、CI 变红、选 review 工具、迁移打包配置。

## 适用条件
Windows 控制台发布/CLI 乱码、GitHub 网络与凭据、ruff/uv 升级、单 commit 评审、build 后端迁移、fork PR 合入。

## 核心 SOP
1. Windows 控制台默认 GBK：CLI 输出含非 GBK 字符会崩溃；twine 加 `--disable-progress-bar`，通用规避 `set PYTHONIOENCODING=utf-8`。PowerShell 下不要经命令行传中文参数。
2. GitHub API 直连被阻时用 PowerShell `Invoke-RestMethod` 走系统网络栈；token 从 `git credential fill` 提取。
3. 发布/推送前扫描归档副本中的密钥：对话归档等 raw 可能原样保留 token。
4. ruff 升级后规则集变宽导致 CI 大面积红：显式 `select` 钉住窄默认集，不顺手放宽。
5. 单次 commit 的业务 review 选 mattpocock/code-review（Spec 轴 diff 级）。
6. 子代理报告「全绿」不可信：真全绿必须自己实跑验证。
7. **build 后端迁移（setuptools→hatchling）后用 `unzip -l <wheel>` 对比新旧 wheel 文件清单**：package-data glob 单层匹配 vs hatchling artifacts 递归。不要只看能否安装。
8. uv ≥ 0.30 须用 `--no-group dev`；Docker 用 `.python-version` 补丁固定时确认基础镜像内置 Python 一致。
9. ruff format panic 先按文件二分定位元凶（常是误提交的一次性诊断脚本），不要急着删 CI 检查步骤。
10. **fork PR 冲突合入**：`git merge-tree --write-tree --name-only` 探测冲突清单 → 确认 `maintainer_can_modify` → git worktree 独立目录解冲突 → push fork head 再 merge。CI 绿 ≠ 可合并。
11. 生成的 `.ps1` 必须 UTF-8 BOM（PowerShell 5.1 按 GBK 误读），`.sh` 必须无 BOM；存量无 BOM 文件做字节级自愈。
12. **发布是手动流程**（CI 只做测试与 lint）：版本引用四处需同步——`pyproject.toml` / `codewiki/__init__.py` / `uv.lock` / `server.py`（server 版本从 `codewiki.__version__` 注入，勿手写常量）；bump 提交 `chore: bump version to X`，lightweight tag `vX.Y.Z`；闸门＝全量 pytest + `uv build`。
13. **发布前清 `dist/`**：`uv publish` 默认上传 dist/ 全部产物，残留旧版本一并尝试上传（PyPI 只增不改会幂等跳过，但不可依赖）；改用 `uv publish dist/<pkg>-<version>*`。发布后用 PyPI JSON API 核对真实上传。
14. **Release 正文乱码不可逆**：UTF-8 被按 GBK 解码写入，字符永久丢失；基于 `git log <old>..<new>` 事实重写并标注哪些是推补措辞请用户核对。API 创建时请求体显式 UTF-8，去掉任何 GBK 中间解码。
15. **别把中文/结构化文本塞进命令行参数或管道**：`git commit -m "中文"` 会乱码或拆词 → 写 UTF-8 消息文件 + `git commit -F`；给 `git credential fill` 喂 stdin 用 Python `subprocess` 精确字节（PowerShell 管道 stdin 常为空、`cmd /c echo` 引号被破坏），凭证只留进程内。
16. **hatchling wheel artifacts 不含新增包内资源**：新增 `locales/*.yaml` 等包内非 py 资源必须同步写进 pyproject 的 `[tool.hatch.build.targets.wheel] artifacts`，否则本地开发读得到、装包后 yaml.safe_load 直接失败。
17. **Windows 环境性 flaky 判定**：`test_locked_rmw_across_processes` 类多进程文件锁时序失败，单测重跑即过且发布范围内无相关改动 → 环境性 flaky，勿当回归处理。
18. **同一文件批量并发 replace_in_file 会触发写锁超时（30s）**：对同一文件的多次编辑必须顺序单发，等前一次返回再发下一次；不同文件可并行。失败后先核对实际落盘状态再重试。
19. **GitHub Push Protection 拦截含 secret 的提交**：追加「删除」提交无效（原提交仍含 secret），必须改写原提交历史；repowiki/conversations/ 未被 .gitignore 忽略且含原始转录，提交前必须扫 secret。
20. **Windows PowerShell 下 git add 中文路径会静默失败**：改用 `git add -u`/`-A` 暂存；不要用退出码判断 amend 是否成功（amend 几乎永远成功），用 `git grep` 校验新提交内容。
21. **命令链中途 shell 从 PowerShell 漂到 cmd 会静默中断**：含 cmdlet（Measure-Object 等）的命令链不要在 shell 环境可能混用的会话里整链跑；拆成单条独立执行，git 操作后用 `git log -1` 复核落盘。
22. **维护者 git reset --hard 归位分支前必须检查用户未提交改动**：工作区不是维护者私有的；先 `git status` + 必要时 stash 或备份 diff。
23. **git filter-repo 会删除 origin remote 并重写全部 hash**：事后表现为「远端凭空消失 + 分支假分叉」；跑之前备份 remote URL，事后重加 remote 并 force push。
24. **PowerShell Remove-Item 被包装器代理**：-Exclude 与管道输入均报错；改用 delete_file 工具逐个删（最稳）或 `Get-ChildItem -File | ForEach-Object { Remove-Item }`。

## 判断逻辑
- 孤儿分支不是「部分文件单独分支」；build 后端迁移对 pip 用户可能是未声明的行为变化。
- 「固定补丁版本」与「依赖镜像内置 Python」是天然冲突策略。
- 乱码/拆词/stdin 失效同源：cmd/PowerShell 中间层破坏参数与编码，统一绕法是「落文件 / 精确 subprocess」，不是加转义。

## 禁忌与反模式
- 不给 git 配置注入明文 token；不依赖子代理口头「通过」。
- 升级依赖后不顺手放宽 lint；不因格式器 panic 移除 CI 检查。
- 不假设 PR 的「对安装用户无影响」——用 wheel 清单验证。
- 不依赖 PyPI 幂等跳过当安全网；不用 shell 管道给交互式协议（git credential）喂 stdin。
- 不在维护者不拥有工作区上直接 `git reset --hard`；不跑 filter-repo 前不备份 remote。

## 关键事实依据
- twine 进度条 + GBK 控制台必崩，PYTHONIOENCODING 已验证兜底。
- ruff 0.16.3 panic 元凶是误提交的 `scripts/_tmp2.py`。
- 5.6.0 发布时 dist/ 残留 6 个旧产物被一并上传，经 PyPI JSON API 核实未造成污染。
