## 工作场景
[KnowledgeStore](../../../codewiki/src/store.py) 跨进程锁（sidecar `.lck`）、`file_lock` 通用层与原子写入临时文件（`*.tmp.<PID>`）的落点、释放与清理治理。适用于改锁/并发写入、排查锁残留与孤儿临时文件。

## 适用条件
改动 `store.locked()` / `file_lock` 行为、处理 `.lck` 累积或残留、给原子写入补清理、评估 lint 侧 GC。

## 核心 SOP
1. **锁路径集中化**：sidecar 锁落 `<wiki-root>/.meta/locks/<sha256(目标绝对路径)[:20]>.lck`（`_lock_path_for()`），内容树只放内容；无 `.meta` 祖先时 fail-open 回退就地 sidecar。锁语义只依赖「目标→锁路径」的确定性映射，与是否相邻无关。
2. **动锁前先枚举全部调用点并分两类语义**：锁目标数据文件本身（I/O 走锁句柄，如 wiki_index 分片）绝不可删；sidecar 哨兵（仅 `store.locked()` 一支）才可做删除/迁移/清理。
3. 清理只在 `store.locked()` 出口做 best-effort unlink 并吞异常，且**仅 Windows 启用**；Unix 保留「锁文件永不删」惯例并在 docstring 注明原因。顺序是先 close 释放再 unlink。
4. 改锁路径算法必须重启 server（新旧进程算出不同路径 ⇒ 期间互不互斥）。
5. 原子写入残留 `*.tmp.<PID>` 不影响功能（聚合按 `*.jsonl` 扫描），手工删即可；根治要补 `finally`/BaseException 兜底或启动期扫描。

## 判断逻辑
- Windows 下删除即探测：文件被任何进程打开时 unlink 抛 WinError 32，「删不掉」＝「有人在用」，清扫不会误删活跃锁。
- Unix 不可删根因是 inode race：等锁方持旧 inode fd，释放方 unlink 后新进程拿到新 inode，两把锁互斥失效。
- lint 侧补刀被否决：锁文件存在是常态，不能当 check 项上报（否则长期红灯）；Unix 同样踩 race；释放即删后残留上界已被钉死。

## 禁忌与反模式
- 不要在通用 `file_lock()` 层加释放即删（会删掉业务数据文件）。
- 不要用 `del /S` / `Remove-Item` 批量清 `.lck`（PowerShell profile 安全钩子会拦截），改用 Python 逐个 unlink。
- 不要把「注释承诺交给 lint_wiki sweep」当已实现——未落地的兜底要么做，要么删注释。

## 关键事实依据
- D19：7 文件 +109/−13，79 passed（Windows/Py3.14.5）；跨进程双进程各 +15 得 30 且仅 1 个锁文件。
- 锁文件 git-ignored、KB 级、上界＝曾被锁过的目标数，累积无正确性影响。
- Windows 路径大小写不同会算出不同哈希（内部路径经 root 归一化，风险极低）。
