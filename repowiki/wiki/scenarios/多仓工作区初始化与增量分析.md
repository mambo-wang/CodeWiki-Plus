## 工作场景
多仓工作区初始化流程、增量分析编排与代码扫描性能治理。适用于 init_workspace/add_workspace_repo 开发、analyze_workspace/analyze_repo 增量模式设计与超时排查。

## 适用条件
初始化/扩展多仓工作区、改 init/bootstrap 流程、实现或排查增量模式、分析扫描超时与文件数爆炸。

## 核心 SOP
1. **工作区痕迹齐备时跳过 init_workspace，直接跑 bootstrap 补 clone**：bootstrap.ps1/.sh 已登记业务仓、.gitignore 已排除 /codewiki-plus/、repowiki/ 骨架存在时，直接跑 bootstrap（避免重复生成 wiki tree、强制覆盖 AGENTS.md 约定块）；clone-only 保留作误调兜底。
2. **clone-only 短路仍必须写 workspace.json 并询问用户模式**——任何短路优化都先列出必要产物 checklist。
3. analyze_workspace 增量模式内部自动判断做主路径（agent 多半无脑传全量），留 `force=true` 逃生门，不加 repos 白名单（YAGNI）。
4. **增量锚点复用 metadata.json 已有的 commit_id**，不新建 analysis_state.json：一个机制覆盖首跑/新登记仓/代码变更/版本升级/锚点丢失，后两者安全降级为该仓全量。
5. 三档分派：workspace_analyzer 对每仓判定「跳过复用缓存 / 全量重跑 / deferred」；拓扑合并从各仓 SQLite 读 routes，跳过仓近乎零增量成本。
6. **登记业务仓后不自动生成 Wiki**：登记只负责登记表 + 克隆，Wiki 生成全部显式触发（最小惊讶原则）。
7. **性能问题先实测计数再下结论**：analyze_repo 超时曾被归因 `.venv`（实际早已在 DEFAULT_IGNORE_PATTERNS 且生效，file_tree 中 .venv 文件为 0），真正拖累是 agent 临时目录 `.caveman-tmp`（929 文件占 65%，含 495 个第三方 .go，首次 detect_services 撞上 Go 项目卡死事件循环）。补进 `.caveman-tmp`/`.qoder`/`.workbuddy` 后 file_tree 1439→505、完整分析 11.1s。跑探测脚本统计路径段分布，用实测证伪「理所当然」的根因。
8. **增量信号三源并存不去重**：affected_modules（git diff）+ stale_pages（manifest 文件级）+ stale_evidence_pages（证据级漂移，ADR-0005，覆盖不在模块树的 notes/entities/concepts 共享池页）；no_changes 短路不跑证据漂移（显式取舍），漂移出口是显式 lint。信号形态 `{页面: {stale/missing/unresolvable 计数}}`，明细留 lint，hint 引导复核 + re-stamp 而非重写。

## 判断逻辑
- bootstrap 脚本读同一张登记表也能补 clone，不必走 MCP 往返。
- initialize_wiki_tree 基本幂等，但 write_workspace_conventions 是强制覆盖，重复执行有副作用。
- 增量收益拿在正文层：analyze_changes 出受影响清单，agent 只重写清单页面。
- 语义不同的双重报告（文件级变更 vs 证据级漂移）是诚实的，不为美观去重。
- 证据只驱动提醒，不自动改写文档。

## 禁忌与反模式
- 不在 clone-only 短路时跳过 workspace.json 与模式询问。
- 不在登记业务仓后自动触发 init_wiki/analyze_repo/analyze_workspace。
- 不新建 analysis_state.json 做增量锚点。
- 不凭直觉归因性能问题；不把 agent 临时目录留在代码扫描范围内。
