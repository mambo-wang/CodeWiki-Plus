## 背景

宿主 Agent（Mode C）蒸馏多个对话文件时，按 prepare→提取→submit 流程把每个文件的 transcript 都读进上下文，多文件内容累积导致上下文撑满（302 轮大对话一次就占满）。

## 讨论走过的弯路

先后讨论了「prepare 内联 transcript 截断」「分块读取 vs 整体蒸馏」「map-reduce 分治 + summary 聚合」等复杂方案，最终都被回退或搁置（代码已回退到原状）。

## 正确做法（用户最终澄清）

蒸馏本身就是**逐文件独立**进行的（`_distill_one` 每个文件一次 LLM 调用，文件间不共享上下文）。宿主 Agent 应遵守操作纪律：

1. 蒸馏完一个文件 → `submit` 保存 notes/memories（确定性落盘）
2. **立即触发 Agent 上下文压缩（compact）**，清掉已处理的 transcript
3. 再蒸馏下一个文件

## 根因

误把「宿主 Agent 上下文撑满」当成「蒸馏 LLM 窗口问题」去解，引入了不必要的复杂度。真正解法是操作纪律：每文件完成后主动压缩上下文，让已处理内容不再占用窗口。

## 边界

这是宿主 Agent（Mode C）侧的操作纪律，不是 `distill_conversation` 工具的责任；Mode A/B 后台独立 LLM 逐文件调用，天然无此问题。
