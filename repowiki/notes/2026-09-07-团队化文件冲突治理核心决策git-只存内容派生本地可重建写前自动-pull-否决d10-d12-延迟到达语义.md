## 背景

2026-09-01 调研「CodeWiki 保持本地 MCP + repowiki 目录 + git 同步形态下如何减少团队文件冲突」，产出设计方案 docs/团队化文件冲突治理与同步策略设计方案.md（Rev. 2，含 D1-D12 决策记录、12 项改造点、四期计划）。teamai-cli 源码级机制调研见既有笔记（2026-09-01-teamai-cli-多人文件冲突处理全景），本条记录的是**我们自己的设计决策**。

## 核心原则（D1）

git 只存「内容」；一切索引/派生/运行态本地可重建（把 search_index.json 的 T3 先例扩展为通则）。

## 写前自动 git pull：否决（§6.3 五条论证）

1. 时机不成立：git 冲突发生在 merge/push 时刻不在写时刻，写前 pull 只缩小过期基线窗口，代价是每次写付网络往返；2. 业务工作树不可行：pull 遇脏重叠文件直接拒绝，--autostash 会 stash 用户代码，工具擅改用户工作区是红线；3. MCP 高频小操作付 0.5~3s 延迟、离线不可用；4. 方向反了——降冲突的是 push 频率（高频小步 push），不是 pull；5. pull 只是挪冲突时机，冲突面只挪不消。替代：写前 fetch 校验（advisory）+ 集中式会话边界 --ff-only pull + 高频小步 push。

## 三形态冲突面

- 单仓：完整冲突面（wiki 整页重生成、schema.yaml 时间戳 churn、.meta/ 整文件重写 JSON、可重建缓存入库、log.md 顶部插入、notes 无 owner）。
- colocated（多仓同仓式）：结构性冲突概率最低——冲突面按仓天然切分。
- centralized（多仓集中式）：modules 按仓分区隔离最大冲突面，但派生/索引文件升格为全局单点（index/log/repo-map/.meta/schema.yaml = 所有人×所有仓）。

## teamai-cli 对照落地决策（Rev. 2 并入）

- D10：auto_push 失败改 fetch+rebase 重试 ≤5 次（失败即 --abort 进下一轮），耗尽保留本地提交等下次搭载，永不 force。
- D11：搭便车语义门控——同仓式/单仓默认工具零 git 动作，知识随业务仓自身同步节奏到达。
- D12：「数据不丢，延迟到达」降级不变量——失败只降级为待搭载，本地盘恒为真相，幂等是搭载前提。
