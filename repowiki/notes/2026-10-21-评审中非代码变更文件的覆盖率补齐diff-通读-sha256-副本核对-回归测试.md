## 背景

用 `review_changes(mode='prepare')` 评审 `HEAD~3..HEAD` 三个提交时，`target.changed_files` 共 7 个文件，但 `changed_sources` 只覆盖 3 个代码文件的行级切片；其余 4 个是测试文件、`.trae/hooks.json` 与 hook 安装副本。评审纪律要求每个变更文件都有去向（进 findings 或进 skipped），而非代码文件拿不到行级切片。

## 正确做法（按序执行）

1. `git diff <range> --stat` 看整体规模，再对每个未覆盖路径单独 `git diff <range> -- <path>` 通读全文，确认是其声称的变更；
2. 多副本类变更（`codewiki/hooks/task_session_start.py` 与 `.trae` / `.codebuddy` / `.qoder` 下的安装副本）用 SHA256 逐一比对（`Get-FileHash -Algorithm SHA256`），确认源文件与各安装副本哈希一致，才能证明「副本同步」这条变更成立；
3. 直接读宿主配置实物（如 `.trae/hooks.json`），确认其命令格式与 `codewiki/cli/utils/ide_config.py` 的平台适配生成逻辑一致（当时已是单解释器快照）；
4. 跑命名约定建议的回归测试：先 `tests/test_install_hooks.py` + `tests/test_task_session_start.py`，再补 `tests/test_wiring_matrix.py` + `tests/test_hook_registry.py`；
5. 每个文件在 findings 或 report.skipped 中写明去向，再 `review_changes(mode='submit')` 落盘（报告存于 `.codewiki/workspace/review_reports/`）。

## Rationale

测试、宿主配置、安装副本、schema 数据这类文件不进依赖图谱，`review_changes` 不会为其产出行级切片；不显式补齐就会触发 coverage 警告，或让这些文件在评审结论中凭空消失。哈希核对 + 实物读取 + 回归测试三者组合，能把「无切片文件」变成可辩护的评审证据。
