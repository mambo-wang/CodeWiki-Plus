## 背景

`improve-codebase-architecture` 扫描 `codewiki/mcp/` 包得出的架构摩擦结论。

## 7 个摩擦点（按严重度）

1. **HIGH**：`output_dir`/session 解析逻辑复制粘贴 7 处——`capture_conversation` 与 `distill_conversation` 各有一份几乎相同的 `_resolve_output_dir()`；`knowledge_loop` 里 6+ 处同构；已有 `workspace_result.resolve_session()` 却未复用。
2. **HIGH**：frontmatter 解析分散 10+ 文件——`cache.py` 有 `_parse_frontmatter_dict`/`_extract_frontmatter`，但 `doc_writer`(74处)/`knowledge_loop`(42处)/`source_ingest`(32处) 各自又实现一版。
3. **MED**：`registry.py` 巨型文件（2108 行，~85% 是 schema）——schema 与 handler 分离两文件，改一个工具跳两处。
4. **MED**：`_ide_hook.py` 绕过 dispatch 独立跑——直接 import handler 手工组装参数，绕过 schema 校验，参数行为可能与 MCP 路径漂移。
5. **MED**：`workspace.py` docstring 过时 + `session_id` 死参数——docstring 说 `.codewiki/sessions/{id}/`，实际是固定 `.codewiki/workspace/`。
6. **LOW**：`find_or_restore` 隐式副作用——查询工具静默重建 session，可能返回 stale path。
7. **LOW**：dispatch 内嵌 CBM enrichment 后置钩子——对 handler 返回值有隐式 JSON 契约。

## 关键事实

- **三派 output_dir 优先级不一致**：`session>od>rp`（capture/distill/source_ingest）、`od>rp>session`（knowledge_loop 的 confirm/reject/batch）、`od>session>rp`（其余 6 处）——同一语义三套实现，本身就是行为分裂源。
- `dispatch()` 已有统一异常兜底（`except Exception` → `{"error": str(e)}`），所以抛异常是安全契约。
