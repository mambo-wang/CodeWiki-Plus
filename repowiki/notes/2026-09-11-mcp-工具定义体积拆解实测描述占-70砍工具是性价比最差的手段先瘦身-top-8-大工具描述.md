## 背景

讨论「增强 CLI 对齐 MCP 是否更省 token」时，用 `get_all_tools()` 实测了 MCP `tools/list` 的载荷体积（2026-09-10，49 个工具）：**88,629 字符**，约 22k–35k tokens。关键在于这份 schema **每个 API 请求都要发一次**，与 agent 到底调不调 MCP 无关。

## 实测拆解

| 部分 | 字符 | 占比 |
|---|---|---|
| 工具级 `description` | 38,980 | 44% |
| 参数级 `description` | 22,839 | 26% |
| `enum` 取值 | 2,011 | 2% |
| 结构开销（JSON 键名/类型/嵌套） | 24,799 | 28% |

- **CJK 字符仅 20 个 / 88,629**：工具定义已经是全英文，「把中文说明改成英文」在工具侧收益接近 0，别把它当优化手段。
- **高度集中**：Top 8 = 29,298 字符 = 33%（`query_wiki` 5,655、`distill_conversation` 4,623、`skill_creator` 3,984、`ingest_source` 3,957、`lint_wiki` 3,832、`write_doc_file` 3,723、`ingest_note` 3,524）；Top 15 = 54%。
- **Bottom 15 个工具加起来只有 11,960 字符 = 13.5%**：砍掉 15 个能力只换 13.5%，是所有手段里性价比最差的。体积跟工具数量**不成正比**，跟参数数量与描述长度成正比——`query_wiki` 一个（18 参数）比最小的 10 个加起来还大。

## 正确做法（优先级反过来）

1. 先瘦身**大工具的描述**（Top 8 优先）：只留「何时用 + 关键约束 + 必填语义」，示例与长说明外移到 `docs/` 或 MCP prompt。描述类砍半 ≈ 省 31k 字符 ≈ 7.7k token/轮（-35%）。
2. **不要先砍工具数量**。
3. **不要顺带改参数**：改参数 = 改契约，会打断所有调用方；描述瘦身才是纯收益（Doctrine「改契约先分清校验层」）。
4. 防退化：保留易错参数的 `enum` 说明，并造 20 条 query 做人工前后对比——工具选错是语义问题，不会崩溃，跑测试发现不了。

## 注意：字符 ≠ token，中文档案会被低估

`injection_budget.py:90-99` 的 `estimate_tokens` 按 `chars/4` 折算，但它自己的 docstring 写着「zh ~1.5 tokens/char, en ~0.25」。中文为主的文本（如 AGENTS.md）用 /4 会严重低估真实 token。汇报收益时说清是字符口径还是 token 口径，别把 -36% 字符当成 -36% token。

## 适用范围

任何「优化 MCP/AGENTS.md 常驻体积」的取舍判断：先量拆解再动手，直觉上的「砍数量」往往是错的那一刀。
