# Open Code Review — Delegation Mode

A skill for performing AI code review where OCR provides deterministic engineering (file filtering, rule resolution) and the host agent performs the actual review using its own intelligence and tools.

## Why Delegation Mode?

If you've used general-purpose agents for code review, you've likely encountered:

- **Incomplete coverage** — On larger changesets, agents tend to "cut corners," selectively reviewing only some files
- **Position drift** — Reported issues frequently don't match the actual code location
- **Unstable quality** — Natural-language-driven skills are hard to debug, and review quality fluctuates with minor prompt variations

Delegation mode solves this by splitting responsibilities:
- **OCR (deterministic code)** handles file selection and rule resolution — tasks that must not go wrong
- **Host agent (LLM)** performs the actual review reasoning — where dynamic decision-making excels

Benefits:
- Zero LLM configuration on OCR side
- Reuses host agent's subscription quota
- Stable, predictable file filtering and rule matching

## Workflow

Follow these seven steps strictly. Do not skip steps or deviate from the protocol.

### Step 1: Preview — Determine What to Review

```bash
ocr delegate preview --format json [--from <ref> --to <ref>] [--commit <hash>] [--exclude <patterns>]
```

This outputs JSON containing:
- **mode** (workspace / range / commit)
- **from / to / commit / merge_base** — ref metadata for constructing git commands
- **reviewable_files** — array of files to review (paths, status, insertions/deletions)
- **excluded_files** — array of files skipped, with exclusion reasons

**Common invocations:**

| Scenario | Command |
|----------|---------|
| Workspace changes (staged, unstaged, untracked) | `ocr delegate preview` |
| Branch comparison | `ocr delegate preview --from main --to feature` |
| Single commit | `ocr delegate preview -c abc123` |

**Important:** Parse the JSON output and extract the `reviewable_files` array. These are the files you MUST review.

### Step 2: Get Rules for Files

```bash
ocr delegate rule --format json <path1> <path2> ...
```

Pass ALL reviewable file paths from Step 1. Output is grouped by rule content — files sharing identical rules appear under one group, avoiding repetition.

Each rule group contains:
- **source** — where the rule comes from (built-in, custom, etc.)
- **pattern** — file pattern this rule matches
- **text** — the actual rule content to apply

**Important:** Build a checklist mapping each file to its rule groups. Use `(path, status)` as the identity — in workspace mode, the same path can appear twice (e.g., staged delete + untracked recreate).

### Step 3: Get Diffs

Choose the diff command based on the mode and refs from Step 1. Use `git --no-pager` for all commands:

- **range mode:** `git --no-pager diff <merge_base>..<to> -- <path>`
- **commit mode:** `git --no-pager show <commit> -- <path>`
- **workspace mode (tracked files):** `git --no-pager diff HEAD -- <path>`
- **workspace mode (untracked files):** Read the entire file content — the whole file is new code

### Step 4: Review Each File Thoroughly

For each file in `reviewable_files`:

1. **Get the diff** using the appropriate command from Step 3
2. **Identify applicable rules** from the rule groups (Step 2)
3. **Review the code** against each rule in the checklist
4. **Mark the file** as `reviewed` or `skipped` (with specific reason)

**Critical constraints:**

- **Review ALL files** — Do not stop after finding the first high-severity issue
- **Process in batches** — Group files by shared rules for efficiency
- **No silent skips** — Every file must have a destination: reviewed or explicitly skipped with justification
- **Deep review** — Read the full file context when needed, not just the diff

### Step 5: Structure Your Findings

For each issue found, output a structured comment with:

**Required fields:**
- `path` — file path where the issue occurs
- `content` — description of the issue and suggested fix

**Optional fields:**
- `start_line` — starting line number
- `end_line` — ending line number
- `category` — one of: bug, security, performance, maintainability, readability, best_practices, other
- `severity` — one of: critical, high, medium, low

**Example:**
```json
{
  "path": "src/auth/login.go",
  "start_line": 45,
  "end_line": 47,
  "category": "security",
  "severity": "high",
  "content": "SQL injection vulnerability: user input is concatenated directly into the query. Use parameterized queries instead."
}
```

### Step 6: Generate Coverage Report

Before presenting results, you MUST verify coverage and output a report:

```
Total files: <total_files>
Reviewed files: <reviewed_files>
Skipped files: <skipped_files>
Coverage rate: <coverage_rate>%
```

**Coverage is mandatory.** You cannot silently skip files. If coverage is below 100%, explain why each file was skipped.

### Step 7 (Optional): Fix Issues

Only when the user explicitly requests "review and fix":

- **Critical/High severity:** Fix directly
- **Medium severity:** Describe the fix, let user decide
- **Low severity:** Skip unless trivial

## Key Principles

1. **Deterministic engineering first** — Trust OCR's file selection and rule resolution. Do not second-guess which files to review.

2. **Complete coverage** — Every reviewable file must be processed. No exceptions.

3. **Rule-driven review** — Apply the rules from Step 2 systematically. Do not invent your own review criteria beyond what OCR provides.

4. **Precise locations** — When reporting issues, provide accurate line numbers. Verify against the actual code.

5. **No early termination** — Do not stop after finding the first issue. Complete the full review.

## Troubleshooting

**OCR CLI not found:**
Install via `npm install -g @alibaba-group/open-code-review` or download from GitHub releases.

**Empty reviewable_files list:**
Check that you have uncommitted changes or specify the correct refs with `--from` and `--to`.

**Rules seem incomplete:**
OCR's rule engine is deterministic. If rules seem missing, check `.opencodereview/rule.json` for custom rules.
