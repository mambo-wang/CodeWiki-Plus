  - 给出“最小可行融合（MVP）”范围与对应工作量。

  - 工作量分档表：形态 / 估算区间 / 主要假设。

# 结论（resolved）

采用用户选定的**借鉴式（对话→Wiki 提取）**形态，工作量与风险如下。

## 工作量分档（以 1 人估算）

| 形态 | 估算区间 | 主要假设 |
|---|---|---|
| 内置集成 | 2-4 人月 | 需补 L0 对话采集、L3 画像、ACL 多租户、Skill 体系 + 引入 Node 服务 |
| 桥接(MCP/SDK) | 2-4 人周 | 写入口(ingest_note→TAM) + 读入口(TAM MemoryProxy→query_wiki) 适配 |
| **借鉴(对话→Wiki)** ✅ | **3-6 人周** | 纯 Python；建 L0 对话采集 + L1 语义原子抽取 + L2 场景聚类，复用 `repowiki/` 与 `ingest_note` |

## MVP 范围（借鉴式）
1. 对话采集入口（IDE/agent 把对话 turns 落盘）。
2. L0→L1 抽取管线（LLM 蒸馏为语义原子：事实/偏好/约束/事件）。
3. L1→L2 场景聚类 + 自动建议 `ingest_note`，复用现有确认飞轮。
4. 输出并入 `repowiki/` 知识笔记，可被 `query_wiki` 检索。
≈ 3 人周。

## Top 风险
1. **对话采集链路缺失**（CodeWiki-CN 当前不接对话流）——首要工程量。
2. **抽取质量/幻觉**：L0→L1 需评测集，否则噪声污染 Wiki。
3. **与 TAM 许可/演进节奏**：仅借鉴设计不引入代码，许可风险低；但需跟踪 TAM 抽取范式更新。
4. **重复造轮子**：L2 场景聚类与现有 CodeWiki 文档生成有重叠，需明确边界避免两套知识库。

## 缓解
- MVP 先只做"对话→经验 note"闭环（复用 `ingest_note` 确认），不上 L3/ACL。
- 抽取结果一律走人工确认飞轮（AGENTS.md 沉淀流程）再落盘。
