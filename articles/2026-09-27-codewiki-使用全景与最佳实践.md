# CodeWiki-Plus 使用全景：从初始化到自生长的团队知识库

> 写作时间：2026-09-27 · 本文是「迎风追日 / WanderingBug」公众号 CodeWiki-Plus 系列专栏的总结篇，把前 12 篇讲过的能力按实际使用顺序串成一条路线，可当作新项目的上手指南，也可当作系列文章的索引。

**TL;DR:** CodeWiki-Plus 是一个由 AI IDE 自身模型驱动的仓库知识引擎，零 LLM API 配置，53 个细粒度 MCP 工具。但工具多不等于都要用：正确的路径是分层的——先做一次性的安装接线，再按需初始化，代码 Wiki 首次全量之后永远增量，日常开发让检索和笔记转起来，任务管理和团队记忆在长线工作中按需启用，最后用治理机制让知识库越用越准。本文给出这条路线的完整地图，每一步附上对应专栏文章的深度展开。

---

## 一、这个项目解决什么问题

原版 CodeWiki 是一个优秀的仓库级文档生成框架，Tree-sitter AST 解析、依赖图构建、拓扑排序这些工具链都不需要 LLM。但它有两个使用门槛：必须自行配置 LLM API（申请 Key、选 provider、处理模型兼容性），且整个生成过程是黑盒，用户无法中途干预。

CodeWiki-Plus 的改造思路是把 MCP Server 从「黑盒式一键生成」拆成 53 个细粒度工具，让它退化为纯工具链服务器。真正需要 LLM 智能的 4 个环节（模块聚类、文档撰写、子模块递归、总览合成），恰好是 AI IDE 的 Agent 最擅长的事：

```
改造前：
  IDE → generate_docs(repo) → [CodeWiki 内部调用 LLM API] → 结果

改造后：
  IDE Agent → analyze_repo → read_code → (Agent 自己推理) → write_doc → overview
              ↑ 纯工具       ↑ 纯工具    ↑ IDE 自身模型      ↑ 纯工具
```

这个架构决策的完整来龙去脉，见[专栏开篇词：从代码文档到 AI 知识引擎](https://mp.weixin.qq.com/s/WpjiDAs62_81mytBWUsDQw)；「一套 Prompt 同时服务人类读者和 LLM 消费者」的双层设计，见[第 2 篇：双层 Prompt 架构同时服务人和模型](https://mp.weixin.qq.com/s/1lNjR_SsrU5Fp2NKnkxnMA)。

理解了这条主线，后面的使用顺序就顺理成章了。

## 二、第一步：安装与初始化（一次性）

### 2.1 三步安装

```bash
# 1. 安装（Python 3.12+；Node.js 可选，用于 Mermaid 校验）
pip install codewiki-plus
codewiki --version

# 2. 配置 MCP Server（CodeBuddy 示例，Cursor / Claude Desktop 同理）
```

```json
{
  "mcpServers": {
    "codewiki": {
      "command": "codewiki",
      "args": ["mcp"],
      "maxOutputLength": 500000,
      "timeout": 36000000
    }
  }
}
```

配置完成后，工具列表里应出现 53 个 `codewiki` 工具。

第 3 步决定后面几层能不能转起来：

```bash
# 3. 接线团队记忆 Hook（检测到哪些 IDE 配置目录就为哪些接线）
codewiki install-hooks --repo-path <repo>
```

这一步拷贝 hook 脚本、幂等合并 settings.json 注册、往 AGENTS.md 写入任务引导段。命令路径一律是项目相对形式，队友克隆到任意目录都能直接工作。支持 CodeBuddy、Qoder、Claude Code、TRAE（hook 档）和千问办公（prompt 档）。

### 2.2 环境变量：真正要设的只有 2 个

开箱即用，默认零配置。值得设的只有：

- `CODEWIKI_LANG`：想用英文界面时设 `en`（默认中文）；
- `CODEWIKI_USER`：遥测署名花名，不想用 git 真名署名的成员设一个。

注意环境变量要写在 MCP 配置 JSON 的 `env` 块里（MCP 进程只在启动时读一次），写 `.bashrc` 对它不可见。`CODEWIKI_RAW_TOOL_DETAIL` 默认开启，除非排障否则别关，关掉会导致后续无法编译出含完整步骤的技能。

### 2.3 初始化：单仓还是多仓

**单仓用 `init_wiki`：** 创建 `repowiki/` 目录骨架和项目级 `schema.yaml`。最佳实践是初始化后第一件事就编辑 `purpose` 字段，用一两句话写清项目定位。它是整个知识库的「宪法」，后续文档生成、检索路由都参考它。这是全库杠杆率最高的一次人工投入。

**多仓用 `init_workspace`：** 面对微服务群、前后端分离这类多业务仓场景。首次初始化会强制征询知识布局选择：`colocated`（知识随仓走）还是 `centralized`（知识集中在工作区顶层），不传参数工具返回 `needs_layout_decision` 且不写任何产物。之后自动生成 bootstrap 克隆脚本、repo-map 导航、工作区级约定。重跑零配置幂等。多仓集中管理的完整方案见[第 9 篇：多仓 Harness 集中式管理方案](https://mp.weixin.qq.com/s/pA1CsLSAIqbeVqFV4-kVQQ)。

判断标准：团队是否在多个仓库间频繁跳转、需要跨服务调用分析？是，走 workspace；只给单个项目建知识库，走 wiki。

## 三、第二步：按需生成代码 Wiki

初始化完成后，在 Agent 模式输入一句话：

```
帮我分析当前仓库并生成 Wiki 文档，输出到 repowiki 目录。请使用中文撰写文档。
```

Agent 走五阶段流水线：

```
阶段 1: analyze_repo → 组件索引、叶节点列表
        （自动检测 monorepo 子服务，构建跨服务调用关系）
阶段 2: get_prompt("cluster") → 聚类规则
        read_code_components → 自主推理分组为 3-8 个逻辑模块
        save_module_tree 保存
阶段 3: 按叶优先顺序逐模块生成文档
        叶模块：read_code → 推理 → write_doc_file
        父模块：读子文档 → 合成总览
阶段 4: 生成仓库总览 overview.md
阶段 5: close_session 释放资源，构建 BM25 索引
```

流水线背后有三个质量机制，不需要手动干预但值得知道：

1. **Evidence-Based 断言**。每条业务规则要求附代码证据（文件:行号 + 置信度），`lint_wiki` 的 `unsupported_claims` 检查在超过 30% 断言无证据时报警。这是对 LLM 幻觉的硬约束，也是「文档可信」的第一块基石。
2. **代码路由分类**。组件自动分为 business / boilerplate / infra 三类，DTO、Config 这类模板代码只注入签名不注入全文，典型 Java 仓库省 30% 以上 token。
3. **BFS 调用上下文**。生成 Prompt 自动注入 1-hop 调用者/被调用者签名摘要，帮 LLM 理解跨模块关系。

由此得出这一层最重要的实践：**首次全量，之后永远增量**。代码有改动时说「帮我更新受影响的模块文档」，Agent 走 `incremental-update` 流程，通过方法级 `content_hash` 只重生成真正变化的部分。全量重生成既浪费 token，又会覆盖掉文档上的手工修订。

另一个容易漏的细节：生成完务必让 Agent 走到 `close_session`。搜索索引在这一步才构建，跳过它，下一层的 `query_wiki` 只能走降级路径。

## 四、第三步：让 Wiki 参与日常开发

生成只是起点，这一层开始知识库兑现价值。

### 4.1 检索：渐进式阅读，不要一步到位

```
query_wiki(mode=overview)       → 初次接触项目，<500 token 了解全貌
query_wiki(mode=directory)      → 按类型分区定位目标模块/实体
query_wiki(query="xxx", hop=1)  → 关键词检索 + 图谱关联扩展
query_wiki(mode=detail, page=...) → 深入阅读特定页面
```

从上往下逐层深入，每层有 token 预算约束。直接跳到 detail 读全文，一个大仓库就能吃掉几万 token。

检索引擎是 BM25 + jieba 分词 + wikilink 图谱多跳，零外部依赖，不引入向量库。为什么这样设计、SQLite 倒排索引怎么支撑跨会话复用，见[第 3 篇：零依赖检索设计](https://mp.weixin.qq.com/s/T7r-ojyWC-YOpM_U5BNbEw)。检索结果带 `source_type` 标注（auto_generated / developer_note / ingested_source）和置信度，draft 笔记带 `[unconfirmed]` 前缀，消费前看一眼标注。

### 4.2 改代码前：查影响范围

```
评估一下修改 OrderService.createOrder 的影响范围。
```

Agent 调用 `analyze_impact`，BFS 传递性遍历调用图，聚合到模块级，识别高风险组件。改之前先知道会波及谁，这是知识库驱动开发最直接的收益。

### 4.3 提交前：四维评审

```
用四维评审检查一下这次变更。
```

Agent 走 `analyze_changes` → `review_changes`，按团队沉淀的评审检查清单逐项核对。清单不是静态的：踩过的坑经确认后自动进入清单，下次同类变更会被自动检查。这套「让踩过的坑自动变成 CHECKLIST」的机制，见[第 8 篇：四维代码评审](https://mp.weixin.qq.com/s/wH_mjG5IL-0qo_qDFpODuw)。

## 五、第四步：知识写入与可信度治理

日常开发中会产生三类知识，各有各的写入通道。全景介绍见[第 4 篇：知识写入方式全景](https://mp.weixin.qq.com/s/V90mghqB5wttKd25eXA-Pw)。

### 5.1 三条写入通道

| 通道 | 工具 | 适用场景 |
|------|------|---------|
| 结构化笔记 | `ingest_note` | 踩坑、决策、教训，8 种类型 |
| 外部文档导入 | `ingest_source` | API 文档、RFC、设计规范 |
| 对话蒸馏 | `distill_conversation` | 对话中涌现的隐性经验 |

### 5.2 OKF v0.2 生命周期

所有笔记遵循 draft → stable → deprecated 状态流转，叠加 strong / weak / shadow 置信分层：

```
踩坑/决策发生
  → ingest_note(status="draft", confidence=weak)
  → 检索可见但标注 [unconfirmed]
  → confirm_note → 升级 stable，带证据（test_ref/commit_ref）升 strong
  → reject_note → 降 shadow，默认不再被检索返回
```

frontmatter 携带 type、generated、stale_after、verified 等标准化字段，兼容谷歌 Open Knowledge Format v0.2。规范细节与实战见[第 5 篇：OKF 0.2 规范介绍和实战](https://mp.weixin.qq.com/s/Dt748cHQCa7mfz1PEvgS6g)。

### 5.3 可信度三件套

让 AI 写的 Wiki 可信，靠的不是「相信模型」，而是三套机制：置信分层让检索排序区分对待（strong +0.10 / shadow −0.30）；冲突案卷让两条矛盾笔记显式立案、限时裁决，败方自动降级；outcome 信号让「用错的知识」在任务收尾时被报告，失败用例自动进入蒸馏提示的 negative_examples。完整论述见[第 10 篇：如何让 AI 写的 Wiki 可信](https://mp.weixin.qq.com/s/OdESdERtINqYTBkIIVFWlQ)。

实践要点：笔记确认时尽量带证据，strong 置信检索权重更高；`wiki_stats` 的 strong 占比是北极星指标（目标 >60%），低于阈值说明确认流程没跑起来，问题多半在流程不在工具。

## 六、第五步：按需启用任务管理

任务记忆解决「长线工作跨会话断片」：一个任务持续数天、横跨多个会话，Agent 每次重启都从零开始。它与 Wiki 笔记的分工是——**Wiki 笔记沉淀跨任务的通用经验，任务记忆保存任务范围内的进度知识**（做了什么、下一步、待办）。

接线原理：SessionStart 事件在会话开始时注入任务引导，SessionEnd 事件在会话结束时采集对话转录。Hook 机制的完整拆解见[第 6 篇：借助 HOOKS 机制实现跨会话记忆和任务管理](https://mp.weixin.qq.com/s/flsqORauNo0Th1v8G4Ceng)。

标准工作流：

```
会话开始：
  list_tasks(status="active") → 关联已有任务或新建
  → set_session_task 绑定会话（后续采集自动携带 task_id）
  → get_task_context 恢复上下文（描述 + 分层记忆 + 关联笔记）
  → pending_raw_count > 0：委托蒸馏 worker 后台补积压，不阻塞干活
  → compaction_due：顺手压缩旧记忆（原文进 archive，可找回）

会话过程中：
  关键进展 → add_task_memory 直写落盘（可逆操作免确认，ADR-0002）
  需要找回旧条目 → search_task_memories（条目级检索，archive 可搜）
```

三条硬约束：task_id 由标题生成且不可变，想改名只能删除重建；任务记忆直写免确认（有 archive 兜底，可逆），笔记必须走确认闸门（跨任务共享，不可逆），两套闸门是刻意区分的；记忆超阈值（40 条 / 24KB）自动触发压缩，Agent 顺手完成。

启用判断：任务当天能闭环，不需要这层；一旦工作以「周」为单位推进、经常换会话甚至换人接手，任务记忆的投入产出比会非常高。

## 七、第六步：团队化与知识飞轮

前面几层跑顺之后，这一层让知识库从「个人工具」变成「团队资产」。

### 7.1 对话经验分层提取

日常对话是最大的隐性经验来源。机制是：采集只落 raw 暂存区，永不自动蒸馏；蒸馏走 Mode C 协议（prepare 取 transcript → Agent 提取 → submit 入库），产出为 draft 待确认。确认后的笔记继续向上归纳：多条同主题笔记经 `consolidate_notes` 归纳为 L2 场景块，共识笔记经 `refresh_doctrine` 晋级为 L3 团队 Doctrine。分层提取的完整设计见[第 7 篇：记忆/经验分层提取——自生长的团队知识库](https://mp.weixin.qq.com/s/s253xe5LiUmgdfDo3xAbg)。

### 7.2 知识编译成技能

反复出现的经验模式可以编译成可执行的 SKILL.md 行为指令。两区制设计：草稿区进索引进 lint 但不生效，用户确认后 install 到生效区。从对话提炼经验到编译成技能的落地实践，借鉴自谷歌 WikiSkill，见[第 11 篇：从对话中提炼经验编译成技能](https://mp.weixin.qq.com/s/jpGqKd_pU-aLp2c9CryzgA)。

### 7.3 团队遥测与隐私

检索命中与采纳记录以 user_id 署名写入遥测并随仓库共享。不想用 git 真名的成员设 `CODEWIKI_USER` 花名，或在 `schema.yaml` 里关掉遥测退回纯本机模式。本地知识库团队化改造的完整方案，见[第 12 篇：本地知识库团队化改造](https://mp.weixin.qq.com/s/Ebsk6CoLN5Wj7ejwF3ytfQ)。

### 7.4 定期体检

| 动作 | 工具 | 节奏 |
|------|------|------|
| 体检 | `lint_wiki`（25 项检查 + health_score） | 每周或大变更后 |
| 归纳 | `consolidate_notes`（笔记 → 场景块） | stable 笔记积累到一定量 |
| 编译 | `skill_creator`（确认知识 → 技能） | 反复出现的经验模式 |
| 反馈 | `report_outcome`（报告用了某文档后成败） | 每次任务收尾 |

`report_outcome` 是 hit（看到）/ adopted（引用）之外的第三环信号，失败用例反哺蒸馏提示，让知识库不只是越攒越多，还会越用越准。

## 八、最佳实践清单

**该做的：**

1. `install-hooks` 在仓库初始化时就跑，别等记忆积压了才补
2. `schema.yaml` 的 `purpose` 字段认真写，它是文档质量的杠杆点
3. 生成完确认 `close_session` 执行了，索引在这一步构建
4. 代码变更后走增量更新，永远不要习惯性全量重生成
5. 检索从 `mode=overview` 开始逐层深入，先看 est_tokens 再 expand
6. 笔记确认时尽量带证据（test_ref / commit_ref），strong 置信检索权重更高
7. 任务收尾时 `report_outcome`，让失败经验反哺蒸馏
8. 每周跑一次 `lint_wiki`，health_score 连续下降要查流程

**不该做的：**

1. 不要把环境变量写进 `.bashrc` 指望 MCP 进程读到，写 MCP 配置的 `env` 块
2. 不要跳过确认闸门直接引用 draft 笔记的结论
3. 不要在任务记忆和 Wiki 笔记里记同样的内容，通道互斥，各记各的
4. 不要关 `CODEWIKI_RAW_TOOL_DETAIL`（除非排障），关了之后技能编译缺素材
5. 不要给短期任务强上任务记忆，当天闭环的工作用不上这层

## 九、一个常见的落地误区

不少团队把 CodeWiki-Plus 当「文档生成器」用：装好、生成一次、把 repowiki 提交进仓库，结束。三个月后文档和代码一起腐烂，最后得出「AI 文档不靠谱」的结论。

问题不在生成质量，在于只跑了前几步就停了。这个系统的设计意图是：生成只是把代码里的显式知识搬进可检索的结构，而检索、笔记、任务记忆、治理这些环节才把对话里的隐性经验（为什么这么选、踩过什么坑、什么条件下绕过）持续注入同一个结构。增量更新让文档跟着代码走，确认闸门让经验可信，outcome 信号让错误知识被淘汰。飞轮转起来，知识库才会比任何一份手写文档活得更久。

接入成本其实很低：安装初始化半小时，日常沉淀是对话里顺口一句「记一下这个坑」，任务管理和治理各自第一次用时照着 workflow prompt 走一遍就会了。从单仓 `init_wiki` 开始，用到哪层开哪层。
